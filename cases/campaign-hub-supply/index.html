기존 캠페인 탐색 경험에 새로운 광고 공급 연결하기

목록의 모양은 같아도 공급 종류가 바뀌면 클릭과 참여 목적지가 달라진다. URL 입력을 캠페인 객체로 넓히고, 해당 함수를 호출하는 목록·진행 카드·보너스도 함께 수정한 경험.

여러 캠페인을 탐색하고 진행 중인 참여를 확인하는 허브에 새로운 광고 공급을 넣었습니다. 목록에서는 같은 카드로 보여도 직영 캠페인과 광고 네트워크 캠페인의 참여 목적지는 달랐습니다. 카드에 URL 하나를 넘기던 입력만으로는 어느 실행 경로를 사용할지 설명하기 어려웠습니다.

기존 허브는 일반 화면과 매체 전용 화면이 클릭 로직을 공유하고 있었습니다. 새로운 종류를 처리하는 분기 하나를 추가하면 끝나는 것이 아니라, 같은 callback을 부르는 목록과 진행 카드, 보너스도 바뀐 입력을 전달해야 했습니다.

먼저 종류가 어디까지 영향을 주는지 물었다

서버 담당자에게 종류 구분이 필요한 범위와 적용 매체, 기간 종료·예산 등 오류 응답을 확인했습니다. 다른 문의 제품의 일정에 미칠 영향도 제품 담당자에게 공유했습니다.

초기에는 별도 요청과 서버 redirect 방식도 논의했습니다. 최종 FE 구현에서는 기존 클릭 생성 요청을 유지하고 확장된 응답을 사용했습니다. 초기 논의의 방식이 그대로 구현된 것은 아닙니다.

URL보다 선택한 캠페인을 입력으로 받았다

공유 클릭 callback의 입력을 URL에서 캠페인 객체로 넓혔습니다. 클릭을 생성한 뒤 새 공급 종류라면 응답의 랜딩 URL과 추적값을 기존 광고 네트워크 참여 화면으로 연결했습니다. 일반·custom 캠페인의 분기는 유지했습니다.

선택한 캠페인
  → 기존 클릭 생성 요청
  → 공급 종류와 응답의 랜딩·추적값
  → 해당 참여 화면

기존 광고 네트워크 참여 화면이 받는 값을 사용해 새 공급의 참여를 연결했습니다. 서버가 공급·할당을 정하면 FE는 그 결과로 사용자에게 열 목적지와 추적값을 전달했습니다.

공유 함수를 바꾸면 실제 호출자도 함께 봐야 했다

입력 타입만 바꿔서는 호출자가 가진 캠페인 정보가 전달되지 않습니다. 전체·진행 중 목록과 보너스 dialog도 캠페인 객체를 넘기도록 바꿔, 공용 로직이 공급 종류를 판단할 수 있게 했습니다.

당시 코드는 랜딩 응답을 타입 단언해서 사용했습니다. 이 변경에 모든 런타임 검증이 들어 있었다고 설명할 수는 없습니다. 이후 다른 제품에서 기사 카드를 통합할 때는 응답을 unknown으로 받아 실패 단위를 나눈 처리를 사용했습니다. 제품과 시기는 다르지만, 타입의 약속과 실제 입력을 구별하는 관점으로 비교할 수 있습니다.

같은 카드를 클릭하는 일이 달라졌다

새 공급을 기존 허브의 캠페인 모델과 호출 코드에 연결하고, 해당 참여 화면으로 이동하도록 수정한 코드가 병합됐습니다. 목록의 모양보다 그 카드가 어떤 참여를 시작하는지가 바뀐 작업이었습니다.

URL만 받던 함수에 캠페인 객체를 넘기면서 다음 참여 화면을 고를 정보를 전달할 수 있게 됐습니다. 이 경험 이후에는 공용 로직에 새 종류를 추가할 때, 분기 자체와 함께 실제 호출자가 판단에 필요한 값을 넘기는지도 확인해야 한다고 생각합니다.
