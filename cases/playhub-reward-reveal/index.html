외부 페이지 복귀 후 리워드 안내 복구

서버의 보상 성공과 화면의 금액 공개를 나눠 기록했다. 문서 교체 뒤 안내를 복구하면서, 지연된 표시 확정이 만드는 중복도 다룬 이야기.

복귀 보상 안내의 미공개 기록·재생·가시성 경합 처리
시기
2026.07
주제
#복귀 #보상 안내 #문서 수명주기

외부로 이동했다 돌아온 사용자의 보상은 처리됐는데, 받았다는 안내가 사라지는 경우가 있었다. QA와 상용 확인에서 나온 문제였다. 고객 문의 담당자는 금액이 적어 보이거나 지급받지 못했다고 인지할 수 있고, 문의하지 않고 떠나는 사용자에게도 안내가 필요하다고 설명했다.

서버 성공 응답을 받은 함수 안에서 오버레이를 여는 것만으로는 부족했다. 이동·복귀 중 웹 문서가 교체되면 그 화면 상태도 사라질 수 있었다. 지급 요청을 다시 보내지 않고, 아직 공개하지 않은 안내만 이어갈 방법이 필요했다.

지급 요청을 다시 실행하는 문제로 보지 않았다

보상 처리와 보상 금액 공개는 다른 사건이었다. 서버가 성공했다고 해서 새 문서가 사용자에게 금액을 보여줬다는 뜻은 아니다. 반대로 안내가 없다고 지급 요청을 다시 보내면 표시 문제를 서버 처리 문제로 바꾸게 된다.

나는 성공 결과를 받은 시점과 안내가 공개된 시점을 따로 기록했다. 새 문서가 이어서 사용할 UI의 성공 정보와 표시 여부를 보관하는 기록이었다.

문서가 바뀌어도 미공개 성공을 이어받게 했다

성공 후 아직 공개되지 않은 marker를 저장하고 새 문서에서 읽었다. 아무 기록이나 복구하면 다른 사용자나 오래된 보상이 섞이므로 신원·당일·유효기간 조건을 확인했다. 새 문서의 상태 조회가 준비된 뒤에만 재생하도록 했다.

신원이 맞지 않는다는 이유로 저장된 모든 기록을 지우지도 않았다. 아직 신선한 다른 신원의 기록은 함부로 소비하지 않았다. 복구할 자격을 판단하는 것과 저장공간 전체를 정리하는 것은 별개였다.

설명용 의사코드이며 실제 회사 코드가 아니다.

onRewardSuccess(result) {
  savePendingReveal(result, identity, day, expiresAt);
}

onStatusReady() {
  const pending = readPendingReveal();
  if (matchesCurrentContext(pending)) showReveal(pending.amount);
}

onRevealVisibilityChange() {
  if (revealIsOpen && documentIsVisible) commitRevealNow();
}

오래 보여준 뒤 확정하는 방식에도 경합이 있었다

첫 복구만으로 끝나지 않았다. 안내가 visible 상태가 된 뒤 일정 시간 기다려 표시 완료를 기록하는 구현에서는 그 사이 문서가 교체될 수 있었다. 이전 문서가 공개했어도 표시 확정 timer는 취소되고, 새 문서는 미공개 marker를 읽어 같은 금액을 다시 연출했다.

그래서 공개 상태와 문서 가시성이 함께 확인되는 즉시 표시 기록을 확정하도록 바꿨다. hidden 문서에서 오버레이 상태만 열렸다면 소비하지 않고, visible로 돌아오는 시점에 다시 확인했다.

표시 확정의 기준은 UI가 공개 상태이고 문서가 visible이라는 클라이언트 신호였다. 이 조건이 맞는 시점에 기록을 남겨 다음 문서가 다시 미공개 안내로 읽지 않게 했다.

지연 확정과 조기 소비를 서로 다른 테스트로 막았다

회귀 테스트는 ‘나중에 표시 기록이 생겼는가’보다 엄격한 시점을 사용했다. visible 상태로 안내가 열린 바로 그 시각에 표시 시각이 기록돼야 했다. 다시 timer를 넣으면 이 기대 결과를 만족하지 못한다.

입력·실행 순서기대 결과
성공 기록→상태 준비→미공개 marker 읽기안내 재생
신원·날짜·유효기간 불일치해당 안내 재생 금지
안내 공개, 문서 visible같은 시점에 표시 기록 확정
안내 공개, 문서 hidden표시 기록 미확정 유지
hidden 공개 후 visible 복귀복귀 시 표시 기록 확정
저장소 읽기·쓰기 실패실패 경로 처리, 정상 저장으로 가장하지 않음

가짜 시간·가시성·저장소를 쓰는 hook 테스트로, 문서가 visible이 되는 시점에 표시 상태를 소비하는 판단을 고정했다.

기록은 발견 이후의 흐름도 읽게 했다

write·replay·discard·commit·error를 나눠 진단 이벤트를 남겼다. 단순히 안내가 열렸다는 하나의 이벤트보다, 성공 정보가 기록됐는지 새 문서에서 재생됐는지 어떤 조건으로 버려졌는지 읽을 수 있었다.

QA와 상용 확인에서 찾은 문제를, 구현 이후에는 이 기록으로 이어서 조사했다. 상태 흐름과 전후 관측을 읽을 때도 활용했다. 상세 로그를 어떻게 줄였는지는 고정 표본 수집의 이야기에서 다룬다.

복귀한 사용자가 안내를 이어받는 변화

수정 후 나는 같은 길이의 전후 관측을 공유했고, 제품 담당자는 많이 개선됐다고 반응했다. 성공한 보상을 새 문서가 미공개 안내로 이어받고, 공개된 안내는 문서 교체 뒤 다시 재생하지 않도록 바꾼 결과였다.

지금 돌아보면 보상 UI는 성공 응답 뒤에 잠깐 붙이는 장식이 아니었다. 성공이 존재하는 시간과 그 성공을 공개하는 문서의 수명이 달랐다. 그 사이를 잇는 작은 기록과 정확한 소비 시점이, 사용자가 이미 받은 혜택을 이해할 수 있는 흐름을 만들었다.
