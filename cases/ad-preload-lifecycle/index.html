광고의 기다림을 줄이며 실제 노출의 의미 지키기

#프리로딩 #SDK 수명주기 #집계 기준

사용자가 광고 보기 버튼을 눌러도 바로 광고가 나오지는 않았습니다. 광고를 할당받고 SDK를 준비하는 시간이 필요했기 때문입니다. 참여 의사를 밝힌 뒤에도 기다려야 하는 흐름이었고, 사업 담당자도 이 대기와 광고 건너뛰기를 연결된 문제로 보고 있었습니다.

저는 6월부터 서버 담당과 요청·응답·timeout을 협의하고, 버튼을 누르기 전에 광고를 준비하는 프론트엔드 구현을 맡았습니다. 7월에는 제품에 통합해 적용했고, 8월에는 집계와 세션을 후속으로 살폈습니다. 디자인이 준비한 화면 시간 안에서 SDK를 준비하면 클릭 뒤의 기다림을 줄일 수 있었습니다. 다만 SDK를 먼저 만들면 공급사의 관측도 먼저 시작될 수 있어, 미리 준비한 광고를 언제부터 실제로 사용한 광고로 볼 것인가를 함께 정해야 했습니다.

요청을 나눠도 표시 순서는 유지해야 했다

SDK 설정과 일반 광고 요청을 분리하면 SDK가 먼저 도착해 준비할 수 있었습니다. 다만 먼저 준비됐다는 이유로 표시 순서를 바꾸면 서버가 의도한 우선순위와 달라집니다.

초기 협의에서 저는 최종 순서를 서버에서 받을 수 있는지 물었습니다. 요청을 분리할 때 서버가 관리해야 할 상태를 논의한 뒤, 프론트엔드에서 display weight를 기준으로 두 응답을 병합하기로 합의했습니다. timeout도 필터 조합의 부수 효과로 바꾸기보다 요청 입력으로 명시하자고 제안했습니다. 서버의 기본값·상한 방식에 동의했고, 프론트엔드는 분리 응답과 settle 상태를 소비했습니다.

분리 흐름은 선택적으로 활성화하고 기존 단일 요청 경로를 유지했습니다. 서버의 할당 정책과 응답 필드는 서버 담당이, 표시·회차·flag·계측·mock과 QA 연결은 제가 맡았습니다.

준비 완료와 사용자에게 표시됨을 분리했다

초기 hidden 방식은 응답 데이터만 cache한 것이 아니었습니다. SDK 광고를 생성하되 화면에서는 숨긴 뒤 실제 표시 시점에 드러냈습니다. 따라서 준비됨과 표시됨을 같은 상태로 처리할 수 없었습니다.

아래는 상태 구분을 설명하는 재구성이며 실제 회사 코드가 아닙니다.

const responses = requestSdkAndOtherAdsSeparately();
responses.sdk.then(prepareHiddenSdk);

async function showNext() {
  const candidates = mergeByDisplayWeight(await settle(responses));
  const session = choosePreparedOrCreate(candidates);
  await session.show();
  markActuallyShown(session);
}

실제 구현에서는 각 응답의 timeout·완료 상태와 재조회 request ID를 관리하고, 준비 신호와 사용 신호도 따로 두었습니다. 요청을 먼저 보냈다는 이유로 사용자가 광고를 보기 시작했다고 기록하지 않기 위해서였습니다. 다만 이렇게 상태를 나눠도 모든 공급사의 내부 동작까지 프론트엔드에서 통제할 수는 없었습니다.

빨라지지 않았다는 QA에는 적용 조건부터 확인했다

적용·미적용 영상을 공유한 뒤 일부 QA 대상은 빠르지 않다는 반응이 있었습니다. 먼저 같은 기능이 켜져 있는지 확인했고, 해당 대상의 flag가 누락돼 있었습니다. 타겟팅을 적용한 뒤 동료가 빠른 표시를 확인했습니다.

그 전의 QA에는 서로 다른 검증 환경과 mock 응답도 섞여 있었습니다. mock이 알려주는 준비 시간과 실제 공급사 SDK의 준비는 같지 않았고, 공급사마다 다른 대기도 남았습니다. 느리다는 반응을 구현 실패로 결론 내리기 전에, 비교 대상이 같은 실행 경로와 조건인지부터 맞춰야 했습니다.

요청이 줄었다는 숫자만으로 실행 실패를 정하지 않았다

프리로딩 적용 뒤 광고 기회와 노출 집계의 변화도 질문이 됐습니다. 저는 실제로 표시된 광고 기록과 최종 노출 로그를 맞춰 보는 분석을 진행했습니다. 미리 준비한 광고의 수와 사용자가 실제로 실행한 광고의 수는 같은 분모가 아니었습니다.

프리로딩이 아닌 경로에서도 기회가 줄어드는 모습이 있어, 준비 방식 하나로 전체 변화를 설명하기 어려웠습니다. 요일과 이용 패턴, 광고 구성처럼 함께 바뀔 수 있는 조건도 나눠 봐야 했습니다. 단순히 전후 총량을 나누면 실행 누락과 사용 기회의 변화가 한 숫자에 섞입니다.

실제 표시 기록과 노출 로그를 맞춰 보니 요청 수의 증감만으로는 설명하지 못하는 부분이 있었습니다. 실제 표시된 광고의 노출이 어디에 기록되는지, 공급사 내부의 클릭 감지가 언제부터 시작되는지도 확인할 필요가 있었습니다.

우리 노출 callback을 미뤄도 공급사 클릭 추론은 움직였다

상용 적용 뒤 노출과 클릭 집계의 변화가 질문으로 돌아왔습니다. hidden SDK가 생성된 시점부터 공급사 내부의 화면 이탈·복귀 기반 클릭 추론이 활성화될 수 있었습니다. 우리 쪽 impression을 표시까지 보류해도 공급사 내부 집계까지 보류된다고 볼 수는 없었습니다.

저는 코드와 관측을 연결해 이 차이를 설명하고, 실제 노출 신호 이후 클릭 감지를 활성화하는 계약을 공급사에 요청하자고 제안했습니다. 이는 공급사 내부 코드를 직접 확인한 결과가 아니라 당시 동작에 대한 분석이었습니다. 공급사 확인과 사업 판단은 해당 담당자들과 함께 진행했습니다.

클릭 집계가 늘었다고 매출도 같은 비율로 늘었다고 읽지 않았습니다. 공급사에서 전달한 설명에서도 클릭과 매출은 집계 출처가 달랐습니다. 프리로딩의 성공 여부를 하나의 숫자로 판정하기 어려운 이유였습니다.

DOM 정리 뒤에도 SDK 세션은 남을 수 있었다

이후 동료가 SDK의 close 호출과 같은 광고 세션 재사용을 보완했습니다. 화면 DOM을 없애는 것과 SDK의 진행 상태를 종료하는 것은 다르기 때문입니다. 후속 집계도 실제 표시된 세션의 광고를 기준으로 유지했습니다.

제 역할은 그 수정 시점과 운영 관찰을 대조해, 같은 페이지에서 연속 광고가 같은 SDK를 사용할 때의 문제 경로를 재구성하는 것이었습니다. 동료가 구현한 세션 종료를 제 최초 프리로딩 구현에 합쳐 설명하지 않습니다. 당시 공급사 간 집계 차이와 세션 문제도 한 원인으로 합칠 수 없었습니다.

이 사건을 확인할 때의 조건은 다음처럼 나뉩니다. 표는 상태와 확인 방법을 정리한 것이며 실기기 전체 통과를 뜻하지 않습니다.

빠른 표시와 운영 판단을 함께 전달했다

프리로딩은 공동 제품에 통합됐고 상용 적용 보고로 이어졌습니다. 사업 담당자는 대기 단축과 건너뛰기 감소를 보고했습니다. 다만 동등한 기기·네트워크·광고 비중·측정 이벤트의 전후 실측을 확보한 결과는 아니어서 여기서는 정성적인 효과 보고로 남깁니다.

집계 차이로 롤백 요청이 나왔습니다. 팀은 추가 영향을 확인한 뒤 롤백하지 않고 매출을 모니터링하기로 했습니다.

SDK 생성을 앞당겨 버튼 뒤의 기다림을 줄이는 과정에서, 화면에 숨겨 둔 시간에도 공급사의 관측이 시작될 수 있다는 점까지 살폈습니다. 우리 표시 callback을 늦추는 조치만으로는 충분하지 않았습니다. 동료가 보완한 세션 종료와 운영 관찰까지 이어서 보며, 다음 프리로딩에서는 준비 시점뿐 아니라 노출·클릭 감지의 시작과 세션 종료 시점도 함께 확인해야 한다고 생각하게 됐습니다.
