주제
#광고주 도구 #FE·BFF #제품 규칙

광고를 집행하기 전에 광고주 쪽의 행동이 제대로 전환으로 들어오는지 확인해야 합니다. 테스트 링크를 만들었다는 사실만으로는 부족합니다. 광고주가 실제 행동을 하고, 그 행동에 해당하는 기록을 서버에서 찾을 수 있어야 다음 집행을 판단할 수 있습니다.

2022년 12월, 제품 담당자가 제가 개발한 도구로 실제 고객의 전환을 확인했습니다. 운영 담당자는 그 결과를 보고 추가 테스트 없이 예정된 집행을 진행할 수 있다고 판단했습니다. 이 판단을 하려면 유형에 맞는 입력을 받고, 광고주가 실제 행동을 한 뒤, 서버에서 그 전환을 확인하는 과정이 하나의 작업으로 이어져야 했습니다. 이후 첫 테스트를 시작하지 못한다는 고객 피드백이 돌아와 1월에는 진행 조건을 다시 바꿨습니다.

연동 유형이 다르면 입력과 성공의 근거도 달랐다

문서로 설명하던 절차를 광고 운영 대시보드 안에서 수행할 수 있도록 만들었습니다. WEB·SDK·MMP는 같은 광고 연동처럼 보여도 필요한 값과 조회할 기록의 의미가 달랐습니다. MMP는 앱 전환을 전달하는 모바일 측정 파트너입니다.

유형입력·확인에서 다른 점
WEBURL과 추적 식별자
SDK광고 식별자
MMPtracker·플랫폼·이벤트 이름과 발생 시각

저는 Vue 단계 화면, ViewModel과 상태, API 소비, Node.js BFF의 조회·권한·요청 조건 전달을 맡았습니다. 실제 전환의 수집과 판정은 서버가 담당했습니다.

기획이 모두 확정될 때까지 기다리기보다 API를 먼저 논의해 실제 응답과 필요한 조건을 확인하자고 제안했습니다. 화면의 순서만 정하고 나중에 응답을 붙이면, 진행할 수 있는 조건과 성공을 확인하는 조건이 달라질 수 있기 때문이었습니다.

단계 완료와 연동 성공을 같은 값으로 만들지 않았다

도구의 흐름은 연동 대상 조회, 유형별 입력, 테스트 링크 생성, 광고주의 행동, 전환 기록 재조회로 나뉘었습니다. 입력 완료와 요청 중 상태, 화면 단계, 서버의 전환 판정을 따로 읽었습니다.

테스트 링크에는 QR과 복사, 유형별 안내를 연결했습니다. 링크 생성은 사용자가 테스트를 시작할 재료가 준비됐다는 뜻이지 실제 전환 성공은 아니었습니다. 결과 조회를 끝냈더라도 전환이 없으면 아직 성공으로 보여줄 수 없었습니다.

링크 생성과 전환 성공을 안내 문구로만 구분해서는 화면이 잘못된 성공 상태를 보여줄 수 있었습니다. 화면의 상태와 서버 응답도 같은 기준으로 읽어야 했습니다. ViewModel에는 유형별 필드와 값 변환을 모으고, store가 서버 조회에 전달할 입력도 함께 확인했습니다.

입력한 값이 서버 판정까지 도착하는지 봤다

BFF에는 기존 인증과 프록시를 재사용해 조회 경로를 연결했습니다. 전환 조회에서는 화면 입력의 query가 상위 요청까지 전달돼야 했습니다. 화면이 값을 받고 API를 호출했다는 사실만으로 충분하지 않았고, 빠진 query 전달을 수정했습니다. 기존 관리 경로의 구·신 권한 이름 호환도 보완했습니다.

QA 뒤에는 광고 식별자를 SDK에서만 입력하게 하고, MMP가 아니면 이벤트 이름을 비웠습니다. 해당 유형에서 보이지 않는 값이 이전 입력으로 남아 서버 조회에 영향을 주면 안 됐습니다.

모델의 표시 조건·기본값·변환과 store의 요청 인자도 테스트에 남겼습니다. 어떤 필드가 화면에 보이는지와 그 값이 특정 전환을 찾는 요청에 실제로 쓰이는지를 함께 검증했습니다.

실제 사용 뒤 첫 테스트의 모순이 드러났다

12월에는 도구가 실제 고객의 전환 확인과 예정 집행 판단에 사용됐습니다. 그러나 출시 뒤 다른 피드백에서는 올바른 연동 대상도 과거 포스트백이 없으면 첫 단계에서 막혔습니다. 아직 첫 이벤트를 만들려고 들어왔는데, 이전 이벤트가 있어야 시작할 수 있었던 셈입니다.

고객은 이 안내를 식별자 오입력으로 받아들였습니다. 제품 담당자가 피드백을 전달했고 팀은 기록이 없어도 다음 테스트로 진행하도록 규칙을 바꿨습니다. 저는 그 조건을 두 화면에 반영했습니다.

이벤트 소스 조회에서 빈 목록을 이유로 반환하던 분기를 없앴습니다. 동시에 다음 화면의 로그 조회 영역도 목록이 없다는 이유로 숨기지 않도록 바꿨습니다. 첫 화면만 통과시켜도 다음 화면의 재조회 버튼이 사라져 있다면 실제 테스트는 끝나지 않기 때문입니다.

과거 이벤트 없음
  → 첫 테스트 링크 생성은 허용
  → 광고주가 실제 행동
  → 서버의 해당 전환을 재조회
  → 조회된 판정으로 성공 여부 표시

응답 형태와 연동 유형 확인은 유지했습니다. 시작 조건을 완화했다고 최종 성공의 기준까지 바꾼 것은 아니었습니다.

도구가 끝내야 하는 일

초기 도구로 광고주가 실제 테스트를 하고 서버 기록을 확인할 수 있게 됐고, 그 결과가 집행 판단에 사용됐습니다. 1월에는 과거 기록이 없는 대상도 첫 테스트를 시작하고 결과를 재조회할 수 있도록 바꿨습니다. 12월의 고객 사용과 이후 진행 조건 수정은 각각 이 과정의 다른 부분을 확인해 주었습니다.

이전 기록이 없는 고객도 첫 이벤트를 만들 수 있어야 하지만, 테스트의 성공을 표시하려면 이번 전환을 확인해야 했습니다. 이 경험 이후에는 온보딩 도구의 단계뿐 아니라 사용자가 처음 들어왔을 때 무엇을 알고 있는지, 마지막에는 무엇을 확인해야 작업을 끝낼 수 있는지도 함께 봐야 한다고 생각합니다.
