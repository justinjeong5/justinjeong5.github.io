비동기 요청의 경쟁 조건과 상태 소유권

아까 광고가 없었다는 결과로 지금의 보너스 제안까지 결정해도 될까? 새로 조회한 결과가 이전 작업에 밀리지 않도록 다룬 이야기.

#최신성 #취소 #테스트 경계

보너스 광고를 제안할 때는 먼저 지금 보여줄 후보가 있는지 조회합니다. 여기서 '준비'는 후보를 읽고 이번 제안이 가능한지 판단하는 과정입니다. 광고가 없으면 제안을 이어갈 재료도 없으므로, 어느 시점의 결과를 사용할지가 중요했습니다.

그런데 미리 읽었을 때 광고가 없었다는 결과가, 나중에 다시 판단할 때도 광고가 없다는 뜻은 아닙니다. 기본 보상 화면에서 나오는 시점에 추가 제안이 광고를 요구하고 이전 준비가 empty라면, 새 할당을 조회해야 하는 흐름이 있었습니다. 이전의 빈 결과를 그대로 쓰면 그사이에 생긴 후보를 읽지 못할 수 있었습니다.

새 요청을 보내는 것만으로 끝나지도 않았습니다. 이전 요청이 아직 진행 중인데 새 조회를 시작하면, 둘의 결과가 도착하는 순서는 시작한 순서와 다를 수 있습니다. 먼저 시작한 작업이 나중에 끝나면서 새 준비의 상태를 바꾸거나 정리해버리면, 새로 읽은 결과가 있어도 그 상태를 유지하지 못합니다.

저는 다시 조회할 시점과 그 결과를 현재 상태에 반영할 조건을 함께 정했습니다. 새 요청을 보내더라도 이전 요청의 응답이나 정리 작업이 나중에 새 준비를 바꿀 수 있었기 때문입니다.

모든 조회의 캐시 정책을 바꾸지는 않았다

보너스 판정에 필요한 요청을 일반 광고 조회와 분리했습니다. 공용 fetcher와 일반 Query 정책은 유지하고, 보너스 세션이 요구하는 최신성 조건을 그 범위에 넣었습니다.

이번 요구는 보너스 회차의 갱신 시점에 새 할당을 읽는 것이었습니다. 일반 조회까지 같은 갱신 정책으로 바꾸기보다, 그 시점을 아는 보너스 세션에서 요청을 직접 다루도록 했습니다. 공용 fetcher는 네트워크 호출을 맡고, 어떤 결과를 재사용할지는 이 준비 흐름이 정했습니다.

같은 준비를 중복 호출하면 진행 중인 Promise를 함께 사용하도록 했습니다. 다만 강제 재조회가 필요한 경우에는 같은 결과를 기다리지 않고 새 세대로 넘어갔습니다. 중복 호출을 합치는 경우와 새 할당을 읽어야 하는 경우를 나눠 처리했습니다.

취소와 결과 적용을 따로 보호하기

요청 키에는 보너스 회차와 광고를 요청하는 환경을 묶었습니다. 회차가 바뀌면 이전 준비를 그대로 이어갈 수 없고, 같은 회차라도 강제 재조회라면 새 시도여야 했습니다. generation은 그 시도를 구분했습니다. 키가 바뀌거나 강제로 다시 조회하면 세대를 올리고 이전 controller에 취소를 전달했습니다.

취소 신호만으로 상태를 보호할 수는 없었습니다. 이미 도착한 결과나 이어서 실행되는 Promise 처리도 있을 수 있기 때문입니다. then·catch에서 현재 요청 키와 세대가 자신과 같은지 확인하고, 오래된 결과는 cancelled로 돌려줬습니다.

후속 후보 생성과 최종 상태 반영에도 준비 키와 세대를 다시 확인했습니다. 할당 요청이 끝나는 시점과 그 결과로 후보를 만들고 화면 상태에 쓰는 시점 사이에도 작업의 소유권을 유지해야 했습니다.

취소 신호를 전달한 뒤에도 then·catch가 이어질 수 있어 키·세대를 다시 확인했습니다. 이전 요청에 중단을 요청하는 처리와 그 결과를 상태에 써도 되는지 판단하는 처리를 함께 둔 것입니다. 요청이 시작될 때만 확인해서는 이후 상태 반영을 보호할 수 없었습니다.

오래된 finally도 새 요청을 건드릴 수 있다

이전 요청이 끝나며 controller ref를 비우는 cleanup도 살폈습니다. 그사이에 새 요청이 ref를 차지했으면 이전 finally가 새 controller를 지우면 안 됩니다.

그래서 정리할 때는 현재 활성 객체가 자기 자신과 같은 경우에만 ref를 비웠습니다. 결과의 키·세대와 정리 객체의 동일성은 서로 다른 위치에서 같은 목적을 지켰습니다. 오래된 작업이 지금 작업의 상태를 바꾸지 않도록 하는 것입니다.

이전 요청은 cancelled, 새 후보는 ready로 남도록

핵심은 응답 처리뿐 아니라 finally에도 같은 소유권 검사가 필요하다는 점이었습니다. 아래는 설명을 위한 재구성이며 실제 회사 코드가 아닙니다.

const mine = { key, generation: ++generation, controller };
active = mine;
try {
  const response = await fetchCandidates(controller.signal);
  if (active !== mine) return "cancelled";
  const candidate = await prepareCandidate(response);
  if (active !== mine) return "cancelled";
  commitReady(candidate);
} finally {
  if (active === mine) active = null;
}

후보를 준비하는 추가 비동기 단계가 있으므로 응답 직후 한 번만 비교해서는 부족합니다. 그리고 오래된 작업의 종료는 새 작업의 취소 권한을 지우면 안 됩니다.

회귀 시나리오는 첫 요청이 진행 중일 때 강제 재조회로 두 번째 요청을 만드는 순서로 구성했습니다. mock HTTP 클라이언트는 첫 요청의 abort 신호를 받으면 AbortError로 reject합니다. 두 번째 요청에는 광고 후보가 있는 응답을 돌려주고, 두 Promise가 끝난 뒤 첫 준비가 cancelled, 새 결과와 hook 상태가 ready인지 보도록 했습니다.

이 테스트가 확인한 순서는 진행 중인 첫 요청의 취소와 새 준비의 완료였습니다. 이전 empty 응답을 새 응답 뒤에 도착시키는 순서까지 구성한 것은 아닙니다.

테스트 입력·순서기대 결과
첫 요청 진행 중 강제 갱신첫 요청에 abort, 새 세대 시작
첫 mock 요청이 abort로 reject첫 준비는 cancelled
두 번째 요청에 광고 후보 반환새 준비 결과와 hook 상태는 ready
첫 작업의 finally 실행새 활성 controller를 정리하지 않음

진행 중 Promise를 공유하는 것은 중복 호출을 합치는 정책이고, 취소 결과를 최종 성공처럼 재사용하는 것은 아닙니다. 관련 광고 세션에서도 사용자가 닫은 경우에는 다음 후보를 강제로 실행하지 않고 다시 시작할 수 있게 구분했습니다.

바뀐 흐름에서는 보너스의 새 판정이 필요한 시점에 이전 empty 결과를 그대로 쓰지 않고 새 할당을 조회합니다. 같은 준비의 중복 호출은 진행 중인 Promise를 공유하고, 강제 갱신은 새 세대로 넘어갑니다. 일반 조회의 정책을 바꾸는 대신 이 준비 흐름이 요청과 적용·정리의 책임을 함께 갖게 했습니다.

지금 다시 보면 응답만큼이나 오래된 finally를 살펴본 부분이 기억에 남습니다. 응답 적용 조건을 정한 뒤에도, 이전 finally가 새 controller ref를 비우면 새 요청의 취소 권한이 사라질 수 있었습니다. 결과에는 키·세대를 확인하고 정리에는 활성 객체의 동일성을 확인해, 먼저 시작한 작업이 새 준비를 건드리지 않도록 했습니다.
