AI 코딩 도구의 사용 한도를 믿고 확인할 수 있도록

Swift 메뉴바 앱에 새 사용량 한도를 연결했다. 갱신한 캐시는 살리되 계정 전환 뒤 이전 한도를 보여주지 않도록, 파일과 캐시의 관계를 다시 정하고 공개 리뷰의 반례를 테스트에 연결한 과정.

#오픈소스 #외부 연동 #캐시 #AI 협업

코딩 도구의 계정을 바꿨는데 메뉴바에는 이전 계정의 사용 한도가 남아 있다면, 사용자는 어느 숫자를 믿어야 할까요? 조회 자체는 성공했으니 오류 메시지도 없습니다. 숫자가 자연스럽게 갱신되고 있다는 점이 오히려 문제를 알아보기 어렵게 만듭니다.

PokeTokenBar는 AI 코딩 도구의 사용량을 보여주는 macOS 메뉴바 앱입니다. 저는 이 오픈소스에 Antigravity의 한도 조회 기능을 추가하고, 이후 토큰 파일의 형식과 만료·갱신을 보완했습니다. Swift 구현에는 AI의 도움을 받았고, 변경을 PR로 제안해 유지보수자와 리뷰를 주고받았습니다.

처음에는 새 도구의 한도를 읽어 화면에 연결하는 일이었습니다. 그런데 토큰을 갱신한 캐시를 유지하려다 보니 다른 질문이 생겼습니다. 아직 유효한 캐시라도, 지금 사용자가 선택한 계정의 정보일까요?

API 응답을 화면까지 연결하기

사용량과 사용 한도는 다른 정보였습니다. 로컬 기록에서 오늘 얼마나 썼는지 알 수 있어도, 계정에 남은 한도와 초기화 시각까지 계산할 수는 없었습니다.

새 provider에서는 API 응답의 모델군과 한도 구간, 남은 비율, 초기화 시각을 읽었습니다. 이를 앱이 쓰는 모델로 바꾸고 UsageStore의 갱신 흐름, 메뉴 표시와 팝오버에 연결했습니다. 일부 값만 읽는 함수가 아니라 사용자가 기존 도구의 한도와 함께 확인할 수 있는 기능을 만드는 작업이었습니다.

이 연동에서는 인증을 다시 얻는 과정도 사용자 경험의 일부였습니다. 주기적인 백그라운드 갱신이 암호 입력을 계속 요구하면, 메뉴바에 조용히 두려던 앱이 작업을 방해합니다. 기존의 자동 갱신과 수동 갱신 정책을 유지하면서, 파일에 있는 토큰으로 답할 수 있는 경로를 보완했습니다.

파일이 바뀌었는지 먼저 읽었다

외부 도구가 저장하는 토큰 파일은 형태가 한 가지가 아니었습니다. 토큰 객체 안에 값이 들어 있는 형태와 최상위에 있는 형태, 이전 형식을 구별해서 읽어야 했습니다. 계정을 바꾸면 같은 경로에 다른 토큰이 기록될 수도 있었습니다.

파일을 메모리 캐시보다 먼저 읽는 기존 순서는 유지했습니다. 이번 보완에서는 그 순서에서 실제 파일의 여러 형식을 읽도록 했습니다. 캐시가 아직 유효하다는 이유만으로 바로 반환하면, 디스크에서 일어난 계정 전환을 놓칠 수 있기 때문입니다.

여기서 반대 방향의 문제가 나타났습니다. 앱이 refresh token으로 새 access token을 받아 캐시에 보관해도, 외부 도구의 파일에는 만료된 옛 토큰이 남을 수 있습니다. 파일을 무조건 우선하면 이미 갱신한 토큰을 다시 옛 값으로 덮어쓰게 됩니다.

처음 보완한 조건은 만료된 파일보다 유효한 캐시를 유지하는 것이었습니다. 같은 계정이라면 필요한 동작이었지만, 만료 여부만 비교해서는 충분하지 않았습니다.

리뷰에서 계정 전환의 반례가 나왔다

유지보수자가 다음 순서의 문제를 재현했습니다.

A 계정으로 조회해 유효한 캐시를 만든다
  → 파일을 만료 임박한 B 계정의 토큰으로 바꾼다
  → 다시 조회한다
  → 유효한 A의 캐시가 반환된다

캐시를 오래 보관해서 생긴 문제만은 아니었습니다. 파일과 캐시가 서로 다른 계정인데도, 유효기간을 기준으로 하나를 골랐다는 것이 핵심이었습니다.

반례를 받아 갱신된 캐시를 유지하는 조건에 같은 출처인지 확인하는 판단을 추가했습니다. access token이 같거나, 비어 있지 않은 refresh token이 같을 때 같은 출처로 취급했습니다. 갱신 과정에서 access token은 달라질 수 있으므로 access token의 일치만 확인해서도 안 됐습니다.

의미를 줄여 쓰면 다음과 같습니다. 실제 코드의 토큰 값 대신 조건만 남겼습니다.

if cacheIsValid && fileTokenIsExpired && sameCredentialSource {
    return cachedToken
}
return try await resolveTokenFromFile()

이 조건은 토큰을 비교하는 구현상의 기준이지, 별도의 사용자 ID로 계정 전체를 검증하는 절차는 아닙니다. 다만 이전 계정의 캐시를 새 계정 파일보다 먼저 고르는 반례는 이 기준으로 구별할 수 있었습니다.

토큰 문자열보다 갱신의 순서를 테스트하기

파일 형식을 읽는 테스트만으로는 이 문제를 설명하기 어려웠습니다. 같은 파일 경로를 두 번 읽고, 그 사이에 계정과 유효기간이 바뀌어야 했습니다.

테스트에서는 A 계정으로 캐시를 만든 뒤 B 계정 파일로 교체해 이전 캐시가 반환되지 않는 조건을 남겼습니다. 토큰 갱신에는 URLSession을 주입하고 mock HTTP 응답으로 새 토큰을 받은 다음, 후속 조회에서도 갱신한 캐시를 유지하는 흐름을 확인하도록 했습니다.

두 검사는 서로 반대 방향을 지켰습니다. 계정이 바뀌었을 때는 이전 캐시를 버려야 하고, 같은 계정의 토큰을 갱신했을 때는 새 캐시를 살려야 했습니다. 한쪽만 고치면 다른 쪽을 다시 깨뜨릴 수 있었습니다.

리뷰 중에는 설명도 좁혔습니다. 자동 경로에서 인증창을 피하는 것과 모든 환경에서 사용자 개입이 사라지는 것은 같지 않았습니다. 수동 갱신의 인증 경로는 남아 있었고, 처음의 넓은 표현보다 어떤 경로에서 무엇을 보장하는지 설명하는 편이 정확했습니다.

공개 버전으로 전달하고 남은 기준

새 한도 기능은 #210, 파일 형식과 갱신·계정 전환 보완은 #274로 병합됐습니다. 각각 v2.5.2와 v2.5.4의 공개 버전에 포함됐습니다. 기존 앱에서 새 도구의 한도를 확인할 수 있게 했고, 같은 계정의 갱신과 다른 계정으로의 전환을 서로 다른 조건으로 다루게 됐습니다.

이번 기여에서 가장 기억에 남는 것은 유지보수자의 재현이 캐시의 조건을 바꾼 장면입니다. AI를 활용해 구현을 준비한 뒤에도, 다른 사람이 만든 입력 순서를 받아 조건과 테스트를 고치는 과정이 필요했습니다.

돌아보면 캐시를 재사용할 때는 아직 쓸 수 있는지와 함께, 지금 읽으려는 대상의 값인지도 확인해야 했습니다. 새 provider를 붙이는 작업이 그 두 가지를 나누어 생각하는 경험으로 남았습니다.
