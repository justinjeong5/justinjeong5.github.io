기술 노트

리워드를 확인하는 마지막 터치가 반응하지 않을 때

복권을 긁을 수 없다는 문의인데 오류 로그에는 원인이 보이지 않았다. 입력의 도달과 Canvas 준비를 나눠 관측하고, 크기·초기화·반복 입력의 책임을 보강해 CS 반응까지 확인한 과정.

담당
입력 문의 조사·touch/click 계측·Canvas 크기/초기화/레이아웃 보완·운영 후속
시기
2026.06–2026.07
주제
#Canvas #입력 계측 #수명주기

사용자는 광고 참여를 마친 뒤 복권 표면을 긁어 리워드 결과를 확인합니다. 그런데 이 화면에서 입력이 반응하지 않으면, 참여를 끝냈어도 결과를 볼 수 없습니다. 복권이 긁히지 않는다는 문의는 이 마지막 동작에서 들어왔습니다.

문의와 같은 조건을 바로 재현하기는 어려웠습니다. Canvas 오류를 찾아도 증상을 설명할 만한 예외가 보이지 않았습니다. 다만 예외가 없다는 것만으로 입력이 정상이라고 판단할 수는 없었습니다. 손가락의 동작이 Canvas까지 도달했는지, 준비 상태로 표시된 화면이 실제로도 맞는 영역에서 입력을 받는지 확인할 필요가 있었습니다.

6월에는 touch/click 가설을 세우고 입력을 확인할 관측과 보강을 넣었습니다. 이후 6~7월에는 Canvas의 크기·초기화·프레임과 반복 입력의 수명주기를 함께 보완했습니다. 이 글의 질문은 예외로 잡히지 않는 입력 문제를 어디에서 관찰하고, 어떤 상태를 보존할 것인가입니다.

문의의 감소와 수정 적용 시점을 먼저 나눴다

조사 중 문의가 줄어드는 관찰도 있었습니다. 그때 저는 아직 수정이 배포되지 않았다고 알렸습니다. 뒤에 넣은 보강으로 그 이전의 감소를 설명할 수는 없었습니다.

입력 관련 보강과 모니터링을 배포한 뒤에는 CS 담당자가 문의가 크게 줄었다고 답했습니다. 전날 오후의 적용 여부를 물었고, 저는 적용 시점을 확인했습니다. 재현이 어려운 문제여서 코드만 보고 끝내는 대신, 무엇을 언제 바꿨고 실제 문의에서는 어떤 변화가 보였는지 함께 대조했습니다.

이 반응은 6월 중순의 입력 보강 직후 확인한 것입니다. 그 뒤의 크기·레이아웃·진단 측정 변경을 모두 합쳐 하나의 감소율로 설명하지는 않습니다.

CSS 크기와 비트맵 크기는 다른 갱신이었다

복권 위아래에는 배너와 영상이 함께 배치됐습니다. 화면의 레이아웃이 변하면 Canvas가 차지하는 크기와 손가락 좌표를 읽을 영역도 맞춰야 했습니다.

그런데 Canvas의 width·height를 다시 설정하는 것은 일반 CSS 스타일을 다시 넣는 일과 다릅니다. 그리기 상태에 영향을 줄 수 있습니다. 같은 값이라도 계속 대입하면 진행 중인 긁기를 보존하기 어려워집니다.

실제 레이아웃을 읽어 비트맵 크기를 정수로 정규화하고, 크기가 달라졌을 때만 width·height를 갱신하도록 했습니다. 입력 영역은 그 레이아웃에 맞춰 연결했습니다.

아래는 공개 설명용 의사코드입니다.

function syncSize() {
  const rect = measureLayout();
  const next = integerBitmapSize(rect);

  if (!sameBitmapSize(canvas, next)) {
    canvas.width = next.width;
    canvas.height = next.height;
    initializeDrawingContext();
  }

  updateInputArea(rect);
}

최신 레이아웃을 읽더라도 비트맵 크기가 같다면 width·height를 다시 설정하지 않도록 했습니다. 같은 값의 대입으로 이미 진행 중인 긁기를 건드리지 않으면서, 실제 크기가 바뀐 경우에는 입력 영역까지 맞추려는 처리였습니다.

준비 실패를 READY로 넘기지 않았다

Canvas ref가 없거나 controller 초기화가 실패했으면 준비 상태로 가장하지 않고 오류 상태로 드러냈습니다. 화면에 Canvas가 있다는 사실과 입력을 받을 준비가 끝났다는 사실은 달랐습니다.

동시에 표시 초기화 오류가 기존 결과 확인 경로까지 끊지 않도록 scratch→stop 흐름의 클라이언트 완료 경로를 유지했습니다. 서버의 리워드 승인과 화면에서 긁는 입력의 종료는 같은 책임이 아니었습니다.

이는 ERROR를 무조건 성공으로 바꾸는 선택이 아닙니다. 초기화 실패는 오류로 남기되, 사용자가 이어 갈 기존 완료 동작은 따로 보존했습니다. 하나의 READY 플래그에 초기화·입력·리워드의 모든 성공을 넣지 않으려는 보완이었습니다.

레이아웃은 paint 전에, 진단은 반복 입력 밖에서

복권의 크기만 맞춰도 배너 높이가 바뀌면 화면 전체의 프레임이 달라졌습니다. 예약 높이를 실제 프레임 계산에 반영하고, 그 prop이 바뀌었을 때 paint 전에 레이아웃을 맞추도록 보완했습니다.

포인터 좌표가 맞는지와 전체 프레임이 화면 안에 들어오는지는 다른 문제였습니다. 손가락이 움직일 때마다 이 배치 문제를 다시 해결할 필요는 없었습니다.

진단에도 비슷한 구분이 필요했습니다. 문제를 조사하려고 DOM 크기와 hit-test 정보를 읽더라도 모든 포인터 이동에서 그 측정을 반복하면 빈번한 입력에 조사 비용이 붙습니다. 화면 진입과 상태 전이에 진단 측정을 두고, 반복 포인터 경로에서는 지오메트리 측정을 하지 않도록 나눴습니다.

진단에 필요한 값이 실제로 달라지는 시점을 기준으로 측정을 배치했습니다. 이렇게 해야 입력을 조사하기 위한 측정이 손가락을 움직일 때마다 반복되는 비용으로 붙지 않았습니다.

서로 다른 실패와 보존할 행동을 테스트로 나눴다

초기화·프레임·입력에는 서로 다른 기대 결과를 남겼습니다.

조건확인할 동작
Canvas 요소가 없거나 초기화가 실패준비 상태로 넘기지 않고 오류 반환
ERROR 뒤 scratch→stopScratch기존 클라이언트 완료 경로 유지
레이아웃 크기 변경정수 비트맵 크기 반영
예약 높이 prop 변경프레임 계산 반영
반복 포인터 액션진단 지오메트리 측정 미호출

같은 크기에서 비트맵을 다시 설정하지 않는 조건도 구현에 남겼습니다. 실제 문의를 좁힐 관측과 상태·입력 조건을 고정할 테스트는 각각 다른 질문에 답했습니다.

마지막 입력도 제품의 일부였다

입력 보강 뒤에는 CS의 감소 확인이 돌아왔고, 후속에서는 초기화 실패와 프레임 변화, 반복 입력의 측정 비용을 따로 다뤘습니다. 사용자의 마지막 동작을 살리려면 Canvas만 볼 수 없었습니다. 광고 뒤의 참여 상태, 입력 준비, 실제 화면 크기, 결과 확인까지 이어져 있었습니다.

조사를 시작할 때는 예외를 찾아봤지만, 오류 로그만으로는 손가락이 닿았는지와 준비된 영역이 맞는지 알 수 없었습니다. 입력이 도달하는 장면을 관측하고 크기 갱신이 진행 중인 긁기에 미치는 영향을 나눠 보니, 확인할 조건을 더 구체적으로 정할 수 있었습니다. CS 반응도 각 보강의 적용 시점과 맞춰 보며 후속으로 확인했습니다.
