광고 실행을 바꾸지 않고 실패 지점을 관측하기

광고가 끝나지 않았다는 기록만으로는 어디서 막혔는지 알 수 없었다. 확인할 정보를 더하면서도 원래 광고 호출을 흔들지 않게 한 과정.

광고가 끝나지 않았다는 문의를 받으면 먼저 어느 단계에서 멈췄는지 알아야 했습니다. 호출을 준비하다가 막힌 것인지, 광고를 불러오지 못한 것인지, 이미 보여줬지만 완료 신호가 늦는 것인지에 따라 살펴볼 코드가 달랐습니다. 문의 내용만으로는 그 위치를 정하기 어려웠습니다.

웹과 네이티브 광고 기능을 연결하는 브릿지에서는 호출의 완료나 오류를 받을 수 있었습니다. 하지만 마지막 결과만 읽으면 그 앞의 어느 작업에서 멈췄는지가 충분히 드러나지 않았습니다. 시작·완료·실패가 어떤 호출에 속하는지 연결할 정보가 필요했습니다.

그 정보를 받는 진단 코드를 붙일 때도 문제가 있었습니다. 이벤트를 읽는 코드가 오류를 내는 바람에 원래 광고 호출까지 실패한다면, 문제를 살피기 위해 추가한 기능이 새로운 문제를 만드는 셈입니다. 기존 호출자가 받는 완료·오류의 의미도 달라져서는 안 됐습니다.

저는 광고 호출의 실행 과정을 별도로 전달하되, 기존 호출자가 받던 결과는 유지하는 방식으로 구현했습니다. 진단 이벤트를 처리하는 코드가 실패해도 광고 호출이 그 오류 때문에 실패하지 않도록 처리했습니다.

관측을 원래 반환값에 끼워 넣지 않기

기존 호출자는 브릿지의 Promise<void>가 완료되거나 원래 오류로 reject되는 계약을 사용하고 있었습니다. 여기에 새로운 관측 결과를 반환값으로 넣으면 소비자의 해석도 바뀝니다. 오류를 문자열이나 새 객체로 바꿔 전달하는 것 역시 기존 호출자에게는 다른 오류가 될 수 있었습니다.

별도의 구독 구조를 두면 기존 호출자는 새 반환값이나 오류 형식에 맞춰 코드를 바꿀 필요가 없었습니다. 원래 Promise는 이전 방식으로 끝나고, 이벤트 구독자만 작업의 시작·완료·실패 이벤트를 받도록 했습니다. 진단이 필요한 쪽에서 구독하면 되므로 모든 호출자에게 같은 변경을 요구하지 않았습니다.

특히 실패에서는 기존 호출이 원래 오류 객체를 그대로 전달하도록 유지했습니다. 관측에 사용할 오류 정보의 정규화와 실제 API 오류의 전달을 같은 처리로 묶지 않은 것입니다.

이벤트에는 작업의 순서와 단계가 있어야 했다

load와 show 작업에 각각 operation ID를 부여하고 단계와 상태, 걸린 시간과 결과를 이벤트로 남겼습니다. 같은 광고 관련 이벤트라도 어느 작업의 시작과 종료인지 이어서 읽을 수 있어야 했습니다.

작업이 시작된 뒤 구독하면 시작 이벤트 없이 종료 이벤트만 받을 수 있습니다. 그 결과를 구독 이후에 시작한 작업처럼 읽지 않도록, 구독 시점 이전에 시작한 operation은 해당 구독자에게 전달하지 않는 조건을 뒀습니다.

이 이벤트에서는 스크립트를 읽는 단계의 실패인지, load·show 호출의 거절인지, 어떤 operation의 결과인지 나눠 읽을 수 있습니다.

구독자가 실패하면 누가 영향을 받을까

구독자 역시 코드를 실행합니다. 이벤트를 처리하다가 동기 예외를 던질 수 있고, 비동기 작업이 rejection을 만들 수도 있었습니다. 이 실패가 원래 브릿지 호출에 전파되면 관측 기능을 켠 것만으로 광고 흐름이 달라집니다.

이벤트를 전달할 때 구독자의 동기 예외를 잡고, 반환된 비동기 작업의 rejection도 별도로 처리했습니다. 한 구독자의 실패 때문에 다른 구독자의 통지나 원래 광고 호출이 중단되지 않게 하기 위해서였습니다. 이 처리가 모든 이벤트의 소비를 보장하는 것은 아닙니다. 진단 코드가 실패했을 때 원래 기능에 미치는 영향을 제한한 것입니다.

오류 이벤트는 필요한 필드만 정리해 전달했습니다. 일반 Error와 객체 형태, 값이 빠진 경우를 다루고 결과 역시 필요한 항목으로 제한했습니다. 이는 관측 이벤트에 담을 데이터 구조를 정한 것이며, 원래 오류 전달과는 별도였습니다.

테스트에서는 기록과 반환 계약을 같이 봤다

관측 정보가 나오는지만 검사하면 새 정보가 기존 기능을 깨뜨리는 경우를 놓칩니다. 그래서 구독자가 실패하는 입력과 원래 호출이 실패하는 입력을 나눠 봤습니다.

아래는 설명을 위한 재구성이며 실제 회사 코드가 아닙니다. 이벤트 전달의 실패 처리와 원래 오류 재전달이 다른 위치에 있습니다.

async function observedCall(run) {
  safelyNotify({ phase: "start" });
  try {
    await run();
    safelyNotify({ phase: "complete" });
  } catch (originalError) {
    safelyNotify({ phase: "error", detail: normalize(originalError) });
    throw originalError;
  }
}

safelyNotify는 동기 예외뿐 아니라 구독자가 반환한 비동기 작업의 rejection도 처리해야 합니다. 통지 함수가 바로 반환했다는 이유만으로 이후 구독자 실패까지 격리됐다고 판단할 수는 없습니다.

이 조건들은 관측 계층의 계약을 확인합니다. 실제 장애 진단 시간이 얼마나 줄었는지나 공급사 호출이 모든 기기에서 성공했는지는 다른 측정입니다.

관측을 추가해도 기존 호출은 같은 방식으로 끝난다

조사하는 쪽에는 스크립트·load·show 중 어느 operation에서 막혔는지 이어 읽을 정보가 생겼습니다. 기존 호출자는 새 반환값이나 오류 형식을 받을 필요가 없었습니다. Promise는 이전 계약으로 끝나고 원래 오류 객체도 그대로 전달했습니다. 구독자의 동기·비동기 실패가 다른 구독자나 광고 호출로 번지지 않는 조건도 함께 검사했습니다.

오류를 정규화할 때는 관측용 표현만 바꾸도록 주의했습니다. 원래 reject 오류까지 바꾸면 기존 호출자가 오류를 판단하는 방식도 달라질 수 있기 때문입니다. 별도 구독으로 조사에 필요한 정보를 제공하고, 기존 호출자는 같은 결과를 받도록 유지했습니다. 이후 수집량을 조절하는 목적별 샘플링도 이 전달 방식 위에서 이어졌습니다.
