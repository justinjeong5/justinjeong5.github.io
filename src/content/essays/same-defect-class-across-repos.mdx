이전 요청을 취소하고 새 요청을 시작했다. 새 결과도 정상적으로 도착했다. 그런데 이전 요청의 finally가 실행되며 지금 활성 controller를 담은 ref를 비워버린다면, 취소 처리가 있다는 사실만으로는 현재 작업을 보호했다고 말할 수 없다.

배포 화면에서도 비슷한 순서가 가능했다. 환경 A의 정보를 읽다가 B로 바꿨는데 A의 응답이 늦게 오면, 선택 상자는 B를 가리키고 배포 정보는 A를 보여준다. 기사 콘텐츠에서는 외부 페이지에서 돌아와 재조회하는 동안 다른 콘텐츠를 열며 복귀 listener가 교체됐다. 이전 감시가 남긴 잠금과 늦은 완료를 새 시도와 나눠야 했다.

서로 다른 제품과 저장소의 일이지만 현재 함께 읽히는 질문은 하나다. **처음 시작할 자격이 있던 작업이 지금도 상태를 바꿀 자격이 있는가?** 요청이 성공했는지보다 결과와 정리 작업의 소유권이 중요했던 장면들이다.

## 취소 신호는 이전 작업의 모든 후속 실행을 지우지 않는다

[보너스 광고의 최신 조회](/cases/latest-request-boundaries/)에서는 이전 준비가 empty인 상황에서 새 판정이 필요하면 다시 할당을 읽어야 했다. 일반 광고 조회의 정책을 모두 바꾸는 대신 보너스 준비 흐름이 필요한 최신성 조건을 맡았다.

같은 준비의 중복 호출은 진행 중 Promise를 공유했다. 그러나 회차가 바뀌거나 강제 재조회가 필요하면 이전 결과를 계속 공유할 수 없었다. 준비 키에는 회차와 요청 환경을 묶고 새 시도는 generation으로 구분했다. 새 세대를 시작할 때 이전 controller에 취소 신호를 전달했다.

그 신호만으로 then·catch와 후보 준비의 후속 실행을 없앨 수는 없었다. 응답을 받아 후보를 만드는 동안에도 새로운 요청이 시작될 수 있다. 요청 결과를 읽는 지점과 후보를 최종 반영하는 지점에서 키와 세대를 확인했다. 오래된 준비는 cancelled로 남기고 현재 준비만 상태를 반영하도록 했다.

취소는 그만하라는 요청이고, 적용 조건은 결과를 써도 되는지의 판단이었다. 네트워크의 수명을 줄이는 조건과 상태의 권한을 제한하는 조건을 같은 것으로 볼 수 없었다.

## finally에도 자기 작업인지 확인해야 했다

결과를 쓰는 코드만 보호하면 정리 단계가 남는다. 이전 요청이 끝날 때 활성 ref를 무조건 null로 만들면 그사이 들어온 새 controller가 지워진다. 그래서 현재 활성 객체가 자신의 객체일 때만 정리했다.

설명용 재구성이며 회사 코드를 옮긴 것은 아니다.

```ts
const mine = { key, generation, controller };
active = mine;
try {
  const response = await request(controller.signal);
  if (active !== mine) return "cancelled";
  const candidate = await prepare(response);
  if (active !== mine) return "cancelled";
  apply(candidate);
} finally {
  if (active === mine) active = null;
}
```

await 뒤의 검사와 finally의 검사는 다른 일을 한다. 앞의 조건은 오래된 결과가 화면을 덮지 못하게 하고, 뒤의 조건은 오래된 정리가 현재 작업의 제어 수단을 지우지 못하게 한다. 후속 비동기 단계가 있으므로 첫 응답 직후 한 번 검사하는 것으로 끝낼 수도 없었다.

당시 회귀 시나리오는 첫 mock 요청이 abort로 reject되고 두 번째 요청의 후보가 ready로 남는 순서였다. 이전 empty 응답을 새 응답 뒤로 지연시키는 테스트와는 다른 조건이다. 구현의 보호 경계와 실제 테스트한 순서를 구별해야 무엇이 더 필요한지 보인다.

## 선택기의 키는 화면 라벨이 아니라 원래 환경이었다

[배포 환경 선택](/cases/deployment-config-contracts/)에는 프로젝트와 환경을 나눠 보여주는 UI가 있었다. 표시 그룹을 고르는 행동과 배포 대상의 식별자는 같지 않았다. 실제 요청에는 원래 환경 이름을 유지해야 했다.

환경을 바꿀 때 현재·최근 배포 정보와 pending request identity를 함께 비웠다. 응답을 적용할 때 요청 식별자뿐 아니라 요청했던 원본 환경이 지금 선택한 환경과 같은지 확인했다. 같은 환경에서도 새 refresh가 시작될 수 있으므로 환경 이름만 비교하면 충분하지 않았다. 반대로 request identity만 읽으면 그 요청이 어떤 대상을 설명하는지 놓치기 쉽다.

롤백 화면에서는 이력과 선택한 deployment도 함께 초기화했다. B 환경으로 바꾼 뒤 A에서 고른 배포 대상을 계속 들고 있으면 조회 결과를 막아도 실행 입력이 남기 때문이다. 데이터가 어느 선택에 속하는지와 실행할 대상이 어느 선택에 속하는지를 같이 정리했다.

이 문제는 배포 backend 전체의 동시성 정책을 새로 만드는 일이 아니었다. 프론트엔드 선택과 응답, 실행 입력이 같은 원본 대상을 가리키도록 한 범위다. 환경 A에서 시작한 요청이 B에서 상태를 쓸 수 없도록 한 점이 광고 준비의 키·세대와 닮았다.

## 복귀 listener를 바꾸면 이전 잠금도 끝내야 했다

[기사 콘텐츠 통합](/cases/article-content-integration/)에서 사용자는 외부 페이지를 열고 돌아왔다. 복귀 때 해당 콘텐츠 query를 다시 읽는 동안 다른 콘텐츠를 열면 감시 listener가 교체될 수 있었다. 클릭 중복을 막는 잠금이 이전 시도에 남으면 새로운 행동까지 막힐 수 있었다.

복귀 감시 교체에서는 취소 callback으로 이전 잠금을 정리하고, finished와 generation을 확인해 늦은 완료가 새 시도를 수정하지 않게 했다. 시작할 때 잠금을 거는 코드만 보면 취소와 교체의 문제가 드러나지 않는다. 정상 복귀 외에 다른 콘텐츠를 여는 순서까지 있어야 잠금의 수명을 설명할 수 있었다.

조회 대상도 hook을 만들 때 query key로 고정했다. 기사 복귀는 기사 query를, 기존 추천 복귀는 추천 query를 갱신해야 했다. 늦은 작업을 막는 것과 올바른 소비자를 갱신하는 것은 다른 검사지만, 둘 다 “누구의 작업인가”를 코드에 남기는 방식이었다.

표시 key와 계측 key도 항상 같지는 않았다. 같은 기사 카드라도 광고 할당이 바뀌면 새 노출 회차였고, 그 식별자가 바뀔 때 기존 노출 타이머를 취소하고 다시 측정했다. 같은 화면을 유지한다는 사실이 이전 타이머를 계속 써도 된다는 뜻은 아니었다.

## 세 경험에서 소유권을 확인하는 위치가 달랐다

광고 준비는 회차·환경 키와 세대가 결과 적용을 제한하고, 활성 객체 동일성이 cleanup을 제한했다. 배포 선택은 요청 identity와 원본 환경이 조회 결과를 제한하며, 선택한 deployment를 비워 실행 입력도 맞췄다. 기사 복귀는 watcher 취소와 종료·세대 조건이 이전 잠금과 늦은 완료를 다뤘다.

하나의 공용 훅으로 모두 묶었다는 이야기는 아니다. 각 흐름이 설명해야 할 대상과 종료 조건이 달랐다. 같은 결함 종류를 안다는 것은 코드를 복사할 근거보다, 그 제품에서 읽어야 할 실행 순서를 찾는 출발점에 가깝다.

현재 다시 비동기 흐름을 검토한다면 성공 응답만 따라가지 않고 마지막 정리까지 읽고 싶다. A 시작, B 시작, A 종료, B 종료의 순서를 놓고 누가 무엇을 바꿀 수 있는지 확인하는 것이다. 새 후보가 ready로 남고, 선택한 환경의 정보만 반영되며, 다른 콘텐츠를 열어도 이전 잠금이 남지 않는 구체적인 변화가 이 질문의 이유다.
