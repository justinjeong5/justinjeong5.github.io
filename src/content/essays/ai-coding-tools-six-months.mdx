새 기능의 화면이 준비되어도 사용자가 문의를 남길 경로가 없으면 제품의 작업은 끝나지 않는다. 화면에서 보여줄 분류를 서버가 제공해야 하고, 실제 문의를 받을 때도 해당 앱에서 지원하는 요청인지 검사해야 한다. 새 분류를 저장할 DB까지 준비되어야 그 경로가 이어진다.

2026년 여름, 프론트엔드 개발자인 내가 이 서버 변경을 맡았다. Python 서버 경험이 많지 않아 AI에 기존 코드의 맥락 조사와 구현 계획을 요청했다. 언어에 익숙한 사람이 작성했을 법한 코드를 얻는 것보다 중요한 질문이 있었다. 내가 어떤 입력을 허용할지 설명할 수 있는가, 이 변경을 담당자가 검토할 수 있는가, 운영 반영의 다음 순서를 정할 수 있는가였다.

AI와 함께 프론트엔드 밖으로 업무를 넓힌 경험은 서버 수정만이 아니었다. 제품 담당자의 데이터 질문을 분석 자료로 정리하고, 개발 계획을 다른 직군이 판단할 수 있는 형태로 나눈 경험도 있다. 서로 다른 일들을 연결하는 기준은 모델이나 언어의 이름보다 팀에 남아 있는 병목을 어디까지 맡았는지였다.

## 화면의 요구를 서버에서 허용할 요청으로 바꾸기

문의 분류를 화면에 추가하는 요구에는 두 경로가 숨어 있었다. 분류 조회는 사용자가 선택할 항목을 내려주는 일이고, 문의 생성은 선택한 값과 앱의 조합을 받아 실제 처리를 시작하는 일이다. 조회에서 특정 항목을 숨겨도 생성 API에 같은 요청이 들어올 수 있다. 화면의 제한만으로 서버의 지원 범위를 표현할 수는 없었다.

AI와 앱별 분류 조회, 기존 문의 생성 경로를 조사하고 변경했다. 지원 앱과 미지원 앱을 구분하고 잘못된 입력을 거절하도록 했다. 이후에는 적용 대상을 좁히는 수정도 이어졌다. 처음 계획의 대상 목록을 고정한 채 구현을 끝내는 문제가 아니었다. 제품의 지원 범위가 바뀌면 조회와 생성 양쪽에서 그 의미가 유지되어야 했다.

지금 돌아보면 익숙하지 않은 서버 코드에서 우선 설명해야 하는 것은 클래스의 구조보다 허용되는 요청이었다. 코드 탐색을 AI가 도와줄 수 있어도 사용자에게 약속할 범위는 제품의 요구와 맞춰야 한다. 이 질문이 있어야 생성된 수정안을 읽을 때 무엇을 확인할지도 정해졌다.

## 실패 응답 앞에 부수효과가 있는지 보기

문의 생성은 응답 하나를 반환하는 함수로 끝나지 않았다. DB 저장과 외부 문의 처리, 자동 처리 경로가 연결되어 있었다. 미지원 요청이 마지막에 오류를 반환하더라도 그 전에 저장이나 외부 처리가 실행되었다면 지원 검증을 제대로 넣었다고 보기 어려웠다.

잘못된 입력에서 예외가 발생하는 조건과 함께, DB에 문의가 남지 않고 외부 생성과 자동 처리가 시작되지 않는 조건을 테스트에 남겼다. 지원하는 요청에서는 저장된 앱과 분류, 외부 생성 경로가 이어지는지도 다루었다. 중요한 것은 성공과 실패라는 이름보다 입력 검증이 어디에서 끝나고 실제 변경이 어디에서 시작되는지였다.

프론트엔드에서도 비슷한 질문을 만난다. 버튼을 잠갔다고 서버에서 중복 실행이 막히는 것은 아니며, 오류 안내를 띄웠다고 실패 전에 생긴 변경이 사라지는 것도 아니다. 서버 작업에서는 그 경계를 더 직접적으로 읽어야 했다. AI가 만든 테스트의 존재 자체보다, 잘못된 요청이 남겨서는 안 되는 결과를 테스트가 표현하는지가 검토의 기준이 됐다.

## 코드를 만든 뒤에도 반영 순서가 남았다

새 분류를 저장할 DB 변경도 필요했다. 화면에 제공할 순서와 기존 저장 값의 순서를 구분해 검토용 DDL을 준비했고, DBA의 운영·검증 환경 반영 완료 뒤 서버 변경을 병합했다. 낯선 서버 기능을 맡는 일에는 코드뿐 아니라 다음 반영이 기다릴 조건을 정하는 일도 포함됐다. [구현과 실제 반영의 책임을 나눈 과정](/essays/delegation-autonomy-calibration/)에서 이 순서를 따로 돌아봤다.

## 코드 밖의 병목도 다음 작업의 입력이었다

같은 해에는 제품 담당자의 질문을 이벤트 분석과 쿼리 설명 자료로 정리하고, PRD와 서버 계획 위에 FE 작업을 나누어 전달하기도 했다. 새 코드를 만드는 일은 아니었지만 동료가 다음 판단을 할 수 있도록 자료를 만드는 일까지 맡은 경험이었다. 분석 자료는 자동 갱신 제품이 아니었다. [다음 작업에 넘길 맥락](/essays/ai-workflow-chains/)에서는 자료와 계획을 인계한 장면을 정리했다.

## 업무 범위가 넓어진 뒤에 남는 전문성

서버 문의 기능은 지원 범위와 부수효과의 순서를 담은 코드·테스트, DBA 반영 완료, 그 뒤의 서버 병합으로 이어졌다. 분석 자료는 제품 담당자가 읽고 활용할 수 있는 설명과 쿼리로 전달됐다. 두 일의 완료 모습은 달랐지만 초안 뒤에 팀이 이어받을 작업이 무엇인지 설명해야 한다는 점은 같았다.

6년차 프론트엔드 개발자로서 이 경험에서 넓어진 것은 언어 목록보다 제품의 경계를 읽는 범위였다. 화면이 요구하는 서버 계약을 따라가고, 운영 담당자가 확인할 자료를 준비하고, 다른 직군이 사용할 설명을 만드는 일도 제품 전달에 포함됐다. AI는 조사와 구현의 진입 부담을 낮췄다. 나는 그 결과를 팀의 책임과 실제 반영 순서에 연결하는 일을 맡았다.

서버 변경의 구체적인 경계는 [문의 분류를 전달한 과정](/cases/ai-cross-functional-delivery/)에, 분석 데이터의 의미를 다루는 다른 경험은 [리텐션 리포트의 빈칸과 0](/cases/retention-report-boundaries/)에 이어서 정리했다.
