배포 환경을 프로젝트와 환경으로 나눠 고르는 화면이 정상적으로 보였다. 새로 만든 저장소 설정이 읽혔으니 성공이라고 말할 수 있을까? 당시에는 같은 화면을 만드는 제품 전용 코드가 아직 남아 있었다. 새 설정이 잘못돼도 기존 분기가 화면을 만들어줄 수 있었다.

다른 작업에서는 반대 장면을 만났다. 광고를 미리 준비하는 기능을 적용했는데 QA 대상 일부에서 빨라지지 않았다는 반응이 있었다. 코드를 더 고치기 전에 확인한 것은 기능이 켜졌는지였다. 해당 대상의 flag가 빠져 있었고, 적용한 뒤 동료가 빠른 표시를 확인했다.

정상 화면과 느린 화면 모두 실행 경로를 모르면 변경의 결과로 읽을 수 없다. 두 작업을 지나 지금 내가 다시 묻게 되는 질문은 **“이 관찰은 어떤 코드가 실행됐을 때만 나올 수 있는가?”**다. 테스트 수를 늘리는 것에 앞서 성공을 구별할 입력과 관찰을 정하는 문제다.

## 설정을 바꿨는데 구 분기가 성공을 대신했다

[배포 환경 선택기](/cases/deployment-config-contracts/)는 제품 전용 분류를 저장소 선언으로 옮기는 변경이었다. 새 선언이 있어도 도구에 구 분기가 남아 있으면 같은 화면이 나올 수 있었다. 그래서 소비자 선언이 통합되고 전용 분기가 제거된 조합을 검증 대상으로 정했다.

그 버전을 검증 환경에 배포해 환경 선택과 실제 배포를 확인했다. 표시가 나뉘는 것뿐 아니라 제출 payload에 원래 환경 이름이 남는지도 확인할 계약이었다. 구 코드가 대신 성공을 만들 수 없는 입력과 새 코드가 유지해야 할 결과를 함께 고른 셈이다.

## 선로딩 비교에는 활성 조건이 포함돼야 했다

[광고 선로딩](/cases/ad-preload-lifecycle/)은 클릭 전에 광고 준비를 시작하도록 실행 순서를 바꾸는 작업이었다. 기존 단일 요청 경로도 남아 있어, 같은 화면을 보더라도 어느 경로가 켜졌는지 먼저 확인해야 했다.

적용과 미적용 영상을 공유한 뒤 일부 QA에서 빠르지 않다는 반응이 나왔다. 화면과 버튼이 같아도 분리 요청 경로가 활성화되지 않으면 기존 흐름을 비교하게 된다. flag 누락을 확인하고 대상에 적용한 뒤 빠른 표시 반응이 이어졌다. 이를 일정 비율의 성능 개선으로 바꿔 쓸 수는 없지만, 잘못된 비교 입력을 바로잡은 과정은 분명하다.

현재 이 사건을 회고하면 검증 조건에 사용자나 기기만 적는 것으로 부족하다. 그 대상에서 어떤 기능 경로가 켜졌는지까지 넣어야 관찰이 구현의 결과가 된다. 같은 commit도 런타임 설정에 따라 다른 프로그램처럼 동작할 수 있기 때문이다.

## 빠른 표시가 답하지 못한 질문도 있었다

기능을 켠 뒤 광고가 빠르게 표시됐다는 반응은 표시 지연에 관한 결과였다. 상용 적용 뒤에는 집계 변화가 다른 질문으로 돌아왔다. 준비를 앞당긴 일이 화면 밖의 동작에 무엇을 바꾸는지도 따로 읽어야 했다. 공급사 내부를 직접 확인한 결과로 확대할 수는 없었으며, 관련 분석과 동료의 후속 보완은 [선로딩의 운영 경계](/cases/ad-preload-lifecycle/)에서 다뤘다. 하나의 긍정적인 관찰이 어떤 질문에 답했고 어떤 질문을 남겼는지 구분해야 했다.

## 입력 테스트는 화면보다 실행 횟수를 봐야 했다

[스크래치 Canvas](/cases/canvas-input-lifecycle/)에서는 다른 종류의 관찰을 사용했다. 사용자 입력은 계속 발생하지만 진단용 DOM 크기 측정을 매번 수행할 필요는 없었다. 측정을 화면 진입과 상태 전이로 옮기고 반복 포인터 입력에서 분리했다.

긁는 화면이 정상이라는 사실은 이 변경을 구별하지 못한다. 이전 코드도 같은 그림을 보여줄 수 있다. 차이는 반복 입력이 불필요한 지오메트리 측정을 실행하는지였다. 당시 테스트에는 포인터 액션에서 그 측정을 호출하지 않는 조건이 남아 있다. 개선을 프레임 속도 수치로 주장하기보다 제거한 실행을 직접 관찰한 셈이다.

다음은 세 경험의 검증 대상을 정리한 설명용 조건이다.

```text
설정 전환 → 소비자 선언 + 구 분기 제거 + 원본 배포 대상
선로딩 → flag 활성 + 실제 분리 요청/준비 경로 + 표시 시점
반복 입력 → 입력은 진행 + 진단 지오메트리 측정은 미호출
```

Canvas의 같은 크기 재설정 guard는 구현에서 확인한 조건이고, 같은 크기에서 setter가 호출되지 않는 별도 테스트가 확인된 것은 아니다. 테스트가 있는 조건과 구현을 읽어 설명한 조건도 동일한 증거로 합칠 수 없었다.

## 완료 조건을 잘 고르면 실패도 해석할 수 있다

배포 선택기는 새 선언을 소비하고 기존 대상 계약을 유지하는 조합으로 확인했다. 선로딩 QA는 적용 조건을 맞춘 뒤에야 구현의 반응을 읽을 수 있었다. Canvas는 정상 렌더링만으로 보이지 않는 반복 실행을 테스트 조건으로 남겼다. 세 작업의 관찰 방법이 서로 다른 이유는 변경하려던 동작이 달랐기 때문이다.

지금 다시 검증 계획을 만든다면 먼저 반례를 적고 싶다. “내 변경이 없어도 이 테스트가 통과할 수 있는가?” 화면이 똑같아도 실행이 달라야 하는 변경이라면, 화면 밖의 관찰이 필요하다. 새 분기를 반드시 지나도록 입력을 만들고, 그 경로가 보존해야 할 기존 계약과 제거해야 할 실행을 각각 확인하는 것이다.

이 경험에서 남는 개발 판단은 검증을 많이 한다는 태도보다, 어떤 성공을 믿을 수 있는지 설명하는 일에 가깝다. 동료가 느리다고 말했을 때 구현을 바로 부정하지 않고 활성 조건을 확인하고, 화면이 잘 보였을 때도 새 코드의 성공을 서둘러 선언하지 않은 장면이 같은 질문으로 이어진다.
