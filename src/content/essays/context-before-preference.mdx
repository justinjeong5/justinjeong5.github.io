광고 소재를 켜고 끄는 토글은 화면을 열자마자 보였다. 그러나 그 소재에 자동화 규칙이 연결돼 있는지는 별도 요청의 응답을 기다려야 했다. 규칙이 있다면 수동 변경 전에 확인 모달을 보여줘야 했다. 빠르게 누른 사용자는 확인 없이 변경하고, 조금 기다린 사용자는 확인을 거치는 상황이 생길 수 있었다.

이 문제에서는 조회 중 버튼을 막았다. 몇 년 뒤 광고 완료 응답을 기다리는 화면에서는 일정 대기 후 빠져나올 버튼을 열었다. 역시 필요한 정보가 아직 오지 않은 상태였다. 앞에서는 기다리게 했고 뒤에서는 기다림을 끝내게 했다.

두 선택을 연결하는 질문은 “사용자에게 얼마나 많은 선택을 줄까”보다 구체적이다. **이 버튼이 실행되면 아직 모르는 사실을 무엇으로 취급하게 되는가?** 버튼의 모양이나 로딩 여부가 같아도, 그 행동이 확정하는 사실은 달랐다.

## 토글의 빠른 클릭은 확인 절차를 건너뛰었다

[자동화 규칙이 있는 소재의 상태 변경](/cases/automation-unknown-state/)에서 서버 응답 전 정보는 규칙 없음이 아니었다. 아직 모르는 상태였다. 그런데 그 상태를 falsy 값으로 읽으면 “규칙 없음 → 직접 변경”의 분기로 들어갈 수 있었다.

실행 순서가 중요했다. 목록을 열고 규칙 조회를 시작한다. 응답 전에 토글을 누른다. 아직 채워지지 않은 값으로 직접 변경한다. 뒤늦게 규칙이 있다는 응답을 받아도 이미 한 변경에 확인 모달을 소급해서 붙일 수 없다. 화면에 스피너가 있는지보다 확인을 건너뛰는 명령이 실행되는지가 문제였다.

나는 클릭이 조회보다 먼저 도착하는 순서를 설명하고 조회 중 표시와 조작 제한을 제안했다. 디자이너와는 정상 응답이 빠를 때 스피너가 주는 부담과 아이콘 정렬도 함께 논의했다. 응답을 기다리는 동안 조작할 수 없다는 비용을 없던 것처럼 취급할 수는 없었다. 다만 기다리지 않고 실행했을 때 없어지는 절차가 명확했다.

## 표시와 실행 함수가 같은 조건을 읽게 했다

조회 중에는 토글을 비활성화하고, 실행 함수에서도 조회 중이거나 다른 변경을 처리 중이면 돌아가도록 했다. 비활성 표시는 사용자가 지금 조작할 수 없음을 이해하는 장치이고, 함수의 조건은 실제 변경을 제한하는 장치였다.

조회 후 규칙이 없으면 직접 변경한다. 규칙이 있으면 모달을 열고, 취소하면 유지하며 확인했을 때만 변경한다. 정보를 읽는 loading과 상태를 바꾸는 processing도 나눴다. 두 상태를 모두 “바쁘다”로 표시할 수는 있어도, 어떤 절차가 끝나야 다음 명령을 실행할지는 달랐다.

리뷰에서는 사용처마다 확인 절차를 붙이다 빠뜨릴 수 있다는 문제가 나왔다. 일반 토글 전체에 자동화 지식을 넣는 대신, 규칙 조회와 확인을 아는 도메인 컴포넌트에 행동을 묶었다. 일반 토글은 On/Off 표현을 맡고 자동화 상태 변경은 그 컴포넌트를 선택하는 사용처가 맡았다. 강제 범위와 재사용 책임을 함께 정한 선택이었다.

## 광고 대기에서는 시간을 성공으로 바꿀 수 없었다

[광고 응답을 기다리는 복구 흐름](/cases/ad-response-recovery/)에는 다른 곤란함이 있었다. 사용자는 광고를 봤는데 상자 열기로 넘어가지 않았고, 다시 시도하다 포기했다는 문의가 있었다. 웹이 알 수 있는 것은 완료 응답을 아직 받지 못했다는 사실이었다. 시청 경험만으로 정상 완료를 확정하거나, 시간이 지났다는 이유로 보상 처리를 승인할 수는 없었다.

그렇다고 응답이 올 때까지 아무 선택 없이 기다리게 둘 필요도 없었다. 나는 일정 시간 뒤 기존 skip UI를 사용할 수 있게 하는 방식을 제안했다. PM과는 fullscreen 광고가 웹 UI를 가릴 수 있다는 제약을 논의했다. 웹 버튼이 있다고 네이티브 광고 위에서도 보이는 것은 아니므로, 웹의 대기 상태와 외부 광고 화면의 문제를 함께 보되 책임을 구분했다.

여기서 시간은 성공이나 실패의 판정 기준이 아니었다. 사용자에게 대기를 끝낼 선택을 제공하는 시점이었다. 타이머만 끝났을 때는 참여 기록을 전송하지 않고, 사용자가 버튼을 눌렀을 때 별도의 복구 결과로 이어갔다. 정상 광고 식별값을 넣어 완료한 것처럼 만들지도 않았다.

## 허용한 선택은 늦은 응답 뒤에도 유지돼야 했다

버튼을 열어주는 것만으로 복구가 끝나지는 않았다. 사용자가 skip을 고른 뒤 외부 Promise가 늦게 resolve하거나 reject할 수 있었다. 그때 이미 고른 복구 결과가 뒤집히면 화면은 다시 이전 대기로 돌아가거나 다른 결과를 사용할 수 있다.

현재 attempt에 시작 여부, skip 여부, controller를 묶었다. skip을 선택하면 먼저 그 시도가 skip됐다고 남기고 취소 신호를 보냈다. 같은 시도를 반복해서 skip하지 않게 하고, 늦은 성공과 실패 모두 기존 선택을 유지하도록 했다. finally 역시 현재 활성 attempt가 자신일 때만 정리했다.

설명용으로 두 행동의 차이를 줄이면 다음과 같다. 실제 회사 코드를 옮긴 것은 아니다.

```text
규칙 조회 전 변경: 모르는 규칙을 없음으로 취급 → 실행 제한
광고 대기 후 탈출: 모르는 완료를 성공으로 취급하지 않음 → 별도 복구 허용
복구 뒤 늦은 응답: 이미 끝낸 시도의 선택을 수정하지 않음
```

테스트는 대기만 한 경우와 클릭한 경우, 중복 클릭과 늦은 응답, 정상 응답이 먼저 끝난 경우를 나눴다. 정상 결과가 먼저 오면 복구를 실행하지 않고, 복구를 선택한 뒤에는 그 결과를 유지하는 조건이었다.

## 같은 로딩 상태에도 서로 다른 다음 행동이 있다

토글에서는 조회가 끝나기 전 클릭이 상태 변경으로 이어지는 경로를 막았다. 광고 대기에서는 일정 대기 뒤 사용자가 수동으로 빠져나오고 남은 후보 처리를 이어갈 수 있게 했다. 이후 참여 기록 요청이 성공해야 상자 화면으로 넘어가는 조건은 계속 남았다. 탈출과 지급을 같은 행동으로 만들지 않은 결과다.

지금 두 작업을 함께 돌아보면, 프론트엔드 상태를 loading 하나로 읽을 때 놓치는 것은 사용자 행동의 의미다. 토글은 확인이 필요한 설정을 바꾸고, 복구 버튼은 미확정인 광고 결과를 성공으로 선언하지 않은 채 대기를 끝낸다. 보수적인 UI와 적극적인 UI라는 취향의 차이로는 이 선택을 설명하기 어렵다.

당시 토글 작업에서 다룬 조회 중 클릭과 별개로, 조회 실패 뒤 어떤 행동을 허용할지는 지금 다시 설계하고 싶은 지점이다. loading이 끝났다는 사실도 규칙 없음의 증거는 아니다. 다음에 같은 화면을 만든다면 버튼을 막을지부터 정하기보다, 그 버튼이 무엇을 확정하고 무엇을 남겨둬야 하는지부터 상태 모델에 적고 싶다.
