적립 문의를 처리하는 운영자에게 문의 내용만 보여주면 어떤 판단을 할 수 있을까? 사용자는 적립이 안 됐다고 설명하지만, 운영자는 참여 캠페인과 시점, 이미 처리된 적립, 반복 참여의 마지막 기록을 함께 알아야 했다. 각 항목이 조회된다는 사실과 그 문의를 처리할 수 있다는 사실은 달랐다.

몇 년 전 리텐션 리포트를 만들 때도 비슷한 질문이 있었다. 날짜별 숫자를 표로 놓고 CSV로 내보내면 기능은 갖춰진다. 그러나 어느 기간의 어떤 사용자 묶음을 비교하는지, 제공되지 않는 값에는 어떤 조건이 있는지 모르면 운영자는 표를 다음 판단에 쓰기 어렵다.

두 제품에서 내가 맡은 코드는 달랐지만 지금 연결해볼 수 있는 질문은 같다. **화면을 읽은 사람이 무엇을 결정할 수 있어야 이 개발이 끝났다고 할 수 있을까?** 이 질문은 화면의 배치에서 시작해 서버 응답의 내용과 요청 후 상태까지 이어졌다.

## 리포트의 기간은 조회 파라미터 이상이었다

[리텐션 리포트](/cases/retention-report-boundaries/)에서는 기준일의 사용자 묶음과 이후 날짜의 값을 행과 열로 바꾸고 내보내기를 구현했다. 같은 기준일의 전환 수와 이후 리텐션을 함께 읽으려면 응답의 배열 순서를 그대로 그리는 것보다 각 값을 올바른 날짜 열에 대응시키는 작업이 필요했다.

서버 담당자에게는 광고의 시작·종료 날짜를 FE가 query로 보내는 경우와, 생략했을 때 서버가 기본 기간을 정하는 경우를 나눠 제안했다. 실제 화면의 조회 코드는 광고 ID를 전달했다. 제안한 모든 날짜 선택이 화면에 구현됐다고 합칠 수는 없지만, 날짜의 책임을 맞춰야 했던 이유는 남는다. 사용자가 읽는 기간을 누가 결정하는지 설명할 수 있어야 했다.

표본과 실험적 성격, 갱신 시점, 작은 규모에서 제공되지 않는 값의 조건을 알리는 문구에도 참여했다. 설명 문구는 데이터의 한계를 숨기지 않게 했지만 셀마다 값 없음과 실제 0을 구별하는 구현까지 대신하지는 못했다. 당시 정규화는 빠진 일자를 0으로 채웠고 그래프는 0을 빈칸으로 보였다. 이 차이는 [데이터 소비 계약을 돌아본 글](/essays/data-trust-two-sided/)에서 더 자세히 다룬다.

## 문의 관리에는 정보보다 처리 문맥이 필요했다

[적립 문의 관리 제품](/cases/cs-workflow-product/)의 목표는 목록과 상세를 새로 만드는 데 머무르지 않았다. 운영자가 그 페이지에서 적립 여부를 판단하고 처리할 수 있어야 했다. 나는 FE와 API client, 기존 서버에 요청을 연결하는 BFF를 맡았다.

상세에는 문의 내용과 사용자·캠페인 정보, 미션별 상태, 최근·전체 서버 이벤트, 처리 이력을 연결했다. 이 정보가 같은 문의와 캠페인을 설명해야 했다. 미션 카드는 적립 완료·가능·불가능·요청 중을 구분하고, 실행 중에는 같은 행동을 다시 누르지 못하게 했다. 목록의 완료 여부와 페이지네이션도 상세 작업의 출발점이었다.

개발 중에는 미션 유형, 복수 이벤트 문맥, 완료 처리자, 목록과 이력의 페이지네이션 계약을 서버 담당자에게 확인했다. 조회 오류도 구체적으로 전달했고 서버 수정의 검증 환경 배포 뒤 회복을 확인했다. 응답을 받아 화면을 그리는 입장이어도, 운영자가 판단할 수 없는 응답을 그대로 소비하는 것으로 책임이 끝나지는 않았다.

읽기 요청과 적립·완료 명령은 BFF에서 각각 읽기·쓰기 권한에 연결했다. 운영자가 정보를 보는 행동과 상태를 바꾸는 행동을 화면에서도 구분한 결과다. 서버의 적립 서비스 자체는 서버 담당자의 작업이었고, 나는 그 계약을 실제 운영 흐름에 연결했다.

## 정상 동작과 편의성을 다른 질문으로 검토했다

QA 전 제품 담당자에게 추가되거나 불필요한 기능과 사용 편의성을 먼저 봐달라고 요청했다. 정상 동작은 QA에서 확인할 수 있지만, 운영자가 어떤 순서로 정보를 읽어야 하는지는 업무 관점에서 검토할 필요가 있었다.

사진 확대와 상단 정보 배치 의견은 반영했다. 이벤트 검색은 후속 논의, 완료 취소는 다음 스펙으로 남겼다. 다른 캠페인을 즉시 적용하는 기능은 공용 컴포넌트 변경이 필요했고 다른 우선순위도 있어 다음 스프린트로 넘길 수 있는지 물었다. 제품 담당자와 범위를 합의한 뒤 핵심 판단·처리 흐름을 먼저 전달했다.

이 구분이 없으면 요구 목록이 곧 출시 완료 목록이 된다. 반대로 작은 버튼만 골라 완료했다고 하면 처음 해결하려던 운영 판단이 사라진다. 당시 범위 조정은 공용 구성 변경 비용을 이유로 특정 기능을 나누되, 문의의 근거를 읽고 적립·완료하는 흐름은 남기는 선택이었다.

## 실사용은 첫 출시에서 빠진 시간차를 알려줬다

출시 뒤 실제 화면에서 처리하기 편하다는 반응이 있었다. 그러나 API 성공 직후의 완료 안내와 실제 적립 이력이 어긋나는 문제도 이어졌다. 운영자는 다시 확인하는 번거로움과 누락 가능성 때문에 실시간 표시를 원했다.

서버 담당자와 지연 조건을 논의하고 즉시 완료 안내 대신 확인 중 상태와 상한이 있는 후속 조회를 넣었다. 요청이 받아들여진 순간과 화면의 상태가 바뀐 순간 사이를 표현한 것이다. 모든 지급·정산을 확정하는 장치가 아니라 운영자가 후속 확인을 결정할 수 있는 화면이었다. [CS 제품의 구축과 후속 조회](/cases/cs-workflow-product/)에 실행 순서를 정리했다.

첫 출시의 범위는 끝나지 않은 기능의 목록만으로 정할 수 없었다. 핵심 판단·처리 흐름을 먼저 전달했고, 실제 사용이 알려준 시간차는 다음 개선의 입력이 됐다.

## 화면의 끝은 다음 판단의 시작이었다

리포트에서는 운영자가 같은 날짜 열의 자료를 보고 파일로 내보낼 수 있게 했다. 문의 제품에서는 판단 근거를 읽고 적립·완료를 실행하는 흐름을 전달한 뒤, 실사용에서 드러난 상태 지연을 다시 화면에 넣었다. 서버 협의와 제품 검토가 필요한 이유도 이 다음 행동에 있었다.

후속 [다음 문의 이동](/cases/operator-next-inquiry/)은 이 관점을 다른 단계로 이어준다. 한 건의 처리가 성공해도 다음 건 조회는 실패할 수 있었다. 끝낸 처리를 다시 실패로 알리지 않고, 새 상세 조회가 실패하면 이전 문의 정보를 비웠다. 문의 한 건의 완료와 다음 작업의 준비를 서로 다른 결과로 다룬 것이다.

지금 돌아보면 운영 화면을 잘 만든다는 말은 정보량을 늘리는 것보다, 사용자가 그 정보를 믿고 무엇을 해도 되는지 정하는 일에 가깝다. API 계약에서 부족한 문맥을 되돌리고, 출시 범위를 협의하고, 응답 뒤 시간차까지 상태로 만든 과정이 내가 이 제품에서 맡은 프론트엔드 개발의 범위였다.
