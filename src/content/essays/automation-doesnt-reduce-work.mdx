여러 팀이 같은 광고 운영 대시보드에 기능을 넣을 때는 버전만 올린다고 릴리스 준비가 끝나지 않았습니다. 어느 커밋을 어떤 릴리스 브랜치에 반영할지, beta 검증 중인 변경과 hotfix를 어떻게 나눌지, 태그가 어떤 코드를 가리키는지 확인해야 했습니다. 메뉴별 QA와 배포 시점을 맞추는 협의도 필요했습니다.

2022년부터 이 반복 절차를 Vump라는 도구로 구현했습니다. 초기화, 버전 확인과 변경, 선택한 커밋 반영, 태그 준비를 스크립트로 연결했고 이후 hotfix와 버전 업데이트 PR 생성도 추가했습니다. 다른 팀 개발자도 직접 태그를 준비할 수 있게 됐습니다. 그런데 실제 사용이 시작되자 실패한 커밋 반영을 복구하고 다음 담당자에게 승인 요청을 넘기는 일도 남았습니다.

## 실행 절차를 넘겨도 릴리스의 판단은 남는다

초기 스크립트는 다음 버전만 계산하지 않았습니다. Git 상태를 검사하고 반영할 커밋의 메시지를 보여주고 확인을 받은 뒤 버전과 태그를 만드는 흐름이었습니다. 릴리스의 입력은 커밋이고 버전은 그 결과를 가리킵니다. 둘을 따로 다루면 숫자는 맞아도 의도한 변경이 들어 있지 않을 수 있습니다.

후속 workflow는 버전용 브랜치의 push를 받아 업데이트 PR을 만들고 담당자를 reviewer로 지정했습니다. 자동화한 것은 반복적인 준비와 PR 생성이었습니다. PR의 승인과 병합, 메뉴별 QA, 태그를 실제로 배포하는 단계는 담당자들이 이어서 수행했습니다.

여러 팀의 배포 정책과 사용 가이드는 동료들이 함께 정리했습니다. 제가 구현한 스크립트는 그 정책 안에서 릴리스 준비를 담당했습니다. 도구를 사용할 수 있다는 것과 지금 이 변경을 내보내도 된다는 것은 서로 다른 판단이었습니다. 자동화의 범위를 설명하려면 그 사이에 남는 사람의 작업도 드러나야 했습니다.

## 사용자의 성공과 실패가 도구의 실제 범위를 보여줬다

다른 팀 개발자는 beta에 자신의 변경을 포함하려고 실행 방법과 커밋 반영 여부를 물었습니다. 동료와 함께 안내한 뒤 beta 태그 생성 성공을 확인했고 편리하다는 반응도 받았습니다. 이때 결과는 다른 사람이 자신의 릴리스 준비에 도구를 실제로 사용했다는 것이었습니다.

한편 초기에는 여러 커밋을 반영하는 제약을 안내했고 구버전 hotfix 오류에는 수동 우회가 필요했습니다. 이후 hotfix 기능을 추가했어도 모든 제약이 사라진 것은 아니었습니다. 중복된 브랜치 초기화와 커밋 반영 실패 같은 사용 문제도 이어졌습니다.

다른 개발자가 태그를 만들 수 있게 된 뒤에는 실패한 입력을 설명하고 기존 작업을 이어가도록 지원할 일이 생겼습니다. 저는 사용 불편을 모았고, 동료들은 상황별 가이드와 지원을 나눠 맡았습니다. 성공한 실행만 보면 빠지는 비용이었고, 명령 목록과 함께 이 사용 지식도 필요했습니다.

## 자동화가 실패했을 때 확인한 것은 전달할 코드였다

2023년 11월, beta 검증과 다른 팀의 hotfix가 겹치는 상황에서 도구의 커밋 반영이 실패했습니다. 먼저 팀 간 릴리스 정책의 위험을 논의했습니다. beta 검증 중인 코드가 다른 hotfix와 함께 운영으로 나갈 수 있는지, beta를 어느 수준으로 다룰지는 태그 생성만으로 풀리지 않는 문제였습니다.

저는 beta도 상용처럼 다루자는 의견을 냈고 동료는 그렇게 하면 beta의 의미가 약해진다고 반론했습니다. 이 정책 논의와 도구의 실행 오류는 별도로 남아 있었습니다. 태그 생성에 실패한 문제를 고치더라도 공유 브랜치에 어떤 변경을 포함할지는 다시 판단해야 했습니다.

실패한 작업에서는 커밋 순서, 기준 브랜치에 포함된 변경, 태그 내용부터 확인했습니다. 수동으로 태그를 준비하고 beta 동기화를 지원했습니다. 담당자는 운영 배포 완료와 잠금 인계를 보고했습니다. 자동 실행은 실패했지만 협업으로 해당 릴리스는 전달됐습니다. 실행 오류의 원인은 그때 파악하지 못한 상태였지만 전달해야 할 코드와 환경을 맞추는 복구는 이어졌습니다.

## 운영을 이관하는 일도 구현의 후속이었다

팀을 옮길 때는 버전 PR의 reviewer를 새 담당자로 바꿨습니다. 사용법을 설명하는 것과 실제로 다음 승인 요청이 누구에게 가는지 바꾸는 것이 함께 필요했습니다. 이관 뒤에는 다른 담당자의 개선과 버전 PR 운영이 이어졌습니다.

지금 이 과정을 보면, 인계할 때는 도구의 사용법뿐 아니라 실행 결과를 판단하고 사용을 지원할 담당자도 정해야 했습니다. 코드가 그대로 남아 있어도 reviewer가 이전 담당자를 가리키면 책임은 옮겨지지 않습니다. 동료가 정리한 가이드와 배포 정책도 새 담당자가 운영할 수 있는 기반의 일부였습니다.

## 다른 사람이 계속 사용할 수 있는 결과

Vump는 다른 팀의 태그 준비 성공과 편리하다는 반응을 얻었습니다. 실행이 실패한 릴리스에서는 수동 지원으로 배포와 인계가 이어졌고, reviewer를 바꾼 뒤에는 다음 담당자가 운영했습니다. 도구는 이후 제거됐지만, 한때 다른 사람이 자신의 작업에 쓸 수 있는 경로를 만들고 넘겼다는 경험은 남았습니다.
