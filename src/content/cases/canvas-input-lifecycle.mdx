광고 참여 뒤 사용자는 복권 표면을 긁어 리워드 결과를 확인한다. 이 마지막 화면에서 입력이 반응하지 않으면, 사용자는 앞의 참여를 마쳤는데도 결과를 확인할 수 없다.

복권이 긁히지 않는다는 문의가 들어왔지만 같은 조건을 바로 재현하기 어려웠다. Canvas 오류를 찾아도 문의를 설명할 만한 예외가 보이지 않았다. 이때 ‘에러가 없다’는 것은 ‘입력이 정상이다’와 같은 말이 아니었다. 손가락의 동작이 Canvas까지 도달했는지, 화면이 준비됐다는 상태와 실제 입력 영역이 같은지도 봐야 했다.

6월에는 touch/click 가설을 세우고 입력을 확인할 관측과 보강을 넣었다. 이후 6~7월에는 Canvas의 크기·초기화·프레임과 반복 입력의 수명주기를 함께 보완했다. 이 글의 질문은 **예외로 잡히지 않는 입력 문제를 어디에서 관찰하고, 어떤 상태를 보존할 것인가**다.

## 문의의 감소와 수정 적용 시점을 먼저 나눴다

조사 중 문의가 줄어드는 관찰도 있었다. 그때 나는 아직 수정이 배포되지 않았다고 알렸다. 뒤에 넣은 보강으로 그 이전의 감소를 설명할 수는 없었다.

입력 관련 보강과 모니터링을 배포한 뒤에는 CS 담당자가 문의가 크게 줄었다고 답했다. 전날 오후의 적용 여부를 물었고, 나는 적용 시점을 확인했다. 재현이 어려운 문제여서 코드만 보고 끝내는 대신, 무엇을 언제 바꿨고 실제 문의에서는 어떤 변화가 보였는지 함께 대조했다.

이 반응은 6월 중순의 입력 보강 직후 확인한 것이다. 그 뒤의 크기·레이아웃·진단 측정 변경을 모두 합쳐 하나의 감소율로 설명하지는 않는다. 당시의 관찰이 알려 준 것은 입력 경로를 더 확인할 가치와 운영에서 돌아온 후속 반응이었다.

## CSS 크기와 비트맵 크기는 다른 갱신이었다

복권 위아래에는 배너와 영상이 함께 배치됐다. 화면의 레이아웃이 변하면 Canvas가 차지하는 크기와 손가락 좌표를 읽을 영역도 맞춰야 했다.

그런데 Canvas의 width·height를 다시 설정하는 것은 일반 CSS 스타일을 다시 넣는 일과 다르다. 그리기 상태에 영향을 줄 수 있다. 같은 값이라도 계속 대입하면 진행 중인 긁기를 보존하기 어려워진다.

실제 레이아웃을 읽어 비트맵 크기를 정수로 정규화하고, 크기가 달라졌을 때만 width·height를 갱신하도록 했다. 입력 영역은 그 레이아웃에 맞춰 연결했다.

아래는 공개 설명용 의사코드다.

```ts
function syncSize() {
  const rect = measureLayout();
  const next = integerBitmapSize(rect);

  if (!sameBitmapSize(canvas, next)) {
    canvas.width = next.width;
    canvas.height = next.height;
    initializeDrawingContext();
  }

  updateInputArea(rect);
}
```

여기서 보존하려는 것은 단순한 크기 값이 아니라 사용자가 이미 시작한 입력이다. 매번 최신 레이아웃을 읽는 것과, 실제로 바뀐 비트맵만 갱신하는 것을 구분해야 했다.

## 준비 실패를 READY로 넘기지 않았다

Canvas ref가 없거나 controller 초기화가 실패했으면 준비 상태로 가장하지 않고 오류 상태로 드러냈다. 화면에 Canvas가 있다는 사실과 입력을 받을 준비가 끝났다는 사실은 달랐다.

동시에 표시 초기화 오류가 기존 결과 확인 경로까지 끊지 않도록 scratch→stop 흐름의 클라이언트 완료 경로를 유지했다. 서버의 리워드 승인과 화면에서 긁는 입력의 종료는 같은 책임이 아니었다.

이는 ERROR를 무조건 성공으로 바꾸는 선택이 아니다. 초기화 실패는 오류로 남기되, 사용자가 이어 갈 기존 완료 동작은 따로 보존했다. 하나의 READY 플래그에 초기화·입력·리워드의 모든 성공을 넣지 않으려는 보완이었다.

## 레이아웃은 paint 전에, 진단은 반복 입력 밖에서

복권의 크기만 맞춰도 배너 높이가 바뀌면 화면 전체의 프레임이 달라졌다. 예약 높이를 실제 프레임 계산에 반영하고, 그 prop이 바뀌었을 때 paint 전에 레이아웃을 맞추도록 보완했다.

포인터 좌표가 맞는지와 전체 프레임이 화면 안에 들어오는지는 다른 문제였다. 손가락이 움직일 때마다 이 배치 문제를 다시 해결할 필요는 없었다.

진단에도 비슷한 구분이 필요했다. 문제를 조사하려고 DOM 크기와 hit-test 정보를 읽더라도 모든 포인터 이동에서 그 측정을 반복하면 빈번한 입력에 조사 비용이 붙는다. 화면 진입과 상태 전이에 진단 측정을 두고, 반복 포인터 경로에서는 지오메트리 측정을 하지 않도록 나눴다.

입력을 관찰하는 코드를 넣는 일과 그 입력 경로를 계속 무겁게 만드는 일은 같지 않았다. 어떤 값이 실제로 바뀌는 순간인지 먼저 정해야 했다.

## 서로 다른 실패와 보존할 행동을 테스트로 나눴다

초기화·프레임·입력에는 서로 다른 기대 결과를 남겼다.

| 조건 | 확인할 동작 |
| --- | --- |
| Canvas 요소가 없거나 초기화가 실패 | 준비 상태로 넘기지 않고 오류 반환 |
| ERROR 뒤 scratch→stopScratch | 기존 클라이언트 완료 경로 유지 |
| 레이아웃 크기 변경 | 정수 비트맵 크기 반영 |
| 예약 높이 prop 변경 | 프레임 계산 반영 |
| 반복 포인터 액션 | 진단 지오메트리 측정 미호출 |

같은 크기에서 비트맵을 다시 설정하지 않는 조건도 구현에 남겼다. 실제 문의를 좁힐 관측과 상태·입력 조건을 고정할 테스트는 각각 다른 질문에 답했다.

## 마지막 입력도 제품의 일부였다

입력 보강 뒤에는 CS의 감소 확인이 돌아왔고, 후속에서는 초기화 실패와 프레임 변화, 반복 입력의 측정 비용을 따로 다뤘다. 사용자의 마지막 동작을 살리려면 Canvas만 볼 수 없었다. 광고 뒤의 참여 상태, 입력 준비, 실제 화면 크기, 결과 확인까지 이어져 있었다.

처음에는 예외를 찾으려 했다. 그러나 손가락이 닿았는지와 준비된 영역이 맞는지는 오류 로그만으로 알 수 없었다. 필요한 장면을 관측하고, 사용자의 진행 상태를 건드리는 갱신과 그렇지 않은 측정을 나눈 뒤에야 문제를 더 구체적으로 설명할 수 있었다.
