같은 광고 카드를 눌러도 어떤 진입점은 SDK를 사용하고, 어떤 경로는 외부 참여 페이지를 연다. 기존 콘텐츠에 인앱 광고 참여를 추가할 때는 페이지를 여는 방법만 바꿀 수 없었다. 이후 참여 요청이 어떤 환경에서 실행됐는지 알아야 하고, 앱 호출에 실패해 외부로 열리면 그 문맥도 달라져야 했다.

나는 인앱 참여의 진입·랜딩·복귀·완료 UI를 맡았고 동료는 미디에이션, 즉 광고 공급사를 연결하는 계층을 리팩터링했다. 교차 추천은 별도 작업으로 두고 핵심 참여부터 전달하기로 했다. 서버·디자인·매체 앱의 역할과 연결하면서 기존 외부 경로도 유지했다.

## 추적 링크와 사용자가 도착할 URL은 같지 않았다

상단 카드와 오퍼월, 콘텐츠 내부 추천은 진입 계약이 달랐다. 어떤 진입점에는 최종 콘텐츠로 연결하는 resolver가 있지만 다른 경로에는 없었다.

초기 FE 조립을 바꾸는 과정에서는 서버가 최종 콘텐츠 URL에 인앱 표식을 넣고, 그 뒤 추적 링크로 감싸는 계약을 소비하도록 맞췄다. 이미 감싸진 추적 URL을 화면에서 고치는 방식으로 모든 목적지에 같은 의미를 만들 수는 없었다.

```text
실제 콘텐츠 URL에 실행 문맥 연결
  → 추적 URL로 감싸기
  → 사용자 진입
  → 콘텐츠가 실행 문맥을 읽고 참여
```

표식은 클라이언트가 어떻게 실행할지 읽는 문맥이었다. 표식이 있다는 사실만으로 실제 앱 실행이나 시청을 인증하는 것은 아니었다.

## 폴백에서는 실패한 실행의 문맥도 바꿨다

앱 인터페이스 호출에 실패해 외부 브라우저를 열면 내부 콘텐츠의 인앱 표식을 제거했다. 실제 실행은 외부인데 URL은 인앱이라고 말하면 다음 요청도 잘못된 조건을 읽을 수 있었다.

같은 이름의 query라고 아무 목적지에서 지우지는 않았다. 내부 콘텐츠의 표식만 다루고 광고주의 동명 파라미터는 보존했다. 열기 방식의 폴백이 광고주 URL의 의미까지 바꾸면 안 됐다.

복귀 listener는 실제 열기 전에 등록했다. 빠르게 돌아오는 경우를 놓치지 않기 위해서였다. 열기에 실패한 경로에서는 listener를 정리했다. 화면을 여는 호출과 복귀를 기다릴 수명이 함께 시작하고 끝나도록 연결했다.

## 먼저 출시한 뒤 완료 표시의 범위를 좁혔다

8월 19일 공동 상용 출시 뒤 동료들의 실제 정상 참여 확인을 받았다. 이후에는 완료 UI를 맞추기 위한 로컬 신호를 추가하고 적용 조건을 보완했다.

이전 회차에서 완료한 기록이 새 카드의 표시를 바꿀 수 있었다. 같은 콘텐츠라고 해도 광고 할당이 다르거나 현재 클릭보다 앞선 완료라면 이번 참여의 근거로 쓸 수 없었다.

완료 기록은 다음 조건을 함께 확인하도록 좁혔다.

| 확인할 것 | 필요한 이유 |
| --- | --- |
| 광고 할당 | 같은 콘텐츠의 새 광고를 이전 기록으로 완료 처리하지 않음 |
| 회차 | 이전 시간대의 완료를 현재 회차로 이어 쓰지 않음 |
| 현재 클릭 이후 시각 | 이번에 시작하기 전의 기록을 새 결과로 읽지 않음 |

8월 하순에는 할당 조건까지 강화해 후속 통합했다. storage와 화면 복귀, 다른 할당·회차·이전 클릭을 무시하는 조건도 회귀 테스트에 포함했다.

로컬 기록은 UI 동기화를 위한 신호였다. 외부 폴백에서는 서버의 전환 확인을 유지했고, 승인과 지급은 서버 상태를 따랐다. 사용자에게 빠르게 완료를 보여주는 선택이 서버 판정을 대신하는 선택으로 넓어지면 안 됐다.

## 새로운 실행 경로를 넣으면서 기존 참여를 지키기

사용자는 기존 콘텐츠에서 새 인앱 참여 흐름을 이용할 수 있게 됐고, 실행이 외부로 넘어가는 경로도 남았다. 초기에 공동 출시한 결과와 이후 완료 동기화를 보완한 결과는 단계가 달랐다.

이 경험에서 가장 크게 남은 것은 문맥을 전달하는 일의 범위였다. URL에 표식을 붙이는 순간뿐 아니라, 실제로 열린 환경과 복귀 때 읽을 기록도 같은 참여를 설명해야 했다. 기존 제품에 실행 경로를 하나 더 넣을 때는 새 정상 경로와 함께, 그 경로가 실패해 이전 방식으로 돌아간 뒤에도 무엇을 믿을 수 있는지 확인하게 됐다.
