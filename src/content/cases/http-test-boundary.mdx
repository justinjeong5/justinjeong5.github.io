통계 조회 API가 시작 날짜와 종료 날짜를 요구한다고 해보자. 날짜 하나가 빠졌을 때 예외가 발생한다면 입력 검증은 있는 것이다. 하지만 화면이 받는 것은 예외 객체가 아니라 HTTP 상태와 JSON 응답이다.

AI와 함께 이 API의 계약 테스트를 보강하는 작업에서, 첫 테스트는 view 메서드를 직접 호출하고 입력 오류가 발생하는지 확인했다. 구현의 한 부분을 검사했지만 API를 사용하는 쪽의 계약까지 따라간 구성은 아니었다.

## 테스트가 지나가지 않은 코드

오류 응답은 view 함수만으로 만들어지지 않았다. 입력 검증에서 발생한 예외를 middleware가 받아 HTTP 상태와 오류 필드를 가진 JSON으로 변환했다. view를 직접 호출하면 그 변환을 지나가지 않는다.

따라서 예외가 맞게 발생해도 사용자에게 잘못된 상태나 응답 형식이 전달되는 변경을 이 테스트가 잡는다고 볼 수 없었다. 검사해야 할 것은 특정 예외 클래스의 이름보다, 요청을 보냈을 때 API 사용자가 읽을 응답이었다.

테스트를 Django client의 실제 요청 경로로 바꿨다. 서비스가 통계를 계산하는 부분은 mock으로 두되, 요청 파싱과 입력 검증, middleware의 오류 응답은 함께 실행하도록 했다.

## 거절과 정상 전달을 각각 확인하기

입력이 부족한 경우에는 종료 날짜가 없는 요청을 보냈다. 응답 상태가 422이고, 입력 오류 코드와 설명이 JSON에 담기는지 확인했다. 서비스가 생성되지 않았다는 조건도 함께 검사했다. 요청을 거절하면서 뒤의 통계 조회까지 실행하는 흐름이면 안 됐기 때문이다.

정상 요청에서는 네트워크·기간·캠페인 조건이 서비스에 전달되는지, 서비스의 결과가 응답 JSON으로 돌아오는지 확인했다. 단순히 200을 받는 것과 올바른 조회 조건을 전달하는 것은 다른 검사였다.

서비스 mock도 자유롭게 메서드를 받아주는 형태에서 `autospec`을 사용하는 형태로 바꿨다. 실제 서비스의 시그니처와 맞지 않는 호출이 테스트에서 조용히 통과하지 않도록, 외부 계산을 대체하는 mock의 모양을 실제 인터페이스에 맞췄다.

## 어디를 실제로 실행할 것인가

이 테스트에서 통계 계산 결과는 미리 정한 값이었다. 계산 엔진이나 실제 데이터의 정확성을 확인하려는 테스트는 아니었다. HTTP 요청이 올바르게 거절되거나, 입력을 전달하고 결과를 반환하는 경로를 확인하는 데 범위를 두었다.

수정한 두 테스트는 CI의 테스트·린트 검사를 통과해 병합됐다. API 동작을 새로 만든 작업이 아니라, 기존 API의 어느 경계를 테스트가 지키는지 바꾼 작업이었다.

AI가 작성한 첫 안이 실행된다는 것만으로 검증이 끝나지는 않았다. 직접 호출한 함수와 실제 사용자가 접하는 경로 사이에서 빠진 처리가 있는지를 봐야 했다. 다음 테스트를 읽을 때도 먼저 묻게 되는 것은 “무엇을 mock했나”보다 “사용자가 받는 결과까지 어떤 코드를 지나갔나”다.
