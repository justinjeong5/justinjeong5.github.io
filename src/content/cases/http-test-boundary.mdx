통계 조회 API에는 시작 날짜와 종료 날짜가 필요했습니다. 날짜 하나가 빠진 요청은 계산 전에 거절하고, 사용하는 쪽에 이유를 읽을 수 있는 오류 응답을 돌려줘야 했습니다. 서버 함수에서 예외가 발생하는지 확인하는 것만으로는 그 응답까지 검사할 수 없었습니다.

웹 화면이나 다른 API 소비자가 받는 것은 서버 함수의 예외 객체가 아닙니다. 요청이 성공했는지 나타내는 HTTP 상태와 오류 코드·설명이 담긴 응답입니다. 소비자는 그 결과를 읽어 잘못된 입력인지 다른 실패인지 구분할 수 있어야 합니다.

AI와 만든 첫 안에서는 요청을 처리하는 view 메서드를 직접 호출했습니다. 이 방식으로 날짜가 없을 때 입력 오류가 발생하는지는 확인했습니다. 다만 HTTP 상태와 오류 JSON까지 확인하려면 함수 뒤에서 응답을 변환하는 코드도 지나야 했습니다.

## 테스트가 지나가지 않은 코드

입력 예외를 HTTP 상태와 오류 필드가 있는 JSON으로 바꾸는 것은 middleware였습니다. view를 직접 호출하면 이 코드를 지나가지 않아, 예외는 맞게 발생해도 응답 형식이 어긋나는 변경을 놓칠 수 있었습니다.

테스트를 Django client의 실제 요청 경로로 바꿨습니다. 서비스가 통계를 계산하는 부분은 mock으로 두되, 요청 파싱과 입력 검증, middleware의 오류 응답은 함께 실행하도록 했습니다.

## 거절과 정상 전달을 각각 확인하기

입력이 부족한 경우에는 종료 날짜가 없는 요청을 보냈습니다. 응답 상태가 422이고, 입력 오류 코드와 설명이 JSON에 담기는지 확인했습니다. 서비스가 생성되지 않았다는 조건도 함께 검사했습니다. 요청을 거절하면서 뒤의 통계 조회까지 실행하는 흐름이면 안 됐기 때문입니다.

정상 요청에서는 네트워크·기간·캠페인 조건이 서비스에 전달되는지, 서비스의 결과가 응답 JSON으로 돌아오는지 확인했습니다. 단순히 200을 받는 것과 올바른 조회 조건을 전달하는 것은 다른 검사였습니다.

서비스 mock도 자유롭게 메서드를 받아주는 형태에서 `autospec`을 사용하는 형태로 바꿨습니다. 실제 서비스의 시그니처와 맞지 않는 호출이 테스트에서 조용히 통과하지 않도록, 외부 계산을 대체하는 mock의 모양을 실제 인터페이스에 맞췄습니다.

## 어디를 실제로 실행할 것인가

보강한 테스트는 입력이 부족한 요청의 HTTP 상태·오류 JSON과, 정상 요청의 조회 조건 전달·응답 결과를 확인합니다. 잘못된 입력에서 서비스를 만들지 않는 조건도 함께 남겼습니다. 계산 결과는 mock이지만, 요청을 사용하는 쪽이 받는 응답까지 실제 처리 경로를 지나며 검사하는 테스트가 됐습니다.

두 테스트는 CI의 테스트·린트 검사를 통과해 병합됐습니다. 제품 API를 새로 만든 작업은 아닙니다. 기존 API를 바꿀 때 함수의 예외뿐 아니라 HTTP 응답도 올바른지 검사하도록 테스트 범위를 넓혔습니다.

첫 안에서 직접 호출한 함수 뒤에는 middleware의 응답 변환이 남아 있었습니다. 테스트를 실제 요청 경로로 옮기면서 그 코드도 함께 실행하도록 했습니다. AI가 만든 테스트를 읽을 때는 assertion이 몇 개인지보다, 소비자가 받는 결과까지 필요한 코드가 실행되는지를 확인하게 된 작업이었습니다.
