리워드 광고에서 사용자는 앱을 설치하거나 게임의 미션을 수행한 뒤 리워드를 받는다. 한 캠페인에서 의미 있는 행동을 끝냈더라도, 다른 캠페인을 찾아 다시 참여하는 일은 별개의 선택이다. 목록을 다시 열고, 무엇을 할지 고르고, 받을 혜택을 비교해야 한다.

제품팀은 이 두 번째 선택을 돕고 싶어 했다. 광고주 과금 조건에 도달한 사용자에게 아직 참여하지 않은 캠페인을 추천하고, 추천을 통해 들어온 경우 일정 시간 동안 추가 리워드를 제공하는 기능이었다. 너무 일찍 다른 게임을 권하면 기존 캠페인에 깊게 참여할 시간을 나눠 버릴 수도 있었다. 그래서 **무엇을 추천하는가 못지않게 언제 추천하는가**가 중요한 제품 규칙이었다.

서버는 추천 자격과 캠페인 선정, 보너스 지급을 맡았다. 나는 추천 API를 화면에 연결하고, 배너를 누른 다음의 참여 진입과 혜택·남은 시간 표시, 기존 미션과 탐색 화면까지 이어지는 FE를 구현했다. 추천 배너를 그리는 작업으로 시작했지만, 실제로는 여러 화면이 같은 참여를 설명하도록 만드는 일이었다.

## 배너를 누른 뒤에도 같은 혜택을 설명해야 했다

추천 결과는 없을 수도, 하나일 수도, 둘일 수도 있었다. 한 캠페인은 배너로, 여러 캠페인은 카드 선택으로 표현했다. 추천을 열고 닫고 선택하는 행동에는 각각 캠페인 문맥을 남겼다.

어려운 부분은 카드를 누른 다음이었다. 추천을 보고 일반 캠페인 주소로만 이동하면, 도착한 화면은 사용자가 어떤 경로로 들어왔는지 모른다. 추가 혜택을 보여줘야 하는 참여와 원래의 참여가 같은 화면에 섞인다.

추천을 통한 진입에서는 서버에 보너스 참여 문맥을 전달하며 새 참여 식별자를 받아 이동하도록 연결했다. 다른 경로의 진입은 기존 동작을 유지했다. 도착한 미션 화면은 그 참여의 응답을 읽어 보너스 UI를 선택했다.

```text
추천 자격·캠페인 조회
  → 배너 또는 카드 선택
  → 추천 경유임을 담아 새 참여 시작
  → 해당 참여의 혜택·만료 시각 조회
  → 미션 화면과 탐색 목록에서 같은 혜택 표시
```

배너의 문구가 약속한 혜택은 다음 화면에서도 설명돼야 했다. 이동 자체가 성공했는지뿐 아니라, **어떤 참여로 이동했는지**가 중요했다. FE가 지급 자격을 새로 계산하는 대신 서버가 정한 참여 문맥을 이어서 읽는 구조였다.

## 두 개의 시계를 하나로 만들지 않았다

이 기능에는 시간이 두 가지 있었다. 추천을 닫은 뒤 다시 보여주지 않을 시간과, 추천으로 참여한 캠페인의 보너스가 끝날 시간이다.

닫힘 기록은 참여 식별자에 연결해 하루 동안 추천 재노출을 제한했다. 이는 사용자가 거절한 배너를 계속 열지 않기 위한 화면 규칙이다. 반면 보너스의 남은 시간은 서버가 내려준 만료 시각으로 표시했다. 닫힘 기록이 있다는 이유로 혜택을 지급하거나, 배너를 다시 열었다고 혜택 시간을 새로 시작할 수는 없었다.

```ts
// 설명용 재구성. 실제 API나 저장 구조를 복사한 코드는 아니다.
const canOpenBanner = !isRecentlyDismissed(entryId);
const remaining = timeUntil(serverBonus.expiresAt);

if (remaining <= 0) {
  refreshParticipation();
}
```

만료 뒤에는 참여 데이터를 다시 읽도록 했다. 화면의 카운트다운이 끝난 것과 서버가 적용하는 혜택이 같아야 했기 때문이다. 안내에는 제한 시간이 끝나면 기본 리워드가 적용된다는 의미도 담았다.

같은 숫자를 세고 있어도 두 시계가 보호하는 행동은 다르다. 하나는 추천을 다시 열지 않는 선택이고, 다른 하나는 혜택의 유효성이다. 로컬 화면의 편의 규칙을 서버의 지급 규칙처럼 쓰지 않는 것이 핵심이었다.

## 한 화면을 바꾸려다 기존 리워드의 의미도 드러났다

보너스는 새 미션 화면에서만 보이면 충분하지 않았다. 사용자는 탐색 목록의 캠페인 카드와 참여 중인 목록, 개별 미션에서도 받을 리워드를 비교한다. 한곳에는 기본값, 다른 곳에는 추가 혜택이 포함된 값이 보이면 같은 캠페인을 다르게 이해하게 된다.

기본 리워드와 보너스가 적용된 리워드를 구별해서 읽도록 표시 모델을 연결했다. 미션의 기존 리워드 값도 그 구분에 맞춰 정리했다. 두 값이 같을 때는 불필요한 취소선이나 할인처럼 보이는 표현을 만들지 않았다.

이 부분은 추천 카드의 새 UI만 추가해서는 끝나지 않았다. 새 정보가 기존 목록과 미션의 값을 어떻게 바꾸는지까지 확인해야 했다. 서버가 계산한 혜택을 여러 화면에서 일관되게 설명하는 일이 FE의 책임이었다.

## 실험 조건은 라우터에서 끝나지 않았다

후속에서는 게임 영상·일반·추천 화면의 진입 조건을 공용 라우터로 모았다. 같은 사용자가 게임 영상 조건과 추천 대상 조건을 동시에 만족할 수 있었다. 첫 구현의 조건 순서가 항상 원하는 화면을 설명하지는 못했다.

게임 영상 경로를 먼저 고르고, 그다음 추천 대상, 그다음 설정된 경로를 읽도록 순서를 보완했다. 현재 경로와 같으면 다시 이동하지 않았고, 이동할 때는 기존 query를 이어 썼다.

그런데 올바른 화면에 보냈다고 실험 노출도 맞는 것은 아니었다. 도착한 게임 화면에서 대상 구분 없이 추천을 조회하고 보여주던 부분을 함께 수정했다. 라우팅과 추천 조회·렌더링이 같은 조건을 이어서 사용해야 했다.

리뷰에서는 이미 읽은 context를 다시 조회하는 부분도 지적됐다. 나는 먼저 그 context를 공용 라우터에 넘기는 좁은 변경을 택했다. 추천 조건을 고치는 작업에 새 네트워크 계층까지 한꺼번에 도입하기보다, 실제로 중복된 조회부터 없애는 선택이었다.

## 다음 참여를 평가할 수 있는 제품으로 전달하기

추천은 새 참여 진입, 보너스와 만료 표시, 기존 목록·미션, 실험 대상의 노출까지 연결됐다. 6월의 후속에서는 게임 화면에서 대상 구분 없이 추천 배너가 동작하던 부분을 수정하고 배포를 보고했다.

이후 제품팀의 추천배너 실험 보고에는 설치당 광고주 과금 이벤트 평균과 구매 건수가 좋아졌고, 추가 리워드 비용에도 수익률을 유지했다는 평가가 담겼다. 추천·인센티브·서버·디자인·FE가 함께 만든 팀의 결과다. 내가 직접 맡은 부분은 그 전략을 실제 화면과 참여 흐름으로 전달하는 일이었다.

돌아보면 이 작업에서 가장 많이 달라진 것은 배너가 아니라, 혜택을 읽는 방식이었다. 추천을 받았다는 사실, 추천으로 참여했다는 사실, 아직 혜택이 유효하다는 사실은 서로 달랐다. 그 구분을 API와 이동, 여러 화면의 표시까지 이어 주어야 사용자가 제안받은 혜택을 실제로 이해할 수 있었다.
