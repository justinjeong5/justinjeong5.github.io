추천 배너가 특정 사용자군에만 보여야 한다면, 어떤 페이지로 들어왔는지에 따라 대상이 달라지면 안 된다. 그런데 여러 페이지가 각자 이동 조건을 가지고 있으면 같은 사용자와 캠페인도 서로 다른 분기를 밟을 수 있다.

이 작업에서는 사용자군 판별과 게임·일반·추천 화면의 이동이 여러 곳에 걸쳐 있었다. 나는 서버의 판별을 외부 API에서도 사용할 필요를 설명하고 요청했고, FE에서는 흩어진 이동 조건을 공용 라우터로 모으는 작업을 했다.

예를 들어 게임 영상이 있는 캠페인의 사용자가 추천 대상에도 해당하면 두 조건이 동시에 성립한다. 추천 조건을 먼저 적용할지 게임 경로를 먼저 적용할지에 따라 그 사람은 다른 화면으로 간다. 이번에 맞춰야 했던 것은 같은 판별을 여러 번 했다는 사실보다 그 우선순위와 도착한 화면의 노출이었다.

## 분기를 한곳에 모아도 순서는 남는다

라우터에는 현재 경로와 판별에 필요한 context를 전달했다. 대상 경로가 현재와 같으면 다시 이동하지 않고, 판별 과정에서 오류가 나면 현재 흐름을 유지하도록 했다. 이동할 때는 기존 query 정보를 이어서 전달했다.

하지만 조건을 공용 함수에 모았다고 분기의 의미까지 자동으로 맞지는 않았다. 첫 구현에서는 추천 대상 판별이 게임 영상 조건보다 앞에 있었다. 두 조건을 모두 만족하는 경우 무엇이 우선인지가 여전히 문제였다.

후속 변경에서는 게임 영상이 있는 경우의 경로를 먼저 고르고, 그다음 추천 대상, 그다음 설정된 경로를 보도록 순서를 바꿨다. 이렇게 하면 게임 영상 조건과 추천 대상이 겹쳐도 게임 경로가 먼저 선택된다. 기본 경로를 사용하는 context도 함께 맞췄다.

조건이 모두 참인지 검사하는 것과 어느 조건의 결과를 먼저 쓸지 정하는 것은 다른 일이었다. 이 순서는 단순 배열 배치가 아니라 상품이 요구하는 행동이었다.

## 노출 조건은 이동 뒤의 페이지에도 필요했다

실험군·대조군 구분 없이 추천 배너가 동작하던 문제를 수정해 배포했다고 보고한 기록도 있다. 이때 필요한 것은 목적지로 보내는 라우터만이 아니었다. 도착한 페이지에서 추천 API와 영역을 사용할 조건도 사용자군과 맞아야 했다.

라우팅과 렌더링이 각자 판별하면 한쪽만 고쳐도 다른 쪽의 노출이 남는다. “어디로 보낼 것인가”와 “그 화면에서 무엇을 보여줄 것인가”를 같은 조건에서 읽어야 하는 문제였다.

## 새 캐시보다 이미 받은 데이터가 먼저였다

리뷰에서는 context를 이미 읽었는데 다시 조회하는 부분이 지적됐다. 캐시도 없는 상태라 같은 정보를 얻기 위해 요청이 겹치고 있었다.

대안으로 이미 받은 context를 전달하는 방법과 요청 캐싱·네트워크 계층 정리가 논의됐다. 나는 먼저 페이지가 받은 context를 공용 라우터에 넘기는 좁은 변경을 선택했다. 판별을 위해 같은 정보를 다시 조회하지 않아도 됐고, 이동과 노출 조건의 정리에 집중할 수 있었다. 큰 네트워크 계층 리팩토링은 후속 기술부채로 남겼다.

## 같은 조건을 페이지마다 다시 해석하지 않도록

변경 뒤의 경로에서는 페이지가 얻은 context를 공용 라우터가 사용하고, 조건의 우선순위가 한곳에서 드러난다. 게임 영상 조건과 추천 대상이 동시에 성립할 때도 적용할 경로를 순서로 정했다.

게임 화면에서 실험군·대조군 구분 없이 추천 배너가 동작하던 문제의 수정·배포도 보고했다. 공용 라우터의 우선순위와, 도착한 페이지가 추천을 사용할 조건을 함께 맞춘 과정이었다.

이후 같은 조건을 추가한다면 나는 한 페이지의 분기만 보지 않을 것이다. 두 조건이 함께 참인 사람을 어느 경로로 보낼지, 그 경로에서도 같은 대상으로 배너를 제한할지를 함께 읽어야 한다.
