리워드 광고에서 사용자는 앱을 설치하거나 게임의 미션을 수행한 뒤 리워드를 받습니다. 한 캠페인에서 의미 있는 행동을 끝냈더라도, 다른 캠페인을 찾아 다시 참여하는 일은 별개의 선택입니다. 목록을 다시 열고, 무엇을 할지 고르고, 받을 혜택을 비교해야 합니다.

제품팀은 이 두 번째 선택을 돕고 싶어 했습니다. 광고주 과금 조건에 도달한 사용자에게 아직 참여하지 않은 캠페인을 추천하고, 추천을 통해 들어오면 일정 시간 동안 추가 리워드를 제공하는 기능이었습니다. 너무 일찍 다른 게임을 권하면 기존 캠페인에 깊게 참여할 시간을 나눌 수 있었습니다. 이 때문에 추천할 캠페인을 고르는 조건과 함께 **언제 추천을 보여줄지**도 정해야 했습니다.

서버는 추천 자격과 캠페인 선정, 보너스 지급을 맡았습니다. 저는 추천 API를 화면에 연결하고, 배너를 누른 다음의 참여 진입과 혜택·남은 시간 표시, 기존 미션과 탐색 화면까지 이어지는 FE를 구현했습니다. 추천 배너에서 안내한 혜택을 사용자가 다음 화면에서도 확인하려면, 여러 화면이 같은 참여의 정보를 읽도록 연결해야 했습니다.

## 배너를 누른 뒤에도 같은 혜택을 설명해야 했다

추천 결과는 없을 수도, 하나일 수도, 둘일 수도 있었습니다. 한 캠페인은 배너로, 여러 캠페인은 카드 선택으로 표현했습니다. 추천을 열고 닫거나 캠페인을 선택할 때는 해당 캠페인 정보도 함께 기록했습니다.

어려운 부분은 카드를 누른 다음이었습니다. 추천을 보고 일반 캠페인 주소로만 이동하면, 도착한 화면은 사용자가 어떤 경로로 들어왔는지 모릅니다. 추가 혜택을 보여줘야 하는 참여와 원래의 참여가 같은 화면에 섞입니다.

추천을 통한 진입에서는 서버에 보너스 참여 문맥을 전달하며 새 참여 식별자를 받아 이동하도록 연결했습니다. 다른 경로의 진입은 기존 동작을 유지했습니다. 도착한 미션 화면은 그 참여의 응답을 읽어 보너스 UI를 선택했습니다.

```text
추천 자격·캠페인 조회
  → 배너 또는 카드 선택
  → 추천 경유임을 담아 새 참여 시작
  → 해당 참여의 혜택·만료 시각 조회
  → 미션 화면과 탐색 목록에서 같은 혜택 표시
```

배너에서 안내한 혜택을 다음 화면에서도 보여주려면 **어떤 참여로 이동했는지** 알아야 했습니다. FE에서 지급 자격을 다시 계산하지 않고, 해당 참여에 대해 서버가 내려준 정보를 다음 화면에서도 사용하도록 했습니다.

## 두 개의 시계를 하나로 만들지 않았다

이 기능에는 시간이 두 가지 있었습니다. 추천을 닫은 뒤 다시 보여주지 않을 시간과, 추천으로 참여한 캠페인의 보너스가 끝날 시간입니다.

닫힘 기록은 참여 식별자에 연결해 하루 동안 추천 재노출을 제한했습니다. 이는 사용자가 거절한 배너를 계속 열지 않기 위한 화면 규칙입니다. 반면 보너스의 남은 시간은 서버가 내려준 만료 시각으로 표시했습니다. 닫힘 기록이 있다는 이유로 혜택을 지급하거나, 배너를 다시 열었다고 혜택 시간을 새로 시작할 수는 없었습니다.

```ts
// 설명용 재구성. 실제 API나 저장 구조를 복사한 코드는 아니다.
const canOpenBanner = !isRecentlyDismissed(entryId);
const remaining = timeUntil(serverBonus.expiresAt);

if (remaining <= 0) {
  refreshParticipation();
}
```

만료 뒤에는 참여 데이터를 다시 읽도록 했습니다. 화면의 카운트다운이 끝난 것과 서버가 적용하는 혜택이 같아야 했기 때문입니다. 안내에는 제한 시간이 끝나면 기본 리워드가 적용된다는 의미도 담았습니다.

추천을 다시 열지 않을 기간은 사용자의 닫기 선택에 따라 로컬에서 관리했습니다. 혜택이 유효한지는 서버의 만료 시각을 따라야 했습니다. 두 시간을 나눠 읽어야 배너를 닫거나 다시 열었을 때 지급 조건이 바뀌지 않습니다.

## 한 화면을 바꾸려다 기존 리워드의 의미도 드러났다

보너스는 새 미션 화면에서만 보이면 충분하지 않았습니다. 사용자는 탐색 목록의 캠페인 카드와 참여 중인 목록, 개별 미션에서도 받을 리워드를 비교합니다. 한곳에는 기본값, 다른 곳에는 추가 혜택이 포함된 값이 보이면 같은 캠페인을 다르게 이해하게 됩니다.

기본 리워드와 보너스가 적용된 리워드를 구별해서 읽도록 표시 모델을 연결했습니다. 미션의 기존 리워드 값도 그 구분에 맞춰 정리했습니다. 두 값이 같을 때는 불필요한 취소선이나 할인처럼 보이는 표현을 만들지 않았습니다.

추천 카드에 새 UI를 추가한 뒤에는 기존 목록과 미션이 읽는 값도 확인했습니다. 서버가 계산한 혜택을 어느 화면에서든 일관되게 설명하려면 기존 표시 모델까지 연결해야 했습니다.

## 실험 조건은 라우터에서 끝나지 않았다

2025년 6월의 후속 수정에서는 게임 영상·일반·추천 화면의 진입 조건을 공용 라우터로 모았습니다. 같은 사용자가 게임 영상 조건과 추천 대상 조건을 동시에 만족할 수 있었습니다. 처음 만든 추천 참여 흐름과는 다른, 화면 진입과 실험 노출의 문제였습니다.

게임 영상 경로를 먼저 고르고, 그다음 추천 대상, 그다음 설정된 경로를 읽도록 순서를 보완했습니다. 현재 경로와 같으면 다시 이동하지 않았고, 이동할 때는 기존 query를 이어 썼습니다.

그런데 올바른 화면에 보냈다고 실험 노출도 맞는 것은 아니었습니다. 도착한 게임 화면에서 대상 구분 없이 추천을 조회하고 보여주던 부분을 함께 수정했습니다. 라우팅과 추천 조회·렌더링이 같은 조건을 이어서 사용해야 했습니다.

리뷰에서는 이미 읽은 context를 다시 조회하는 부분도 지적됐습니다. 저는 먼저 그 context를 공용 라우터에 넘기는 좁은 변경을 택했습니다. 추천 조건을 고치는 작업에 새 네트워크 계층까지 한꺼번에 도입하기보다, 실제로 중복된 조회부터 없애는 선택이었습니다.

## 다음 참여를 평가할 수 있는 제품으로 전달하기

추천은 새 참여 진입, 보너스와 만료 표시, 기존 목록·미션까지 연결됐습니다. 6월의 후속 수정에서는 게임 화면에서 대상 구분 없이 추천 배너가 동작하던 부분을 고치고 배포를 보고했습니다.

이후 제품팀의 추천배너 실험 보고에는 설치당 광고주 과금 이벤트 평균과 구매 건수가 좋아졌고, 추가 리워드 비용에도 수익률을 유지했다는 평가가 담겼습니다. 추천·인센티브·서버·디자인·FE가 함께 만든 팀의 결과입니다. 제가 직접 맡은 부분은 그 전략을 실제 화면과 참여 흐름으로 전달하는 일이었습니다.

배너에서 약속한 혜택은 사용자가 추천 경로로 참여했는지, 그 참여의 보너스가 아직 유효한지에 따라 달라졌습니다. 다음 참여를 권하는 화면을 만들면서, 도착한 화면도 같은 참여의 사실을 설명해야 한다는 기준이 남았습니다.
