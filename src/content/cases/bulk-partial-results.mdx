저장 버튼을 한 번 눌렀는데 일부만 성공했다. 화면이 “실패했습니다”라고만 알려준다면 사용자는 무엇을 고쳐야 할까? 전체를 다시 저장해도 되는지, 이미 끝난 항목이 무엇인지부터 알아야 한다.

광고 소재를 일괄 등록하는 기능을 만들 때 이 문제를 다뤘다. 한 화면에서 여러 광고 항목을 편집하고, 각 항목에는 네이티브·HTML 같은 소재를 함께 둘 수 있었다. 사용자가 하는 일은 한 번의 저장이지만 실제 생성 요청은 소재별로 일어났다.

이 차이 때문에 저장의 성공과 실패를 버튼 하나의 결과로만 표현하기 어려웠다. 일괄 작업은 입력을 한 번에 받는 기능이기도 하지만, **작업이 중간까지 끝났을 때 사용자가 어디서 이어갈지**를 정하는 기능이기도 했다.

## 코드의 의존성을 사용자의 입력 순서로 만들 뻔했다

같은 화면을 만들며 랜딩 URL의 입력 방식도 논의했다. URL은 화면에서는 묶음의 공통 정보처럼 보였지만 데이터에서는 소재가 가진 속성이었다. 소재를 모두 지우면 소재에서 읽어오던 URL도 사라지는 구조였다.

처음에는 소재를 먼저 추가한 뒤 URL을 입력하게 하면 되겠다고 제안했다. 구현의 의존성을 입력 순서로 풀려 한 것이다.

동료는 다른 관점에서 봤다. 사용자는 여러 필드를 자유롭게 입력하는 화면을 보고 있는데, 실제로는 순서를 지켜야 한다면 화면이 보여주는 사용법과 동작이 맞지 않는다는 지적이었다. 이미 입력한 값이 소재 삭제와 함께 사라지는 것도 사용자에게는 예상하기 어려운 일이었다.

그 의견을 받아 소재를 모두 제거해도 입력한 URL이 남도록 수정했다. 코드에서 자연스러운 구조가 화면에서도 자연스러운 것은 아니라는 점이 드러난 협의였다. 사용자의 작업을 데이터 구조에 맞추기보다, 화면이 그 차이를 다뤄야 했다.

## 부분 실패도 사용자가 다시 해석하게 두지 않기

저장 결과에서도 비슷한 질문이 생겼다. 같은 광고 항목의 네이티브 소재는 저장됐지만 HTML 소재는 실패할 수 있었다. 행 전체를 성공이나 실패로 표시하면 소재별로 다른 결과를 표현할 수 없었다.

그래서 저장 오류를 각 소재에 보여주고 성공·실패 상태를 구분하는 표시를 제안했다. 동료들과 방식과 표시 위치를 논의했다. 운영자가 모든 입력을 다시 살피기 전에, 어느 소재의 작업이 남았는지 알 수 있어야 한다고 봤다.

표시만 세분화해서도 끝나지 않았다. 화면이 알려준 결과와 다음 저장 버튼의 동작이 이어져야 했다. 성공한 소재에 다시 생성 요청을 보내는 흐름이라면, 상태를 보여줘도 운영자의 다음 행동은 여전히 불분명하다.

## 표시·저장·목록을 남기는 단위를 나누기

구현에서는 각 소재의 저장 호출에서 오류를 처리했다. 한 호출이 실패해도 그 오류를 해당 소재의 상태에 남기고 다음 소재의 처리를 이어갔다. 성공한 소재에는 저장 완료 상태를 남겼다.

첫 저장이 끝난 뒤 화면에 남길 항목은 아직 저장되지 않은 소재가 있는 묶음이었다. 여기서 성공한 소재를 전부 삭제하고 실패한 소재만 새 목록으로 만드는 방식을 쓴 것은 아니다. 같은 묶음 안에 성공한 소재와 실패한 소재가 함께 남을 수 있었다.

동작을 작은 예로 보면 다음과 같다.

| 첫 저장 이후의 묶음 | 화면에 남기는 것 | 다음 저장에서 처리할 것 |
| --- | --- | --- |
| 두 소재 모두 성공 | 묶음을 남기지 않음 | 없음 |
| 한 소재 성공, 한 소재 실패 | 두 소재가 들어 있는 묶음 | 아직 저장되지 않은 소재 |
| 두 소재 모두 실패 | 두 소재가 들어 있는 묶음 | 두 소재 |

따라서 재시도에서는 묶음이 남아 있다는 사실만으로 그 안의 모든 소재를 다시 저장하면 안 됐다. 개별 소재의 저장 완료 상태를 확인해 이미 성공한 생성 호출은 건너뛰었다. 이 상태는 같은 화면에 남아 있는 저장 결과였다.

소재별 오류 표시와 일부 개별 필드의 비활성화도 저장 상태에 연결했다. 예를 들어 이미 저장된 소재의 이름이나 삭제 버튼을 비활성화하는 것은, 화면에서 아직 수정할 작업과 끝난 작업을 구분하는 처리다. 공통 입력과 개별 소재 입력이 섞인 화면에서는 이런 동작도 각각 살펴야 했다.

이 작업에서 화면의 표시 단위는 소재, 남길 목록의 단위는 묶음, 재시도할 요청의 단위는 미저장 소재였다. 세 단위를 구분해서 보니 부분 실패를 단순한 오류 메시지보다 구체적인 상태로 다룰 수 있었다.

## 입력을 유지하고 남은 소재를 이어서 저장할 수 있게

변경한 화면에서는 소재를 모두 지웠다가 다시 추가해도 공통 입력에 남긴 URL을 새 소재가 이어받는다. 입력을 먼저 했다는 이유로 값을 잃거나, 소재를 만들기 전에는 공통 정보를 편집하지 못하는 순서를 피했다.

저장 뒤에는 모든 소재가 성공한 경우 목록으로 이동하고, 일부가 남으면 그 묶음을 화면에 유지한다. 운영자는 성공·실패 표시를 보고 남은 소재를 수정한 뒤 같은 화면에서 다시 저장할 수 있다. 이미 저장된 소재는 다음 생성 요청에서 건너뛴다.

즉 입력을 잃지 않고 작업을 구성하는 흐름과, 부분 결과를 가진 상태에서 이어서 저장하는 흐름이 생겼다. 일괄 등록의 편의성을 입력 단계뿐 아니라 저장 뒤의 복구 행동까지 연결한 변화였다.

## 저장 결과는 다음 행동의 설계다

돌아보면 이 기능에서 중요했던 것은 화면과 저장 모델 사이의 번역이었다. 소재에 속한 값을 사용자가 편집하는 방식으로 유지하고, 개별 요청의 결과를 이어서 작업할 수 있는 화면으로 돌려주는 일이다.

일괄 작업을 편하게 만드는 것은 입력을 한 번에 받는 데서 끝나지 않는다. 일부가 끝났을 때 그 결과를 읽고 남은 일을 이어갈 수 있어야 한다. 나는 이 작업에서 저장 이후의 상태도 사용자의 작업 흐름이라는 점을 구체적으로 다뤘다.
