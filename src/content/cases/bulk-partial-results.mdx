광고 소재를 일괄 등록하는 화면에서는 여러 광고 항목과 각 항목에 사용할 소재를 한꺼번에 입력했습니다. 소재는 사용자에게 보여줄 광고 내용을 담는 단위입니다. 운영자가 보기에는 입력을 모두 마친 뒤 저장 버튼을 한 번 누르는 작업이었습니다.

그런데 버튼 하나가 실제로는 소재별 생성 요청을 실행했습니다. 예를 들어 같은 광고 항목의 두 소재 중 하나는 저장되고 다른 하나는 실패할 수 있었습니다. 화면이 “실패했습니다”라고만 알려주면, 방금 입력한 것 중 무엇이 끝났는지부터 다시 확인해야 합니다.

그 상태에서 전체를 다시 저장해도 되는지, 실패한 것만 고쳐야 하는지도 불분명합니다. 이미 성공한 소재에도 생성 요청을 다시 보내면 끝난 일을 반복하게 됩니다. 반대로 화면을 비워버리면 아직 저장하지 못한 입력을 다시 구성해야 합니다. 오류 메시지를 보여주는 것만으로는 다음 행동을 정할 수 없었습니다.

사용자가 **일부만 끝난 작업을 같은 화면에서 이어갈 수 있도록** 입력 유지 방식과 저장 결과, 다음 저장의 동작을 함께 정해야 했습니다. 여러 항목을 보내는 기능이 있어도 이 세 가지가 맞지 않으면 무엇을 다시 저장할지 알기 어려웠습니다.

## 코드의 의존성을 사용자의 입력 순서로 만들 뻔했다

저장 전의 입력에서도 같은 차이가 드러났습니다. 화면에서는 묶음을 편집하지만 데이터는 개별 소재에 속해 있었습니다. 랜딩 URL의 입력 방식이 그 예였습니다. URL은 화면에서는 묶음의 공통 정보처럼 보였지만 데이터에서는 소재가 가진 속성이었습니다. 소재를 모두 지우면 소재에서 읽어오던 URL도 사라지는 구조였습니다.

처음에는 소재를 먼저 추가한 뒤 URL을 입력하게 하면 되겠다고 제안했습니다. 구현의 의존성을 입력 순서로 풀려 한 것입니다.

동료는 다른 관점에서 봤습니다. 사용자는 여러 필드를 자유롭게 입력하는 화면을 보고 있는데, 실제로는 순서를 지켜야 한다면 화면이 보여주는 사용법과 동작이 맞지 않는다는 지적이었습니다. 이미 입력한 값이 소재 삭제와 함께 사라지는 것도 사용자에게는 예상하기 어려운 일이었습니다.

그 의견을 받아 소재를 모두 제거해도 입력한 URL이 남도록 수정했습니다. URL이 소재의 속성이라는 이유로 입력 순서를 제한하면 사용자가 화면의 데이터 구조까지 이해해야 했습니다. 입력은 자유롭게 하되 그 값을 유지하는 처리는 화면에서 맡았습니다.

## 부분 실패도 사용자가 다시 해석하게 두지 않기

저장 결과에서도 비슷한 질문이 생겼습니다. 같은 광고 항목의 네이티브 소재는 저장됐지만 HTML 소재는 실패할 수 있었습니다. 행 전체를 성공이나 실패로 표시하면 소재별로 다른 결과를 표현할 수 없었습니다.

그래서 저장 오류를 각 소재에 보여주고 성공·실패 상태를 구분하는 표시를 제안했습니다. 동료들과 방식과 표시 위치를 논의했습니다. 운영자가 모든 입력을 다시 살피기 전에, 어느 소재의 작업이 남았는지 알 수 있어야 한다고 봤습니다.

성공·실패 표시를 나눈 뒤에는 다음 저장도 그 결과를 따라야 했습니다. 성공한 소재에 다시 생성 요청을 보낸다면, 운영자는 상태를 보고도 무엇을 재시도할지 결정하기 어려웠습니다.

## 표시·저장·목록을 남기는 단위를 나누기

구현에서는 각 소재의 저장 호출에서 오류를 처리했습니다. 한 호출이 실패해도 그 오류를 해당 소재의 상태에 남기고 다음 소재의 처리를 이어갔습니다. 성공한 소재에는 저장 완료 상태를 남겼습니다.

첫 저장이 끝난 뒤에는 아직 저장되지 않은 소재가 있는 묶음을 남겼습니다. 한 행은 공통 입력과 여러 소재를 함께 편집하는 단위였으므로, 남은 작업도 그 행에서 이어갔습니다. 결과적으로 성공한 소재와 실패한 소재가 같이 보여도 어떤 묶음에서 무엇이 끝났는지 읽을 수 있었습니다.

동작을 작은 예로 보면 다음과 같습니다.

| 첫 저장 이후의 묶음 | 화면에 남기는 것 | 다음 저장에서 처리할 것 |
| --- | --- | --- |
| 두 소재 모두 성공 | 묶음을 남기지 않음 | 없음 |
| 한 소재 성공, 한 소재 실패 | 두 소재가 들어 있는 묶음 | 아직 저장되지 않은 소재 |
| 두 소재 모두 실패 | 두 소재가 들어 있는 묶음 | 두 소재 |

따라서 재시도에서는 묶음이 남아 있다는 사실만으로 그 안의 모든 소재를 다시 저장하면 안 됐습니다. 개별 소재의 저장 완료 상태를 확인해 이미 성공한 생성 호출은 건너뛰었습니다. 이 상태는 같은 화면에 남아 있는 저장 결과였습니다.

소재별 오류 표시와 일부 개별 필드의 비활성화도 저장 상태에 연결했습니다. 이미 저장된 소재의 이름과 삭제 버튼은 비활성화했고, 남은 소재는 수정해 다시 생성할 수 있게 했습니다. 공통 URL 입력은 화면에 남은 값에 반영되지만, 이미 저장된 소재에는 다음 생성 요청을 보내지 않습니다. 이 화면의 재시도는 남은 소재를 만드는 절차이지 완료한 소재까지 수정하는 명령은 아니었습니다.

소재별 결과를 표시하고, 남은 작업은 묶음 안에서 편집하게 했습니다. 다음 저장에서는 그 묶음의 미저장 소재만 요청하도록 연결했습니다.

## 입력을 유지하고 남은 소재를 이어서 저장할 수 있게

운영자는 소재를 모두 지웠다가 다시 추가해도 이미 입력한 URL을 이어서 쓸 수 있게 됐습니다. 저장이 일부만 끝나도 남은 묶음을 다시 구성할 필요는 없었습니다. 같은 화면의 성공·실패 표시를 보고 미저장 소재를 수정해 다시 저장하며, 이미 성공한 소재의 생성 요청은 건너뜁니다. 일괄 등록은 한 번 보내는 기능에서, 중간까지 끝난 작업을 이어갈 수 있는 화면이 됐습니다.

부분 결과를 나눠 보여주는 제안에는 제품·QA 담당자가 긍정적으로 답했고, 표시 위치도 함께 논의했습니다. 사전 QA 확인 뒤에는 미리 확인한 보람이 있었다는 피드백도 주고받았습니다. 결과 표시와 다음 저장의 행동을 함께 맞춘 협의가 있었습니다.

처음에는 데이터 구조에 맞춰 사용자의 입력 순서를 제한하자고 제안했습니다. 동료의 반론을 듣고 입력한 값을 유지하는 방향으로 바꿨습니다. 오류가 난 소재를 알려주는 데서 멈추지 않고, 끝난 소재는 보존한 채 남은 입력을 고쳐 다시 저장할 수 있도록 해야 사용자의 작업이 이어진다고 생각합니다.
