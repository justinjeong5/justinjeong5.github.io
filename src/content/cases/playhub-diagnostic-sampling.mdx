광고·콘텐츠에 참여해 리워드를 받는 PlayHub에서, 외부 콘텐츠를 열었다 돌아온 뒤 보상 안내가 없어졌는데 예외는 발생하지 않았다. 이런 문제를 읽으려면 오류 하나보다 사용자의 이동, 클라이언트 상태, API 결과, 복귀, 보상 표시를 이어서 봐야 했다. 그래서 상세 진단을 늘렸지만 상태와 버튼을 자주 기록하면서 수집량도 커졌다.

이벤트마다 일정 확률로 버리면 양은 줄어든다. 대신 한 기기의 흐름에서 시작은 남고 완료는 빠지거나 그 반대가 된다. 제품 퍼널까지 같은 방식으로 줄이면 분석의 분모도 변한다. 내가 풀어야 했던 질문은 **조사에 필요한 연결과 제품 지표를 보존하면서 어디를 줄일 것인가**였다.

## 비율을 정하기 전에 이벤트의 목적을 정했다

KPI에 사용하는 analytics와 상세 diagnostic을 이벤트별로 분류했다. 제품 참여를 집계하는 이벤트는 표본 정책 밖에 두고, 상세 상태 진단만 고정된 기기 표본에 적용했다.

처음 분류가 완벽했던 것은 아니다. 자동 수령 성공을 진단으로 분류했다가 실제 소비 KPI의 전수 집계 계약을 확인하고 analytics로 교정했다. 이름에 debug가 붙었는지만 보고 수집 목적을 결정할 수 없었다. 생산하는 코드뿐 아니라 그 이벤트를 어떤 분모로 읽는 소비자가 있는지 확인해야 했다.

정책상 전수 수집한다는 말은 모든 네트워크 전송과 적재 성공을 보장한다는 뜻은 아니다. 여기서 지킨 계약은 클라이언트가 KPI 이벤트를 샘플링으로 제외하지 않는다는 것이었다.

## 2%는 이벤트가 아니라 기기를 고르는 조건이었다

서버가 제공하는 유효한 기기 ID로 고정 bucket을 계산해 2%를 선택했다. 선택된 기기는 관련 진단 흐름을 이어서 보내고, 같은 기기의 다음 이벤트를 새 확률로 다시 뽑지 않는다. 사용자·세션을 무작위로 2% 선택한 것도 아니었다.

설명용 의사코드이며 실제 회사 코드가 아니다.

```ts
function baseCollection(purpose, deviceId) {
  if (purpose === "analytics") return true;
  if (!validDeviceId(deviceId)) return false;
  return deviceId % 100 < 2;
}
```

고정 표본은 선택된 기기의 이벤트 사이를 의도적으로 끊지 않는 선택이다. 모든 문제 기기가 포함되거나 모든 메시지가 도착하는 보장은 없다. 이 한계 때문에 이후 특정 조사 대상을 추가하는 경로가 필요했다.

## 많이 나오는 원시 상태는 전환 요약과 연결했다

상태나 버튼 값을 자주 남기는 raw 이벤트를 줄이면 작은 전환을 놓칠 수 있었다. 전환 지점의 compact 이벤트를 만들고, raw와 같은 전환 ID·발생 시각·계약 버전으로 연결한 뒤 raw만 표본으로 전환했다.

요약을 새 이름으로 보내는 것으로 끝내지 않았다. 같은 전환을 두 표현으로 대조할 수 있어야 raw를 줄인 뒤에도 해석이 이어졌다. 이는 진단과 분석을 분류하는 일과 별개의 계약이었다. 무엇을 수집할지와 수집한 이벤트끼리 어떻게 이어 읽을지를 함께 다뤘다.

## 표본 밖 문의를 조사할 때는 판정 지연도 상태였다

고정 표본 밖에서 문의가 들어올 수 있었다. 조사·내부 검증 대상을 기능 플래그로 추가 수집하도록 확장했다. 문제는 대상 판정이 첫 행동보다 늦게 도착할 수 있다는 점이었다.

표본 밖 진단은 판정 대기 중 발생 시각과 순번을 붙여 제한된 버퍼에 보관했다. 대상이면 보관분을 보내고, 비대상이면 비웠다. 먼저 발생한 항목을 상한까지 보관하고 이후 유실 수를 기록했다. KPI 이벤트와 기본 표본 안의 진단은 이 판정을 기다리지 않았다.

| 조건 | 기대 결과 |
| --- | --- |
| analytics, 대상 판정 대기 | 지연 없이 전송 경로 진행 |
| 기본 표본 안 diagnostic | 추가 대상 판정을 기다리지 않음 |
| 표본 밖 diagnostic, 판정 대기→활성 | 보관한 순서·발생 시각으로 전송 |
| 표본 밖 diagnostic, 판정 대기→비활성 | 보관분 폐기 |
| 상한 100인 버퍼에 102개 입력 후 활성 | 100개 전송, 초과 2개를 유실 수로 표시 |

마지막 행의 숫자는 회귀 테스트 입력과 기대 결과다. 실제 문의 수나 개선 성과가 아니다. 이 버퍼는 영속 큐가 아니므로 페이지 종료까지 무한히 보존한다고 볼 수도 없다.

## 적재를 나누는 일은 클라이언트 혼자 끝낼 수 없었다

클라이언트는 기존 전송 API와 이벤트 계약을 유지했다. 이후 일반 분석이 상세 진단까지 스캔하는 부담을 줄이기 위해 데이터 플랫폼팀과 전용 적재·조회 분리를 협의했다. 나는 진단 type 규칙, 보관주기, 기존 계약 보존과 조회 이관을 제안했다. 데이터 플랫폼팀은 적재·뷰·백필·정합성 확인을 맡았다.

나는 관리하던 조회의 소스를 전환하고 다른 조회의 사용 여부를 소유자에게 확인해 교체·정리를 마쳤다. 전송량을 줄이는 클라이언트 변경과 데이터를 어디에 저장하고 어떤 분석이 읽는지는 서로 다른 작업이었다.

## 줄인 양과 남긴 의미

적용 후 데이터 플랫폼 담당자는 당시 실측에서 debug 이벤트가 약 86%, BI 전체 throughput이 약 54% 감소했다고 보고했다. 2%라는 설정에서 역산한 수치가 아니라 담당자의 적용 후 수집량 보고였다. 청구 비용 절감률은 아니다.

팀 동료는 로그가 없었으면 디버깅하기 어려웠을 것이라고 반응했다. 고정 표본으로 선택된 기기의 흐름을 이어 읽을 수 있게 했지만, 표본 밖 문의까지 처음부터 모두 기록하는 방식은 포기했다. 추가 조사 대상의 판정이 늦는 동안은 제한된 버퍼로 보완하고 상한을 넘긴 유실은 남겼다. 가장 크게 바뀐 판단은 샘플링 비율보다 이벤트의 소비 목적을 먼저 확인하는 것이었다. 자동 수령 성공을 KPI로 다시 분류한 일이 그 기준을 실제로 바꾼 장면이었다.
