콘텐츠 카드가 여러 개 놓인 화면은 익숙하다. 카드를 누르면 콘텐츠를 열고, 돌아오면 다른 카드를 고르면 될 것 같다. 하지만 광고와 미션에 참여하고 리워드를 받는 허브에서는 카드가 보인다는 사실만으로 사용자가 할 수 있는 일이 정해지지 않았다.

어떤 콘텐츠는 이미 참여를 끝냈고, 다른 콘텐츠는 지금 참여할 수 없었다. 외부 페이지를 다녀온 뒤에는 진행 상태가 바뀔 수 있었고, 요청이 성공한 뒤에도 사용자가 리워드 결과를 알아볼 화면이 필요했다. 목록을 잘 그리는 것과 **참여가 끝나고 다음 행동으로 이어지는 제품을 만드는 것**은 다른 문제였다.

PlayHub는 파트너 앱에서 광고·콘텐츠·미션에 참여하고 리워드를 받는 서비스다. 나는 기존 미션과 공용 기능 위에 초기 허브의 핵심 프론트엔드를 구축하고, 이후 반복 참여 제품의 메인·광고 흐름과 여러 출시의 후속 작업을 맡았다. 이 글은 새 제품의 책임과 기존 기반의 계약을 어떻게 연결했는지에 관한 이야기다.

## 처음 만든 것은 카드보다 상태를 연결하는 화면이었다

초기 허브에는 메뉴뿐 아니라 튜토리얼, 미션 진행과 완료, 랜덤박스, 프로모션, 리워드 안내가 함께 있었다. 기존 미션과 콘텐츠를 전부 다시 구현하는 것은 아니었다. 새로운 허브가 그 기능을 어떤 순서로 소개하고 이어 줄지를 만들어야 했다.

나는 콘텐츠별 상태와 광고 조회를 연결해 메뉴의 참여 가능 여부와 완료 표시를 계산했다. 콘텐츠를 열고 돌아오면 서버 상태를 다시 읽어 진행과 다음 안내를 갱신했다. 화면 안의 선택에서 외부 이동, 복귀, 상태 확인까지를 하나의 사용자 작업으로 봤다.

여기서 완료를 어디에 기록할지도 중요했다. 서버 참여 결과와 화면에서 잠깐 유지할 표시, 매체별로 보관하던 완료 상태는 서로 다른 의미와 수명을 가졌다. 로컬에서 버튼을 비활성화했다고 서버 참여가 완료된 것은 아니며, 서버에 완료가 남았다고 복귀 안내까지 전달된 것도 아니었다.

| 화면이 답할 질문 | 연결한 정보와 동작 |
| --- | --- |
| 지금 어떤 콘텐츠를 열 수 있는가? | 콘텐츠 상태와 광고 조회로 메뉴의 가능·완료 상태 표현 |
| 외부 콘텐츠에서 돌아오면 무엇이 달라지는가? | 이동과 복귀를 연결하고 서버 상태 재조회 |
| 사용자가 리워드 결과를 알아볼 수 있는가? | 성공한 요청의 결과와 오버레이 표시 연결 |
| 안내를 닫은 뒤에는 무엇을 제안할 것인가? | 참여 가능·완료·닫힘을 읽어 다음 단계 선택 |

서버는 참여와 지급 정책을, 제품과 디자인 담당자는 상품의 규칙과 표현을 함께 정했다. 나는 그 계약을 소비하는 핵심 FE를 만들고 실제 행동으로 연결했다. 기존 공용 기반의 재사용과 새 허브 전용 구현이 같은 작업 안에 있었다.

화면이 어떤 판단을 맡았는지 정리하면 다음과 같다. 실제 모듈 이름이나 고정된 호출 순서가 아니라 이 글에서 설명하는 책임 관계다.

```text
서버: 참여 상태·지급 정책
핵심 FE
  ├─ 상태: 참여 가능·완료·다음 행동
  ├─ 실행: 광고·완료 확인·외부 복귀
  └─ 결과: 끝난 요청의 결과 보관·표시

함께 맞출 계약
  제품·디자인: 상품 규칙·표현
  매체·동료: 진입점·문의·후속 통합
```

## 다시 조회할 정보와 이미 끝난 결과를 다르게 다뤘다

참여 뒤에는 상태를 다시 조회해야 한다. 그렇다고 화면의 모든 정보를 새 조회 결과에서만 도출하면, 방금 성공한 작업의 결과까지 사라질 수 있었다.

랜덤박스의 성공 안내를 표시하는 동안 광고 데이터가 바뀌더라도 그 안내가 현재 광고의 유무에 매달려서는 안 된다. 사용자가 확인하는 것은 새 광고가 아니라 조금 전 작업의 결과다. 초기 구현에서는 요청이 끝난 성공·오류 정보를 오버레이가 사용할 수 있게 남겨 조회 데이터의 변경과 결과 안내를 구분했다.

이 질문은 나중의 [외부 복귀 뒤 리워드 안내](/cases/playhub-reward-reveal/)에서도 다시 중요해졌다. 그때는 웹 문서가 교체돼도 아직 표시하지 않은 성공을 이어 보여줘야 했다. 초기 오버레이의 결과 보관과 후속 문서 간 재생은 같은 구현이 아니지만, 현재 조회 상태와 끝난 작업의 결과를 구별한다는 질문은 연결된다.

## 반복 참여로 확장할 때는 공통화할 기준이 바뀌었다

허브 다음에는 광고 참여, 미션 진행, 복권, 리워드 수령, 다음 회차 대기로 이어지는 흐름을 다뤘다. 앱 안에서 끝나는 참여와 외부 화면을 거쳐 복귀하는 참여도 연결해야 했다.

광고 흐름을 화면별로 복제하는 방법과 공통 흐름에 실행 전략을 주입하는 방법을 비교했다. 복제하면 앱과 외부 웹을 빠르게 분리할 수 있지만 후보 순회·추적·빈 광고·실패 처리가 따로 바뀔 수 있었다. 공통 흐름을 택하면 환경마다 광고를 열고 완료를 확인하는 방법을 연결해야 했다. 나는 같은 서버 상태에서 다음 행동을 계산하는 규칙과 후보 순회를 공유하고, 실행 환경의 차이는 남겼다. [두 참여 화면의 상태 규칙](/cases/playhub-product-flow/)에서는 정각을 넘긴 보상 상태가 이 구분을 어떻게 요구했는지 설명한다.

광고 실행에서도 후보를 순회하는 책임과 공급사별 표시 처리를 분리했다. 나는 공용 SDK 어댑터와 실행 기반 일부를 먼저 개발했고 후속 제품에서 재사용했다. 닫힘만 온 경우와 시청 완료 뒤 닫힘이 온 경우를 같은 완료로 읽지 않았다. 공용 실행을 유지하면서도 환경마다 완료를 확인하는 방법은 남겨 둬야 했다.

독립 제품 구성과 후속 통합은 동료와 함께 진행됐다. 서버 상태·앱 진입점·디자인·영상·문의 화면 같은 기여가 합쳐졌다. 공통 규칙을 추출한 일과 모든 소비자가 새 실행을 선택한 일도 구분했다. 코드가 있다는 이유만으로 모든 매체에서 그 경로가 활성화됐다고 판단하지 않았다.

## QA에서는 화면 문제와 참여 조건을 먼저 나눴다

초기 QA에서 같은 화면이라도 참여 이력과 서버의 광고 할당 조건에 따라 다른 결과가 나왔다. 화면만 고치면 될 문제인지, 해당 사용자에게 콘텐츠가 제공되는 조건을 다시 확인해야 하는지부터 나눠야 했다.

나는 제품·디자인 담당자에게 QA를 요청하고 서버 이력과 할당 조건을 화면의 재현 조건과 연결했다. 일부 이슈는 수정으로 닫았고, 일부는 담당자들과 설정이나 진입 제한, 알려진 이슈를 포함한 출시 범위를 맞췄다. 모든 항목을 동일한 수준의 화면 버그로 취급하지 않았다.

화면의 클릭·표시, 서버가 반환할 상태, 매체의 진입 경로는 같은 작업의 서로 다른 확인 지점이었다. 후속 반복 참여 개발에서는 흐름 문서를 작성했고, 그 문서는 팀의 QA 체크리스트를 준비하는 자료로 다시 요청됐다.

## 출시 버튼보다 먼저 확인한 것은 의존성과 진입점이었다

초기 상용 전달에서는 설정·서버·FE의 반영 순서를 설명하고 서버 완료 뒤 FE 배포를 이어 갔다. 실제 매체 진입을 확인했고 제품 담당자도 상용 참여를 확인했다. 내가 놓쳤던 리뷰 시간을 다시 확보하려고 동료에게 리뷰를 요청한 과정도 있었다. 구현 완료와 전달 준비를 같은 말로 쓰기 어려웠던 이유다.

후속 상품을 교체할 때는 사전 배포하고 기능 플래그를 켜면 될 것처럼 보였다. 하지만 코드를 확인하니 새 진입점이 기존 상품의 진입점을 대체했다. 사전 배포와 공개를 독립적으로 취급하면 매체가 아직 준비하지 않은 진입점을 먼저 바꿀 수 있었다.

나는 그 의존성을 설명하고 매체의 준비와 배포 시간을 맞추는 방향으로 계획을 바꿨다. 공개 플래그가 무엇을 숨기는지와 배포가 어떤 진입점을 바꾸는지는 별개의 질문이었다. 완료 뒤에는 제품 담당자의 실제 참여·문구 확인과 동료의 후속 수정이 이어졌다.

## 사용자가 참여할 수 있는 제품으로 전달하기

초기 허브는 목록과 안내를 개발한 데서 멈추지 않고 실제 매체의 진입과 상용 참여 확인까지 이어졌다. 이후 같은 기반에서 반복 참여 제품과 후속 매체 전달을 진행했다. 기능을 쌓는 동안 FE의 책임도 목록 표시에서 상태 해석, 외부 복귀, 광고 실행, 결과 안내, QA와 출시 의존성으로 넓어졌다.

이 경험에서 바뀐 기준은 제품의 완성을 화면 수로 세지 않는다는 것이다. 지금 할 수 있는 행동을 알 수 있는지, 이동했다 돌아온 뒤에도 작업이 이어지는지, 다음 담당자가 확인할 조건이 남아 있는지가 더 유용한 기준이었다. 그 기준으로 초기 제품을 전달하고 후속 참여 흐름을 확장해 간 것이 내가 맡은 개발이었다.
