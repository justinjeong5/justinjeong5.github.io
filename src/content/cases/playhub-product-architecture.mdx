콘텐츠를 고르고, 광고를 보고, 미션을 끝내고, 리워드를 확인한 뒤 다음 참여로 넘어갑니다. 사용자가 보기에는 한 흐름이지만, 개발할 때는 서버 상태와 광고 SDK, 앱 안의 화면과 외부 웹이 서로 다른 시점에 결과를 알려줍니다. 화면을 각각 완성하는 것만으로는 이 흐름을 끝낼 수 없었습니다.

PlayHub는 파트너 앱에서 광고·콘텐츠·미션에 참여하고 리워드를 받는 서비스입니다. 저는 기존 미션과 공용 기능 위에 초기 허브의 핵심 FE를 구축하고, 이후 반복 참여 제품의 메인·광고 흐름과 공유 상태를 개발했습니다. 서버는 참여·지급 정책을, 제품과 디자인은 상품 규칙과 표현을 함께 정했습니다.

초기 제품을 만든 뒤 실제 참여를 연결하며 공통 규칙을 추출했습니다. 후속 제품의 정각 QA에서는 현재 미션이 끝나지 않아도 이전 시간대의 미수령 리워드가 남는 조건을 만났습니다. 그 조건은 앱과 웹이 같은 서버 상태를 읽더라도 안내와 실행을 각각 판단해야 한다는 문제를 드러냈습니다.

## 카드보다 먼저 다음 행동을 연결했다

초기 허브에는 메뉴뿐 아니라 튜토리얼, 미션 진행과 완료, 랜덤박스와 리워드 안내가 있었습니다. 기존 기능을 모두 다시 만드는 대신 새 허브가 어떤 순서로 소개하고 이어 줄지를 정해야 했습니다.

콘텐츠 상태와 광고 조회를 연결해 참여 가능 여부와 완료 표시를 계산했습니다. 외부 콘텐츠에서 돌아오면 서버 상태를 다시 읽고, 미완료·유효 상태인 다음 안내를 골랐습니다. 지금 조회가 준비되지 않았다면 다음 행동도 성급히 확정하지 않았습니다.

반대로 이미 끝난 작업의 결과는 새 조회의 수명과 분리했습니다. 랜덤박스 성공 안내를 보여주는 동안 광고 데이터가 바뀌었다고 그 안내까지 사라져서는 안 됩니다. 사용자가 확인하는 것은 새 광고가 아니라 조금 전 작업의 결과입니다. 성공·오류 상태의 안내는 저장한 결과를 사용하고, 현재 콘텐츠의 제공 여부만으로 닫히지 않게 했습니다.

```text
서버 상태 → 지금 참여할 수 있는 것과 다음 행동
광고 실행 → 이동·완료·복귀를 확인하는 방법
끝난 작업의 결과 → 사용자에게 아직 보여줄 안내
```

위 흐름은 실제 모듈 이름 대신 각 부분이 하는 일을 설명한 것입니다. 다음 참여를 위해 읽는 최신 상태와 방금 끝난 참여의 결과는 따로 유지해야 했습니다. 새 조회 결과에 안내를 종속시키면 재조회가 사용자가 아직 확인하지 못한 결과를 지울 수 있었기 때문입니다.

## 작은 동작을 연결한 뒤 공유할 규칙을 추출했다

처음부터 두 환경의 화면과 광고를 한 번에 묶지는 않았습니다. API와 상태 규칙을 먼저 만들고, 초기 앱 화면에서 버튼을 누른 뒤 요청·리워드 안내·재조회로 이어지는 흐름을 연결했습니다. 외부 웹을 붙이면서 진행·영상·버튼의 공통 규칙을 공유 위치로 옮겼습니다.

앱에서는 바로 처리할 수 있는 일도 외부 웹에서는 앱으로 돌아온 뒤 처리해야 했습니다. 같은 상태를 읽는 부분은 공유하되, 그 상태를 바꾸는 실행과 복귀 처리는 남겼습니다. 실제 광고와 복권, 동료의 디자인, QA 조건은 후속 단계에서 통합했습니다.

```text
API·상태 규칙
  → 초기 앱의 버튼·요청·안내·재조회
  → 외부 웹 연결과 공통 규칙 추출
  → 실제 광고·복권·디자인 통합
  → 참여 조건 QA와 매체 출시
```

두 화면의 공통 구조를 먼저 만들기보다 실제 실행을 연결한 뒤, 같은 입력에서 같은 행동을 계산하는 부분을 공유했습니다. 다음 기능을 붙일 때도 이 기준을 유지해 환경마다 다른 완료 신호는 별도로 남겼습니다.

## 같은 금액처럼 보여도 같은 상태는 아니었다

반복 참여 제품에서는 광고 참여, 미션 진행, 복권, 리워드 수령, 다음 회차 대기가 연결됐습니다. 앱 안의 화면과 외부 웹의 참여 화면도 함께 다뤘습니다.

겉모양이 달라도 같은 서버 응답에서 사용자가 할 수 있는 행동은 일치해야 했습니다. 그래서 진행 수와 완료 여부, 카운터·버튼·대기 상태를 도출하는 공통 층을 만들었습니다. 진행 수는 전체 범위 안에서 읽고, 전체가 양수일 때만 완료로 판단했습니다. 빈 목록에서 수치만 비교해 완료를 만들어서는 안 됐습니다.

금액도 하나로 취급할 수 없었습니다. 이전 시간대의 미수령분, 현재 수령 가능분, 현재 시간대에 지급된 값은 다른 의미였습니다. 외부 웹의 카운터는 앱에서 받을 보상을, 인앱의 카운터는 이미 받은 보상을 설명할 수 있었습니다.

이 차이는 정각 QA에서 드러났습니다. 이전 시간대에 일부 참여한 사용자가 새 시간대로 넘어왔고, 받을 보상이 남아 있었습니다. 현재 미션은 아직 끝나지 않았다는 이유로 복귀 수령 안내가 뜨지 않았습니다. 서버 담당자가 상태를 설명했고, 저는 기존 안내가 전체 미션 완료를 전제로 읽고 있음을 짚었습니다.

이전 보상이 있으면 현재 미션 완료와 무관하게 안내하도록 고쳤습니다. 보상 상태를 도출하는 함수와 팝업을 띄울지 판단하는 함수도 나눴습니다. 팝업에는 표시 지연과 문서 가시성, 복귀 경로의 조건이 추가되기 때문입니다.

아래는 핵심 조건을 줄인 설명용 코드입니다.

```ts
function needsReturnGuide(state) {
  if (positiveFinite(state.previousReward)) return true;
  return state.currentCycleComplete
    && positiveFinite(state.currentReward);
}
```

버튼의 동작과 팝업의 표시를 무조건 같은 조건으로 결정하지는 않았습니다. 버튼은 참여 정책을 따르고, 팝업은 필요한 안내를 보여줍니다. 다만 둘 다 '이전 보상이 있는데 현재 미션은 미완료'라는 상태를 놓쳐서는 안 됐습니다. 수정 후 같은 조건에서 동료들이 정상 노출을 확인했고, 해당 규칙과 이를 사용하는 코드가 함께 제품에 통합됐습니다.

## 공유할 것은 화면이 아니라 규칙과 실행의 책임이었다

광고 흐름은 화면별로 복제하는 방법과 공통 흐름에 실행 전략을 주입하는 방법을 비교했습니다. 복제하면 앱과 웹을 빨리 분리할 수 있지만 후보 순회·추적·빈 광고·실패 처리가 따로 바뀔 수 있습니다. 공통 흐름을 택하면 기존 동작을 유지하면서 환경별 실행을 연결할 비용이 생깁니다.

같은 서버 상태를 읽는 규칙과 후보 순회는 공유하고, 광고를 여는 방법과 완료를 확인하는 환경 차이는 남겼습니다. SDK의 완료 신호와 외부 이동 후 복귀는 같은 사건이 아니었습니다. 닫힘만 온 경우와 공급사의 완료 조건을 충족한 뒤 닫힘이 온 경우도 다르게 읽었습니다.

앱과 웹이 같은 함수를 사용하더라도 한쪽은 SDK 신호를 읽고 다른 쪽은 외부 복귀를 확인했습니다. 둘을 같은 완료로 처리하면 코드가 줄어도 실제 참여를 잘못 판단할 수 있었습니다. 이 선택을 돌아보면 공통화할 때는 코드가 얼마나 닮았는지와 함께, 같은 사실을 읽고 완료를 판단하는지부터 봐야 한다고 생각합니다.

환경별 실행 로직을 구현하는 것과 각 제품에서 해당 모드를 사용하는 것은 다른 단계였습니다. 상품·매체의 조건에 따라 외부 복귀 경로가 남았고, 공통 코드를 만들었다고 모든 광고가 인앱에서 끝나게 된 것은 아니었습니다. 버튼의 참여 요청을 연결하는 단계와 실제 SDK 광고를 실행하는 단계도 나눴습니다.

## Promise의 성공과 제품의 성공을 나누었다

참여 요청의 409는 화면 상태와 서버의 현재 상태가 충돌한 결과로 반환해 재조회하도록 했습니다. 다른 기술 오류는 원래 오류로 던졌습니다. 모든 실패를 같은 토스트와 재시도에 넣으면 현재 상태를 확인할 상황과 요청 자체가 실패한 상황이 섞입니다.

비동기 라이브러리의 성공 콜백도 지급 성공의 근거로 쓰지 않았습니다. Promise가 resolve되는 결과 안에 상태 충돌이 들어올 수 있었기 때문입니다. 리워드 연출은 반환된 성공 여부와 데이터를 보고 열고, 충돌이면 재조회 후 연출 없이 종료했습니다.

| 확인한 조건 | 화면의 판단 |
| --- | --- |
| 이전 보상 있음, 새 시간대 미완료 | 복귀 수령 안내 |
| 이전 보상 없음, 현재 일부 참여 | 완료 안내를 앞당기지 않음 |
| 참여 요청 409 | 재조회, 성공 연출 생략 |
| 요청의 기술 오류 | 원래 오류 전달 |

같은 화면의 클릭 잠금으로 중복 실행을 줄였지만, 서버 지급의 멱등성을 대신하지는 않았습니다. 상태 규칙의 단위 테스트로 화면의 판단을 검증하고, 실제 참여 QA에서는 실행과 결과가 이어지는지 별도로 확인했습니다.

## 출시에서는 코드보다 먼저 바뀌는 진입점이 있었다

QA에서는 참여 이력과 서버의 광고 할당 조건을 재현 조건으로 함께 맞췄습니다. 일부는 FE 수정으로 닫고, 일부는 설정·진입 제한·알려진 이슈를 담당자들과 출시 범위에 넣었습니다. 화면이 같다는 이유로 모든 관찰을 같은 버그로 읽지 않았습니다.

초기 상용 전달에서는 설정·서버·FE의 반영 순서를 설명하고 서버 완료 뒤 FE 배포를 이어 갔습니다. 실제 매체 진입과 제품 담당자의 상용 참여 확인까지 연결했습니다.

후속 상품 교체에서는 사전 배포 후 공개 플래그를 켜는 계획을 다시 봤습니다. 새 진입점이 기존 상품의 진입점을 대체했기 때문입니다. 화면을 숨기는 플래그가 매체의 진입 경로 변경까지 숨겨 주지는 않았습니다. 그 의존성을 설명하고 매체 준비와 배포 시간을 맞추는 방향으로 계획을 바꿨습니다.

## 사용자에게 남는 제품으로 전달하기

정각 QA에서 미수령 리워드 안내를 고치고, 후속 상품의 진입점 교체에서는 매체 준비와 배포 시점을 맞췄습니다. 8월 보너스 기능에서는 참여 전에 혜택을 알 수 있도록 서버 상태 응답에 적용 여부를 요청했습니다. 광고 실행 중에는 같은 세션의 요청을 공유하되 취소 뒤에는 다시 시작할 수 있게 나눴고, SDK 완료와 서버의 시청 인정·리워드 결과도 별도로 처리했습니다. 문의를 제출한 뒤에는 상태를 다시 읽어 인정 여부를 확인했습니다.
