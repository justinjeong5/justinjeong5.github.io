채팅창에 메시지를 보낸 뒤 화면을 갱신하는 방법은 두 가지였습니다. 요청의 응답으로 방 전체를 다시 받거나, 서버가 전달하는 새 메시지를 현재 목록에 더할 수 있습니다. 개인 채팅 앱의 첫 변경에서는 REST 전송 뒤 받은 방 상태로 교체하던 경로를 Socket.IO 메시지 전송과 수신 이벤트로 바꿨습니다.

## 새 메시지는 현재 목록에 더했다

[메시지·연결 변경 PR](https://github.com/justinjeong5/j-chat/pull/23)에서는 메시지를 보낼 때 Socket.IO 이벤트를 사용하고, `returnMessage` 이벤트에서 전달된 메시지를 목록에 더하도록 했습니다. 이전 화면 코드는 방 상태가 바뀔 때마다 수신 구독을 다시 등록했습니다. 변경 뒤에는 화면이 열릴 때 구독하고, 이벤트가 오면 `setChatRoom(prev => ...)`로 그 시점의 목록에 메시지를 더합니다.

이 선택은 현재 상태를 닫힌 함수 안에 오래 붙잡아 두지 않으려는 것이었습니다. PR의 diff는 전송과 수신 상태의 연결이 바뀐 사실을 보여주지만, 모든 네트워크 끊김이나 중복 전달까지 해결했다는 증거는 아닙니다.

## 방을 떠나도 연결의 일은 남는다

[방 입퇴장 PR](https://github.com/justinjeong5/j-chat/pull/24)에서는 사용자가 들어갈 수 있는 방 목록과 입장·퇴장 UI를 더했습니다. 퇴장은 membership API 호출, 목록으로의 이동, `leaveRoom` 이벤트를 연결했습니다. 채팅 화면을 떠날 때는 소켓 연결을 끊는 정리 함수도 넣었습니다.

화면에서 방을 떠나는 것, 서버의 방 소속을 바꾸는 것, 실시간 연결을 정리하는 것은 서로 다른 동작입니다. PR에서 이 경로를 연결한 것은 확인되지만, 당시 실제 사용자의 재접속 경험이나 장기간 운영 결과는 이 기록에 없습니다.

두 PR은 병합됐습니다. 이 개인 프로젝트에서 남길 수 있는 결과는 메시지를 이벤트로 받고 현재 목록에 반영하는 코드, 방 입퇴장 UI, 페이지를 떠날 때의 연결 정리입니다. [최신 요청의 결과와 정리](/cases/latest-request-boundaries)는 다른 업무 경험이지만, 새 상태를 적용하는 코드와 이전 작업을 끝내는 코드가 함께 필요하다는 질문으로 이어집니다.
