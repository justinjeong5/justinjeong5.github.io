코딩 도구의 계정을 바꿨는데 메뉴바에는 이전 계정의 사용 한도가 남아 있다면, 사용자는 어느 숫자를 믿어야 할까요? 조회 자체는 성공했으니 오류 메시지도 없습니다. 숫자가 자연스럽게 갱신되고 있다는 점이 오히려 문제를 알아보기 어렵게 만듭니다.

[PokeTokenBar](https://github.com/chattymin/PokeTokenBar)는 AI 코딩 도구의 사용량을 보여주는 macOS 메뉴바 앱입니다. 저는 Antigravity의 사용 한도 조회를 연결한 뒤, 토큰 파일과 캐시를 다루는 코드를 보완했습니다. Swift 구현에는 AI의 도움을 받았고, 두 변경을 PR로 제안해 유지보수자와 리뷰를 주고받았습니다.

이 기여에서 중요한 판단은 API 값을 화면에 표시한 뒤에 나왔습니다. **아직 유효한 캐시라도, 지금 선택한 계정의 값인가?** 만료 시간만 보고 캐시를 고르면 계정을 바꾼 뒤에도 이전 사용 한도를 보여줄 수 있었습니다.

## 한도 조회를 기존 앱의 갱신 흐름에 연결하기

사용량과 사용 한도는 다른 정보였습니다. 로컬 기록에서 오늘 얼마나 썼는지 알 수 있어도, 계정에 남은 한도와 초기화 시각까지 계산할 수는 없었습니다.

새 provider의 API 응답에서 모델군·한도 구간·남은 비율·초기화 시각을 읽어 `UsageStore`의 갱신 흐름과 메뉴·팝오버 화면에 연결했습니다. 일부 값을 읽는 함수에서 끝내지 않고, 기존 도구의 한도와 함께 볼 수 있도록 했습니다.

주기적 백그라운드 갱신에서 암호 입력이 반복되면 메뉴바 앱의 목적과 어긋납니다. 기존 자동·수동 갱신 정책을 유지하며 파일의 토큰을 쓸 수 있는 경로를 보완했습니다. 수동 갱신의 인증 경로까지 없앤 것은 아닙니다.

## 유효기간만으로는 캐시를 고를 수 없었다

외부 도구의 토큰 파일은 값이 토큰 객체 안에 있거나 최상위에 있는 등 형식이 달랐습니다. 계정을 바꾸면 같은 경로의 토큰도 바뀔 수 있었습니다. 여러 형식을 읽되 파일을 메모리 캐시보다 먼저 확인하는 기존 순서를 유지했습니다.

문제는 파일을 읽은 **뒤** 어느 토큰을 쓸지 결정하는 조건이었습니다. 캐시가 유효하다는 이유만으로 반환하면 파일에 반영된 계정 전환을 놓칩니다. 반대로 갱신된 캐시가 있는데 파일에는 만료된 옛 access token이 남아 있다면, 파일만 우선해서도 안 됩니다.

처음에는 만료된 파일보다 유효한 캐시를 유지했습니다. 같은 계정에서는 필요한 동작이었지만, **캐시의 유효기간과 캐시의 출처는 다른 조건**이었습니다.

## 리뷰에서 계정 전환의 반례가 나왔다

유지보수자가 다음 순서의 문제를 재현했습니다.

```text
A 계정으로 조회해 유효한 캐시를 만든다
  → 파일을 만료 임박한 B 계정의 토큰으로 바꾼다
  → 다시 조회한다
  → 유효한 A의 캐시가 반환된다
```

캐시를 오래 보관한 문제가 아니라, 파일과 캐시가 서로 다른 자격 증명 출처인데 유효기간만으로 하나를 고른 문제였습니다.

이 반례를 받아 **갱신된 캐시를 유지할 때 파일과 같은 자격 증명 출처인지 확인**하도록 바꿨습니다. access token이 같거나 비어 있지 않은 refresh token이 같을 때만 같은 출처로 취급했습니다. 갱신 과정에서 access token은 달라질 수 있어 access token만 비교해서는 부족했습니다.

의미를 줄여 쓰면 다음과 같습니다. 실제 코드의 토큰 값 대신 조건만 남겼습니다.

```swift
if cacheIsValid && fileTokenIsExpired && sameCredentialSource {
    return cachedToken
}
return try await resolveTokenFromFile()
```

이 조건은 토큰을 비교하는 구현상의 기준이지, 별도의 사용자 ID로 계정 전체를 검증하는 절차는 아닙니다. 다만 이전 계정의 캐시를 새 계정 파일보다 먼저 고르는 반례는 이 기준으로 구별할 수 있었습니다.

## 두 방향의 실패를 같은 테스트 경계에 두기

파일 형식을 읽는 테스트만으로는 계정 전환 문제를 잡을 수 없었습니다. 같은 경로의 파일을 두 번 읽되 그 사이에 계정과 유효기간이 바뀌는 순서가 필요했습니다.

테스트에서는 A 계정으로 캐시를 만든 뒤 B 계정 파일로 교체해 이전 캐시가 반환되지 않는 조건을 남겼습니다. 토큰 갱신에는 `URLSession`을 주입하고 mock HTTP 응답으로 새 토큰을 받은 다음, 후속 조회에서도 갱신한 캐시를 유지하는 흐름을 확인하도록 했습니다.

두 검사는 서로 반대 방향을 지켰습니다. **계정이 바뀌면 이전 캐시를 버리고, 같은 출처의 토큰이 갱신되면 새 캐시를 살려야 했습니다.** 한쪽만 고치면 다른 쪽을 다시 깨뜨릴 수 있었습니다.

리뷰 중에는 설명도 좁혔습니다. 자동 갱신에서 인증창을 피하는 것과 모든 경로에서 사용자 개입이 사라지는 것은 다릅니다.

## 공개 버전으로 전달하고 남은 기준

새 한도 기능은 [#210](https://github.com/chattymin/PokeTokenBar/pull/210), 파일 형식과 갱신·계정 전환 보완은 [#274](https://github.com/chattymin/PokeTokenBar/pull/274)로 병합됐습니다. 각각 [v2.5.2](https://github.com/chattymin/PokeTokenBar/releases/tag/v2.5.2)와 [v2.5.4](https://github.com/chattymin/PokeTokenBar/releases/tag/v2.5.4)의 공개 버전에 포함됐습니다. 기존 앱에서 새 도구의 한도를 확인할 수 있게 했고, 같은 계정의 갱신과 다른 계정으로의 전환을 서로 다른 조건으로 다루게 됐습니다.

유지보수자의 반례를 받아 조건과 테스트를 바꾼 것이 이 기여의 핵심입니다. 캐시는 아직 쓸 수 있는지만으로 재사용할 수 없습니다. **지금 읽으려는 대상의 값인지**까지 확인해야 합니다.
