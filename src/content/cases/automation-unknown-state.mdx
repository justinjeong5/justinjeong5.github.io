광고 소재 목록에는 소재를 켜고 끄는 토글이 있었습니다. 단순한 On/Off처럼 보이지만, 그 소재의 실행 상태에 자동화 규칙이 연결돼 있으면 수동 변경 전에 확인 모달을 거쳐야 했습니다. 같은 버튼이어도 연결된 규칙에 따라 필요한 절차가 달랐습니다.

문제는 페이지가 열릴 때 규칙 정보를 서버에서 따로 읽는다는 점이었습니다. 토글은 화면에 보이는데, 그 토글에 규칙이 있는지는 아직 응답을 기다리고 있었습니다. 이 잠깐의 상태는 '규칙이 없다'가 아니라 '아직 모른다'였습니다.

조회가 끝나기 전에 빠르게 누르면 아직 채워지지 않은 정보로 분기해 확인 없이 변경할 수 있었습니다. 조금 기다렸다가 같은 버튼을 누르면 확인 모달이 열립니다. 사용자는 같은 화면에서 같은 행동을 했는데, 누른 시점과 응답 속도에 따라 다른 절차를 밟는 셈이었습니다.

규칙 정보를 읽기 전에도 토글을 사용할 수 있게 둘지 정해야 했습니다. 로딩 표시를 추가하는 것만으로는 확인 없이 실행되는 변경을 막을 수 없어서, 조회 중 허용할 동작도 함께 정했습니다.

## 클릭이 조회보다 빠를 때

화면이 열리면 규칙 정보를 비동기로 읽습니다. 조회가 끝나기 전에 클릭하면 아직 채워지지 않은 존재 여부로 분기하고, 이를 규칙 없음으로 읽으면 곧바로 상태를 변경합니다. 뒤늦게 규칙이 있다는 응답을 받아도 이미 실행한 변경에 확인 모달을 적용할 수는 없었습니다.

저는 조회보다 클릭이 먼저 도착하는 순서를 설명하고 조회 중 표시와 조작 제한을 제안했습니다. 그만큼 사용자는 정보를 기다리는 동안 토글을 바로 쓸 수 없습니다. 디자이너와는 그 제약을 두되 정상 응답이 빠를 때 스피너가 주는 부담과 아이콘 정렬도 함께 논의했습니다. 지연을 넣은 재현은 실제 지연 시간을 측정하려는 것이 아니라, 확인이 생략되는 실행 순서를 보여주기 위한 것이었습니다.

## 비활성 표시와 실행 가드를 함께 둔 이유

조회 중에는 토글을 비활성화해 지금 조작할 수 없음을 보여줬습니다. 입력 함수에서도 조회 중이거나 다른 변경을 처리 중이면 돌아가도록 했습니다. 표시가 바뀌는 것에만 의존하지 않고, 실제 상태를 바꾸는 함수가 실행 가능 여부를 확인하게 했습니다.

조회가 끝난 뒤에는 규칙이 없으면 바로 변경하고, 규칙이 있으면 확인 모달을 열도록 나눴습니다. 모달에서 취소하면 변경 함수를 실행하지 않고, 확인했을 때만 실행했습니다.

설명의 핵심만 줄이면 이런 흐름입니다.

```text
조회 중 또는 변경 처리 중 → 실행하지 않음
조회 완료, 연결된 규칙 없음 → 상태 변경
조회 완료, 연결된 규칙 있음 → 확인 모달
모달 취소 → 기존 상태 유지
모달 확인 → 상태 변경
```

조회는 loading, 변경은 processing으로 나눴습니다. 정보를 읽는 동안에도, 실제 상태 변경을 처리하는 동안에도 추가 입력을 막아야 했기 때문입니다.

## 일반 토글에 어디까지 책임을 둘까

리뷰에서는 이 확인 절차를 일반 토글의 사용처마다 직접 붙이면 빠뜨릴 수 있다는 문제가 나왔습니다. 반대로 모든 토글 사용을 강하게 통제하는 구조로 만들면 일반 컴포넌트의 책임이 너무 넓어질 수 있었습니다.

저는 자동화 규칙의 존재를 조회하고, 필요한 확인을 거쳐 변경하는 동작을 도메인 컴포넌트에 묶는 쪽으로 설명했습니다. 단순한 On/Off UI는 일반 토글이 맡고, 자동화에 따른 행동은 그 도메인을 아는 컴포넌트가 맡도록 구분한 것입니다.

그 결과 자동화 상태를 바꾸는 사용처에서는 조회·확인 절차를 다시 조립하는 대신 그 동작을 가진 컴포넌트를 선택할 수 있었습니다. 일반 토글 전체에 도메인 지식을 넣지는 않지만, 사용처가 자동화-aware 동작을 골라야 한다는 비용은 남습니다. 리뷰에서 논의한 강제 수준도 바로 그 선택의 책임에 관한 문제였습니다.

## 조회 중 클릭은 더 이상 바로 변경으로 이어지지 않는다

규칙 정보를 기다리는 동안에는 사용자의 입력이 곧바로 변경으로 이어지지 않게 됐습니다. 조회가 끝나면 규칙이 없는 경우는 직접 변경하고, 있는 경우는 확인을 거칩니다. 빨리 눌렀다는 이유로 필요한 확인을 건너뛰던 경로를 막은 것입니다. 기다리는 비용은 생기지만, 조회가 진행 중인 동안에는 아직 모르는 정보로 중요한 행동을 결정하지 않게 했습니다.

디자이너와는 기다리는 동안의 조작 제한과 표시 부담을 맞췄고, 리뷰에서는 이 확인 절차를 어느 컴포넌트에 둘지 논의했습니다. 스피너를 어떻게 보여줄지 정하면서 버튼을 언제 실행할 수 있는지도 함께 정했습니다.

지금 다시 보면 조회 실패도 별도로 다뤄야 한다고 생각합니다. loading이 끝났더라도 정보를 읽지 못했다면 규칙이 없다고 판단할 수는 없습니다. 이번에는 조회 중 확인을 건너뛰던 클릭 경로를 막았습니다. 다음에 같은 흐름을 만든다면 실패 뒤 재조회와 그동안 허용할 행동까지 먼저 정하고 싶습니다.
