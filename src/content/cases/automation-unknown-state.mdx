## 확인 근거와 공개 범위

문제 제안·디자인 협의, 코드·리뷰와 일부 테스트 파일을 대조했습니다. 테스트 파일의 존재와 실행 통과를 구분하며, alpha 보고를 실제 운영 완료로 확장하지 않습니다.

이 글은 원문을 대조한 공개용 재구성입니다. 내부 코드·협의 원문·고객 정보는 공개하지 않으므로 방문자가 원문을 직접 검증할 수 있는 자료는 아닙니다.

## 같은 토글이 다른 의미를 가졌다

운영 화면의 토글은 자동화 룰의 존재 여부에 따라 확인 절차가 달라졌다. 그런데 룰 조회가 끝나기 전에 클릭하면 필요한 확인 모달을 우회할 수 있는 실행 순서가 있었다.

이 문제를 구체적인 순서로 설명하고, 조회 중 표시와 조작 제한을 제안했다. 디자이너는 제한에 동의했고, 빠른 정상 응답에서 표시가 주는 부담과 아이콘 정렬도 함께 논의했다. 지연 예시는 인위적 재현이었다. 실제 사용자 지연의 측정값은 아니다.

## 표시와 행동을 나눴다

화면의 disabled 처리와 입력 함수의 loading/processing 가드를 두고, 룰이 있다고 판정되면 확인 후 상태를 바꾸는 흐름을 도메인 컴포넌트에 묶었다.

리뷰에서는 일반 토글을 잘못 사용할 가능성과 책임 분리를 논의했다. 모든 사용처를 강하게 강제하는 framework식 구조에 대한 우려를 설명하고, 공유하는 도메인 동작과 사용처의 명확성을 함께 고려했다.

## 테스트와 전달은 다른 질문이다

테스트 파일과 리뷰·병합·릴리즈 포함 기록이 남아 있다. 확인한 해당 테스트 파일은 계산 속성 중심이었다. 파일이 있다는 것만으로 로딩 가드와 모달 승인/취소가 실행 검증됐다고 말하지 않는다.

조회가 실패해도 loading이 끝나는 경로가 있다. **조회 중 행동 제한**과 **조회 실패 이후의 안전한 정책**은 서로 다른 주장이다. 후자의 전체 계약과 실제 운영 오류 감소는 여기서 확정하지 않는다.

[사용자가 대기에서 빠져나올 경로](/cases/ad-response-recovery)는 반대로 불확실성이 남아 있을 때 선택지를 여는 기록이다. 무엇을 막고 무엇을 열지는 행동의 의미와 시스템 경계에 따라 달라진다.
