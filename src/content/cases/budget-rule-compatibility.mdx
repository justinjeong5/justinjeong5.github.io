광고 운영 화면의 자동화는 하나의 설정이 아니었습니다. 시간 조건을 사용하는 규칙과 예산 상태를 사용하는 규칙이 있었고, 광고나 개별 소재에 이미 연결된 설정도 남아 있었습니다. 새 예산 자동화를 넣어도 운영자가 이전에 구성한 규칙이 없어지는 것은 아니었습니다.

운영자가 예산 규칙 하나만 끄려고 토글을 바꿨는데 시간 규칙까지 제거된다면, 화면이 보여주는 행동과 실제 변경 범위가 달라집니다. 예산 설정을 바꾸는 화면에서는 그 규칙만 바뀌도록 해야 했습니다.

조회에서도 같은 문제가 있었습니다. 새 형식의 규칙만 읽으면 기존 규칙만 가진 설정은 비어 보일 수 있습니다. 목록을 하나로 합쳐 보여주더라도, 저장하거나 삭제할 때는 어떤 규칙을 대상으로 한 행동인지 남아 있어야 했습니다.

이미 사용 중인 규칙을 읽고 유지하면서 새 규칙을 추가해야 했습니다. 이를 위해 토글이 가리키는 대상과 조회·저장·삭제의 대상을 함께 맞췄습니다.

## 리뷰가 화면 밖의 계약을 드러냈다

동료는 기존 규칙만 있는 경우에도 조회와 표시가 유지되는지 물었습니다. 저는 구·신 규칙을 함께 조회하는 처리와 권한을 맞추고 gateway도 수정했다고 설명했습니다. API 필드를 바꾼 뒤에는 영향을 받는 부분을 다시 리뷰해달라고 요청했습니다.

삭제에 대해서도 어떤 규칙을 없애는지 범위를 설명했습니다. 예산 규칙 제거와 시간 규칙 제거는 같은 작업이 아니었습니다. 새 화면의 토글을 모든 자동화 설정의 삭제 신호처럼 사용할 수는 없었습니다.

## 규칙의 ID와 상태를 남긴 채 저장하기

구현에서는 광고에 연결된 규칙과 각 소재에 연결된 규칙을 조회해 화면의 목록으로 합쳤습니다. 목록을 하나로 보여줘도 저장 대상을 하나로 뭉뚱그릴 수는 없었습니다. 각 규칙의 ID와 제거 상태를 유지해야 했습니다.

저장할 때는 그 상태로 작업을 골랐습니다. 기존 ID가 있고 제거된 규칙이면 삭제하고, 기존 ID가 남아 있으면 갱신하고, 새 규칙이면 생성했습니다. 아직 서버에 만들지 않은 규칙을 화면에서 지운 경우에는 저장 대상에서 제외했습니다.

아직 만들지 않은 규칙을 추가했다가 지우면 서버에 삭제 요청을 보낼 ID가 없습니다. 이미 저장된 규칙을 제거할 때는 그 ID에 대한 삭제가 필요합니다. 화면에서는 둘 다 ‘제거’로 보여도 API 요청은 달라야 해서, 개별 규칙의 ID와 제거 상태를 남겼습니다.

gateway에도 조회·생성·수정·삭제 경로와 권한을 함께 맞췄습니다. FE의 폼에서 만든 요청이 실제 조회와 저장까지 이어질 수 있도록 연결했습니다.

## 기본값처럼 보였던 시간 분기가 새 규칙을 잘못 묶었다

후속 작업에서는 토글을 켜고 끌 때 규칙의 시간 조건이 잘못 저장되는 버그를 다뤘습니다. 여기서 첫 번째·두 번째 알림은 Slack으로 알림을 보내는 규칙의 구분입니다. 수정한 코드는 광고 종료일을 비교할 기준 시각을 저장하는 부분이었습니다. 기존 분기는 첫 번째 알림이면 기본 시각을 쓰고, 그 밖의 규칙에는 별도 시각을 넣는 형태였습니다.

문제는 첫 번째가 아닌 것이 모두 두 번째 알림은 아니라는 점입니다. 규칙 종류가 늘어난 상태에서 넓은 else가 원래 예외를 넘어 다른 규칙까지 묶을 수 있었습니다.

두 번째 알림일 때만 별도 시각을 쓰고 나머지는 기본 시각을 쓰도록 조건을 좁혔습니다. 기존의 “첫 번째가 아니면” 조건이 늘어난 규칙까지 포함하므로, 별도 시각이 필요한 “이 예외에 해당하면”으로 바꿨습니다.

## 변경 뒤에 남은 것은 새 폼보다 공존하는 동작이었다

운영자는 기존 규칙이 있는 설정을 새 화면에서도 읽고, 새 규칙을 추가하거나 각 ID에 맞춰 수정·삭제할 수 있게 됐습니다. 예산 규칙을 제거하는 행동이 다른 종류의 규칙까지 제거하는 명령이 되지 않도록 범위를 나눴습니다. 후속 시간 조건도 두 번째 알림에만 예외를 적용했습니다. 새 자동화를 쓰기 위해 기존 설정을 비워야 하는 화면이 아니라, 두 종류가 함께 남는 동작을 만든 결과였습니다.

동료가 기존 규칙만 있는 경우를 질문하면서 화면의 폼만으로는 확인하기 어려운 조건을 함께 살폈습니다. 조회·권한·gateway를 맞추고 API 변경에 다시 리뷰를 요청하면서 기존 설정을 유지해야 하는 조건도 확인했습니다. 지금 다시 보면 새 규칙을 추가할 때는 그 규칙의 동작과 함께 기존 입력이 어떤 조회와 분기로 들어가는지도 확인해야 한다고 생각합니다. 후속 else 수정에서도 예외를 적용할 범위를 그렇게 좁혔습니다.
