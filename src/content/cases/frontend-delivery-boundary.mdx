## 확인 근거와 공개 범위

전달 구조의 코드·리뷰와 협의를 대조했습니다. 개별 배포 실행과 전체 시스템의 이전 완료는 별도 확인 대상입니다.

이 글은 원문을 대조한 공개용 재구성입니다. 내부 코드·협의 원문·고객 정보는 공개하지 않으므로 방문자가 원문을 직접 검증할 수 있는 자료는 아닙니다.

## 화면의 변경이 어디에 묶여 있었는가

서버 템플릿에 있던 웹 페이지는 FE 생태계 재사용, 리뷰, 테스트와 배포에 제약이 있었다. 화면을 바꾸는 일의 책임과 전달 경계를 별도 FE 앱으로 나누는 방향을 팀과 논의했다.

초기 방향·범위를 동료와 조율하고 필요한 인프라 협업을 요청했다. 도메인이나 인프라 전체를 혼자 소유한 작업은 아니다.

## 산출물과 전환 범위를 구현했다

Next.js를 서버 실행하지 않는 정적 export로 구성하고, 정적 산출물을 S3로 전달하며 CloudFront를 갱신하는 workflow를 구현했다.

리뷰에서는 상품 코드와 환경 설정의 범위를 어디까지 묶을지 피드백을 받았다. 초기에는 기존/새 경로가 공존했고, 남은 작업과 상품별 후속 진행을 안내했다.

## 구조의 도입과 실제 운영 결과

workflow source와 개별 진행/배포 보고가 남아 있다. 그러나 특정 실행의 SHA와 서버 release를 대조한 결과나 전체 레거시 이관 완료, 배포 리드타임·비용 감소까지 확정하지 않는다.

구현과 후행 논의의 시간 순서도 바꾸지 않는다. 뒤에 완성된 문서를 언제나 선행 승인처럼 표현할 수는 없다.

[캐시 변경 뒤의 회귀](/cases/build-cache-compatibility)와 [기존 계약을 유지하는 관측](/cases/bridge-observation-contract)을 연결해 읽으면, 기술 도입 자체보다 변경의 영향을 어디까지로 둘지 살핀 과정이 보인다.
