광고 참여 화면의 문구나 표현을 바꾸려면 광고 서버의 리뷰·테스트·배포도 함께 거쳐야 했습니다. 화면이 서버의 HTML 템플릿 안에 있어서 FE 라이브러리와 컴포넌트를 재사용하는 데도 제약이 있었습니다. 자주 바꾸는 화면 코드와 서버 코드를 같은 경로로 전달하면서 생기는 비용이었습니다.

별도 FE 앱으로 옮기면 화면 개발의 구조를 나눌 수 있었습니다. 하지만 새 폴더와 프레임워크를 만드는 것만으로 끝나지는 않습니다. 누가 검사하고, 어떤 산출물을 어디에 전달하며, 아직 옮기지 않은 상품은 어떤 경로를 사용할지도 함께 정해야 했습니다.

2023년 12월부터 팀과 방향을 논의했고 2024년 1월 초기 앱을 전달했습니다. 인프라 담당자의 협업을 받아 기존 전달 경로를 연결하고 일부 상품부터 전환했습니다. 렌더링과 운영 선택을 정리한 RFC는 구현 이후인 5월에 남겼습니다.

## 앱을 분리하는 선택과 서버를 늘리는 선택

이전의 장단점을 동료에게 물었고, 기존 FE 프로젝트를 재사용하자는 추천을 받아 프론트엔드 동료들과 방향을 논의했습니다. 새 앱을 만들더라도 모노레포와 공유 패키지, 기존 인프라를 어디까지 이용할지는 함께 결정해야 했습니다.

Next.js를 선택했다고 요청마다 렌더링하는 새 서버까지 운영할 필요는 없었습니다. 구현은 정적 export로 파일을 만들고 기존 S3·CloudFront 전달 경로에 연결하는 방식으로 시작했습니다.

5월 후속 RFC에서는 광고에서 진입하는 화면의 낮은 SEO 필요, 당시 FE 인력과 별도 서버의 운영 대응 부담을 함께 설명했습니다. 정적 산출물로 시작하되 이후 서버 렌더링이 필요해질 여지는 남겼습니다. 초기 논의와 구현으로 먼저 경로를 전달하고, 사용하던 구조의 이유를 후속 문서로 정리한 순서였습니다.

Next.js를 쓰는 것과 렌더링 서버를 새로 운영하는 일을 나눠 결정했습니다. FE 개발 구조는 바꾸되 새 서버의 장애 대응과 배포까지 늘릴 필요는 없었습니다.

## 검사한 파일이 실제 전달할 파일이어야 했다

새 앱에는 로컬 실행과 빌드뿐 아니라 PR 검사와 전달 workflow가 필요했습니다. 앱과 공유 패키지 변경을 검사하고, 실제 정적 빌드 결과를 기존 저장소에 동기화한 뒤 CDN 캐시를 갱신하도록 연결했습니다.

```text
앱·공유 코드 변경
  → lint·format·test
  → 정적 빌드
  → 산출물 동기화
  → CDN 갱신
  → workflow의 성공·실패 보고
```

파일 업로드가 끝나도 CDN 갱신이 실패하면 전달의 마지막 단계가 남습니다. 앞 단계가 실행됐다는 사실로 전체 성공을 선언하지 않도록 workflow 상태를 연결했습니다. 이것이 업로드를 원자적으로 롤백하는 시스템을 만든 것은 아닙니다. 제가 만든 범위는 검사한 산출물의 전달 순서와 실패 보고였습니다.

실행·검사·배포 방법을 같은 앱의 문서로 남겼습니다. 코드를 옮긴 사람만 실행할 수 있는 앱이 아니라, 다음 화면을 맡을 개발자도 변경 경로를 따라갈 수 있게 하려는 작업이었습니다.

## 리뷰는 실행 가능한 변경의 다른 비용을 보여줬다

초기 변경에는 앱 전달 구조와 상품 동작, 환경 설정이 함께 들어 있었습니다. 사람 리뷰에서 상품 코드와 환경 설정을 별도 PR로 나눠 달라는 요청을 받았습니다.

상품의 행동을 읽다가 환경의 위험을 놓치거나, 환경을 보다가 상품 규칙을 놓칠 수 있었습니다. 구현이 실행된다는 사실과 동료가 이해하고 검토할 수 있는 단위는 같지 않았습니다. 처음부터 깔끔하게 분리한 경험이 아니라, 전달할 변경을 어떻게 설명해야 하는지 피드백을 받은 경험이었습니다.

인프라 담당자의 도움도 필요했습니다. 정적 파일 전달 기반을 제가 새로 만들었다고 할 수는 없습니다. 독립 앱이 생성하는 산출물을 그 기반에 연결한 개발과 협업이 제 책임이었습니다.

## 모든 화면을 한 번에 옮기지 않았다

일부 시험 상품부터 새 경로를 사용하고 기존 경로와 함께 두었습니다. 오류 페이지와 남은 상품의 진행 상태도 따로 안내했습니다.

공존은 복잡성을 없애는 선택이 아니었습니다. 어느 상품이 어느 경로를 사용하는지 계속 설명해야 했습니다. 대신 기존 상품의 전달을 한 번에 바꾸지 않고 새 앱의 산출물을 쓰는 범위를 늘릴 수 있었습니다.

전환 뒤에는 리워드 표시와 계측, CTA와 서버 이벤트 오류, 후속 상품을 같은 FE 환경에서 개발했습니다. 공유 컴포넌트를 추상화하고 재사용하는 변경도 이어졌습니다. 폴더 분리의 실험에서 끝나지 않고 실제 다음 개발이 사용하는 경로가 된 것입니다.

## 새 기술보다 변경을 전달할 경로가 남았다

개발자는 해당 FE 앱의 실행 환경을 준비하고, 검사·빌드한 정적 산출물을 기존 인프라로 전달할 수 있게 됐습니다. 일부 상품이 실제로 새 경로를 사용했고, 후속 상품과 공용 기능 개발이 이어졌습니다.

정적 앱으로 시작하면 새 렌더링 서버의 운영 부담을 늘리지 않을 수 있었습니다. 반면 상품 코드와 환경 설정을 나눠 달라는 리뷰를 통해, 실행 가능한 변경이어도 검토할 때는 다른 단위가 필요하다는 것을 확인했습니다. 다음 전환에서는 코드의 위치뿐 아니라 동료가 무엇을 확인하고 어디서 다음 개발을 이어갈지도 함께 정하려고 합니다.
