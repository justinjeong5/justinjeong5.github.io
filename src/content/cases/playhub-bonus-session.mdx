추가 혜택이 있다는 사실을 언제 알려줘야 할까? 사용자가 광고를 본 뒤 결과 화면에서 처음 알게 된다면, 그 혜택은 참여할 이유가 될 수 없다. 새 보너스 기능을 만들 때 서버는 추가 금액을 결과 응답에 제공하려 했지만, 화면에는 참여 전부터 이벤트가 적용되는지 알아야 하는 요구가 있었다.

나는 상태 응답에도 적용 여부가 필요하다고 요청했다. 서버 담당자와 boolean 필드를 제공하는 계약을 맞추고, 상태·참여·리워드 결과와 상자 UI를 연결했다. 화면의 문구를 고치는 일이 아니라 **새 상품의 어느 단계에서 어떤 정보를 알아야 하는지**를 함께 정한 작업이었다.

이 기능에서는 광고를 보고 상자를 여는 정상 경로 외에도 늦은 조회, 광고 취소, 새 회차, 문의 뒤 인정 상태가 있었다. 버튼 하나로 시작하지만 서로 다른 작업의 수명을 함께 설계해야 했다.

## 먼저 참여 상태를 만들고 실제 실행을 붙였다

8월에는 서버 상태를 해석하는 규칙부터 만들었다. 광고가 필요한지, 상자를 열 준비가 됐는지, 현재 참여할 수 없는지를 화면의 행동으로 도출했다. 이후 실행 가능한 광고 후보와 세션을 연결하고 상자·제안 UI, 클릭과 연출 완료를 실제 참여 흐름에 붙였다.

그 순서는 다음처럼 이어졌다.

```text
서버 상태 → 지금 가능한 행동
  → 광고 후보 준비와 실행 세션
  → 서버의 시청 인정·리워드 결과
  → 상자 UI와 다음 상태 조회
```

광고 SDK가 끝났다는 사실과 서버가 시청을 인정한 결과도 같은 단계는 아니었다. 문의를 제출한 뒤에는 상태를 다시 읽고 서버의 인정 상태를 확인해야 했다. 제출 성공만으로 상자 준비를 확정하지 않았다.

## 늦은 응답은 항상 최신의 사실이 아니었다

광고를 마친 직후 이전에 시작한 상태 조회가 도착할 수 있었다. 서버 값으로 로컬 상태를 무조건 덮으면 방금 완료한 시청이 미완료로 돌아갈 수 있다. 반대로 로컬 완료를 무조건 지키면 새 회차에서도 이전 시청을 이어 쓰게 된다.

초기화 시각으로 같은 회차인지 확인하고, **같은 회차의 유효한 상태에서만 진행을 보존**했다. 새 회차나 서버 비활성화, 비정상 응답에서는 이전 완료를 그대로 이어 쓰지 않았다.

같은 회차의 지연 응답, 회차 변경, 참여 불가 응답을 서로 다른 기대 결과로 테스트했다. 이 판단은 UI의 진행을 맞추는 규칙이다. 서버의 지급 정책을 클라이언트 기록으로 대신하는 것은 아니었다.

## 광고를 다시 부르는 세 가지 이유를 구별했다

상자 앞의 광고 실행이 여러 곳에서 요청될 수 있었다. 요청마다 새 광고를 실행하면 같은 참여 안에서 광고가 겹친다. 그렇다고 모든 결과를 계속 재사용하면 사용자가 취소한 뒤 다시 시작할 방법도 사라진다.

세션 시작 때 실행 가능한 후보를 고정하고, 호출 시점의 상태에 따라 다르게 처리했다.

| 세션 상태 | 다음 호출의 의미 |
| --- | --- |
| 아직 실행 중 | 같은 Promise를 공유 |
| 이미 완료 | 완료 결과를 재사용하고 광고 재실행 생략 |
| 사용자가 취소 | 다음 후보를 강제로 열지 않고 재시작 허용 |

진행 중의 두 호출이 같은 Promise를 받으며 runner가 한 번만 실행되는 조건과, 취소 뒤 다시 실행할 수 있는 조건을 따로 테스트했다. 중복 호출을 합치는 정책과 취소 결과를 영구적으로 재사용하는 정책은 달랐다.

후보를 고정하는 범위도 이 세션이었다. 새 회차의 판단까지 과거 후보와 완료를 이어 쓸 수는 없었다. 더 자세한 요청 적용·정리의 문제는 [비동기 요청의 소유권](/cases/latest-request-boundaries/)에서 다룬다.

## 검증 환경과 서버 설정도 참여 흐름의 일부였다

검증 환경에서 실제 SDK를 사용할 수 있는지 서버 담당자와 맞췄다. 화면이 잘 만들어졌어도 광고 실행 경로가 다른 환경에서는 같은 기능을 확인할 수 없었다.

문의의 외부 인입과 리워드 요청 오류도 따로 확인했다. 리워드 오류는 서버 설정 누락을 추적하고 담당자 조치 뒤 정상 동작을 확인했다. 서버 설정을 내가 바꾼 것은 아니지만, FE 오류로만 읽고 끝냈다면 다음 단계가 남았을 상황이었다.

참여 전 이벤트 안내에 필요한 응답을 8월 27일 맞췄고, 28일에는 QA 피드백을 수정·배포해 CS·디자인·제품 담당자의 확인과 함께 상용 전달을 마쳤다. 이후에도 헤더와 다크 모드 등 후속이 있었다. 첫 출시는 후속 검토가 필요 없는 상태가 아니라, 실제 참여할 수 있는 핵심 흐름을 전달한 시점이었다.

## 추가 혜택을 실제로 참여할 수 있는 상품으로

결과에 금액을 붙이는 것만으로 새 보너스가 완성되지는 않았다. 참여 전 안내, 광고 실행, 서버의 인정, 상자 결과, 문의 후 재확인이 한 사이클로 이어져야 했다. 상태 응답의 변경과 광고 세션의 정책을 함께 다뤄 이 흐름을 출시했다.

이 작업에서 오래 남는 판단은 두 가지다. 결과에 필요한 정보와 참여를 결정할 때 필요한 정보는 다를 수 있다는 것, 그리고 진행 중·완료·취소를 모두 같은 재사용 정책으로 다룰 수 없다는 것이다. 새 상품의 규칙을 화면으로 옮길 때는 무엇을 표시할지와 함께, 사용자가 다음 행동을 결정하는 순간에 무엇을 알 수 있어야 할지를 먼저 보게 됐다.
