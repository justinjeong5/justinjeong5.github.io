사용자가 추가 혜택을 광고를 본 뒤 결과 화면에서 처음 알게 된다면, 그 혜택을 보고 참여를 결정할 수는 없습니다. 새 보너스 기능을 만들 때 서버는 결과 응답에 추가 금액을 제공하려 했습니다. 하지만 화면에서 참여 전에 혜택을 안내하려면 이벤트 적용 여부를 그보다 먼저 알아야 했습니다.

저는 상태 응답에도 적용 여부가 필요하다고 요청했습니다. 서버 담당자와 boolean 필드를 제공하는 계약을 맞추고, 상태·참여·리워드 결과와 상자 UI를 연결했습니다. 참여 전 안내에 필요한 값을 결과 응답보다 먼저 받아야 했기 때문에, **새 상품의 각 단계에서 필요한 정보**를 먼저 맞췄습니다.

광고를 보고 상자를 여는 흐름에 늦은 조회와 광고 취소, 새 회차, 문의 뒤 인정 상태가 들어올 수도 있었습니다. 버튼을 누른 뒤 이 결과들이 어느 참여에 적용돼야 하는지 함께 정해야 했습니다.

## 먼저 참여 상태를 만들고 실제 실행을 붙였다

8월에는 서버 상태를 해석하는 규칙부터 만들었습니다. 광고가 필요한지, 상자를 열 준비가 됐는지, 현재 참여할 수 없는지를 화면의 행동으로 도출했습니다. 이후 실행 가능한 광고 후보와 세션을 연결하고 상자·제안 UI, 클릭과 연출 완료를 실제 참여 흐름에 붙였습니다.

그 순서는 다음처럼 이어졌습니다.

```text
서버 상태 → 지금 가능한 행동
  → 광고 후보 준비와 실행 세션
  → 서버의 시청 인정·리워드 결과
  → 상자 UI와 다음 상태 조회
```

광고 SDK가 끝났다는 사실과 서버가 시청을 인정한 결과도 같은 단계는 아니었습니다. 문의를 제출한 뒤에는 상태를 다시 읽고 서버의 인정 상태를 확인해야 했습니다. 제출 성공만으로 상자 준비를 확정하지 않았습니다.

## 늦은 응답은 항상 최신의 사실이 아니었다

광고를 마친 직후 이전에 시작한 상태 조회가 도착할 수 있었습니다. 서버 값으로 로컬 상태를 무조건 덮으면 방금 완료한 시청이 미완료로 돌아갈 수 있습니다. 반대로 로컬 완료를 무조건 지키면 새 회차에서도 이전 시청을 이어 쓰게 됩니다.

초기화 시각으로 같은 회차인지 확인하고, **같은 회차의 유효한 상태에서만 진행을 보존**했습니다. 새 회차나 서버 비활성화, 비정상 응답에서는 이전 완료를 그대로 이어 쓰지 않았습니다.

같은 회차의 지연 응답, 회차 변경, 참여 불가 응답을 서로 다른 기대 결과로 테스트했습니다. 이 판단은 UI의 진행을 맞추는 규칙입니다. 서버의 지급 정책을 클라이언트 기록으로 대신하는 것은 아니었습니다.

## 광고를 다시 부르는 세 가지 이유를 구별했다

상자 앞의 광고 실행이 여러 곳에서 요청될 수 있었습니다. 요청마다 새 광고를 실행하면 같은 참여 안에서 광고가 겹칩니다. 그렇다고 모든 결과를 계속 재사용하면 사용자가 취소한 뒤 다시 시작할 방법도 사라집니다.

세션 시작 때 실행 가능한 후보를 고정하고, 호출 시점의 상태에 따라 다르게 처리했습니다.

| 세션 상태 | 다음 호출의 의미 |
| --- | --- |
| 아직 실행 중 | 같은 Promise를 공유 |
| 이미 완료 | 완료 결과를 재사용하고 광고 재실행 생략 |
| 사용자가 취소 | 다음 후보를 강제로 열지 않고 재시작 허용 |

진행 중의 두 호출이 같은 Promise를 받고 runner가 한 번만 실행되는 조건과, 취소 뒤 다시 실행할 수 있는 조건을 따로 테스트했습니다. 진행 중 요청을 합치더라도 취소 결과까지 계속 재사용하면 재시작을 막게 되므로 별도로 처리했습니다.

후보를 고정하는 범위도 이 세션이었습니다. 새 회차의 판단까지 과거 후보와 완료를 이어 쓸 수는 없었습니다. 더 자세한 요청 적용·정리의 문제는 [비동기 요청의 소유권](/cases/latest-request-boundaries/)에서 다룹니다.

## 검증 환경과 서버 설정도 참여 흐름의 일부였다

검증 환경에서 실제 SDK를 사용할 수 있는지 서버 담당자와 맞췄습니다. 화면이 잘 만들어졌어도 광고 실행 경로가 다른 환경에서는 같은 기능을 확인할 수 없었습니다.

문의의 외부 인입과 리워드 요청 오류도 따로 확인했습니다. 리워드 오류는 서버 설정 누락을 추적하고 담당자 조치 뒤 정상 동작을 확인했습니다. 서버 설정을 제가 바꾼 것은 아니지만, FE 오류로만 읽고 끝냈다면 다음 단계가 남았을 상황이었습니다.

참여 전 이벤트 안내에 필요한 응답을 8월 27일 맞췄고, 28일에는 QA 피드백을 수정·배포했습니다. CS·디자인·제품 담당자의 확인과 함께 실제 참여할 수 있는 핵심 흐름을 상용으로 전달했습니다. 이후에도 헤더와 다크 모드 등 후속 작업을 이어갔습니다.

## 추가 혜택을 실제로 참여할 수 있는 상품으로

상태 응답에 이벤트 적용 여부를 넣어 참여 전에 안내하고, 광고 세션을 연결해 실행과 완료·취소를 처리했습니다. 광고를 본 뒤에는 서버의 인정과 상자 결과를 읽고, 문의를 제출한 뒤에는 다시 확인하도록 했습니다. 이 흐름을 함께 연결해 새 보너스를 출시했습니다.

결과 화면에 필요한 값만 받아서는 참여 전 혜택을 안내할 수 없었습니다. 진행 중 호출을 재사용하는 처리도 취소 뒤 재시작에는 그대로 적용할 수 없었습니다. 이런 조건을 다루면서 새 상품을 화면에 옮길 때는 사용자가 다음 행동을 결정하는 순간에 어떤 정보를 알고 있어야 하는지부터 확인하게 됐습니다.
