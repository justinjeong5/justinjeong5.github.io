운영자가 적립 문의를 처리하려면 문의 내용만으로는 부족했다. 어느 캠페인에 언제 참여했는지, 이미 적립됐는지, 반복 참여의 마지막 적립은 문의 전인지 후인지, 최근 서버 이벤트는 무엇인지 함께 읽어야 했다. 기존 알림과 템플릿 중심의 흐름을 관리 화면으로 옮기면서 목표로 삼은 것도 이 페이지에서 적립 여부를 판단할 수 있게 하는 일이었다.

문의 목록과 상세를 만드는 데서 끝나면 정보는 모이지만 처리는 여전히 다른 곳에 남는다. 새 화면은 판단 근거를 읽고 대상을 선택해 적립하거나 완료 처리한 뒤 이력을 확인하는 흐름이어야 했다. 나는 이 운영 제품의 프론트엔드와 API client, BFF 연결을 맡았다.

## 정보를 나열하는 대신 처리 문맥을 만들었다

목록에는 완료 여부와 캠페인·접수 시점, 페이지네이션을 연결했다. 상세에는 문의 내용, 사용자와 캠페인 정보, 미션별 상태, 최근·전체 서버 이벤트, 처리 이력을 함께 두었다. 운영자가 지금 어느 문의와 캠페인을 다루는지 같은 문맥으로 읽도록 구성했다.

미션 카드는 적립 완료, 적립 가능, 불가능, 요청 중인 상태를 구분했다. 반복 참여와 타임부스팅 같은 조건도 판단에 필요했다. 실행 중에는 같은 적립 동작을 다시 누르지 못하게 하고, 완료 처리 후에는 목록으로 이어지도록 했다.

중요한 것은 조회 항목의 개수가 아니라 그 정보가 다음 행동의 근거가 되는지였다. 최초 요구에는 다른 캠페인으로 바꾸는 동작 등도 있었지만 모든 요구를 첫 출시의 완료 목록으로 만들지는 않았다. 구현과 협의할 범위를 함께 나누었다.

## 화면에서 발견한 빈칸을 API 계약으로 돌려보냈다

TypeScript API client와 응답 타입을 추가해 목록·상세 문맥·미션·캠페인·이벤트 이력·적립·완료 요청을 연결했다. 구현하면서 미션과 캠페인 조회 오류, 미션 유형과 복수 이벤트 문맥, 완료 처리자, 목록과 이력의 페이지네이션 계약을 서버 담당자에게 구체적으로 확인했다.

서버 담당자가 수정한 내용을 검증 환경에 배포한 뒤 조회가 회복된 것을 확인했다. 서버의 서비스 전체를 직접 만든 것은 아니지만, 운영자가 판단하려면 어떤 정보가 필요하며 어떤 응답이 부족한지는 화면 개발에서도 되돌려야 했다.

BFF에서는 조회 요청을 읽기 권한에, 적립과 완료 처리를 쓰기 권한에 연결했다. 기존 서버로 프록시하는 경로와 권한을 화면의 요청에 맞춰 추가한 것이다. 이 작업은 해당 기능의 읽기·쓰기 경계를 연결한 범위이며 운영 계정의 최소 권한 체계 전체를 새로 완성한 것은 아니었다.

## 정상 동작 QA와 편의성 검토를 나누었다

QA에 들어가기 전에 제품 담당자에게 추가·불필요한 기능과 사용 편의성을 먼저 봐 달라고 요청했다. 버튼이 동작하는지는 QA에서 확인할 수 있지만, 운영자가 판단하는 순서에 화면이 맞는지는 실제 업무의 관점이 필요했다.

사진 확대와 상단 정보 배치에 대한 의견은 반영했다. 이벤트 검색은 이후 논의로, 완료 취소는 다음 스펙으로 남겼다. 다른 캠페인을 즉시 적용하는 기능은 기존 공통 컴포넌트를 바꿔야 했고 다른 우선순위도 있었다. 다음 스프린트로 미룰 수 있는지 물어 제품 담당자와 범위를 합의했다.

요청을 모두 구현해야 좋은 운영 도구가 되는 것은 아니었다. 첫 출시에서 판단과 처리가 이어지는 핵심을 전달하고, 공용 구성의 변경이 필요한 동작은 별도로 검토할 수 있게 했다. 어떤 제안이 반영됐고 무엇이 남았는지도 같은 범위로 설명했다.

## 실제 처리에서는 응답 성공과 상태 반영이 달랐다

1월 14일 서버 배포 뒤 화면과 BFF를 전달했고, 개발자들의 런타임 모니터링과 제품 담당자의 확인을 나누었다. 출시 직후에는 실제 관리 화면에서 처리하기 편하다는 반응이 있었다. 하지만 실사용에서 화면의 적립 완료·처리 중 표시와 이벤트 이력이 맞지 않는 문제가 이어졌다.

프론트엔드가 볼 수 있는 정보의 한계를 설명하고 서버 담당자와 연결한 결과, 상태 반영의 지연을 다루게 됐다. 운영자는 다시 확인해야 하는 번거로움과 누락 가능성 때문에 실시간 표시를 원했다. 나는 지연이 짧으면 polling으로 확인하되 더 긴 지연은 다른 UX가 필요하다고 나누어 제안했다. 서버 담당자도 loading과 짧은 주기 조회, 조회 상한을 제안했다.

초기 화면은 API 응답 직후 완료 toast를 보여줬다. 후속에서는 이를 제거하고 미션별 조회 중 상태를 두었다. 1초 간격으로 미션을 읽으며 이전 상태의 변화 또는 적립 완료 상태를 확인한 뒤 결과를 알렸다. 상한을 넘으면 별도 문의 안내를, 조회가 실패하면 오류 안내를 보여줬다. 이 확인 조건은 화면의 상태 갱신 기준이지 모든 지급과 정산이 확정됐다는 뜻은 아니다.

## 후속 조회도 화면의 수명 안에 두었다

후속 조회가 추가되면 상세를 떠난 뒤 타이머가 남거나, 비활성 화면에서 불필요하게 일반 조회가 계속될 수 있다. 화면이 숨겨지거나 비활성일 때 일반 refetch를 억제하고 unmount에서는 타이머와 listener를 정리했다. 요청 성공 뒤 기다리는 UI만 넣은 것이 아니라 기다림이 언제 끝나는지도 같이 다뤘다.

기존 사용자 활동 화면에서 문의 상세로 들어가는 경로도 보완했다. 조회 문맥만 가지고 이동하는 대신 문의를 찾거나 생성하고, 받은 문의 식별자로 진입하도록 바꾸었다. 관련 BFF 경로까지 함께 연결한 뒤 1월 23일 후속 배포와 페이지 진입 확인으로 이어졌다.

이후 5월에는 한 건을 끝낸 뒤 다음 미처리 문의로 이동하는 별도 개선이 있었다. 그 작업은 [다음 문의를 준비하는 흐름](/cases/operator-next-inquiry/)에 따로 정리했다. 초기 운영 제품의 구축과 작은 후속 개선은 같은 제품의 다른 단계였다.

## 판단 화면을 출시하고, 사용 뒤의 시간차를 다시 제품에 넣었다

운영자는 한 상세 화면에서 참여와 처리 근거를 읽고 적립·완료를 실행할 수 있게 됐다. 제품 담당자의 편의성 의견을 출시 범위에 반영했고, 실제 사용에서 드러난 상태 지연은 즉시 완료 안내 대신 확인 중 상태와 후속 조회로 바꾸었다.

이 경험에서 운영 제품의 완성도를 보는 기준이 구체화됐다. 정보가 조회되는지와 버튼이 성공하는지에 더해, 운영자가 그 결과를 보고 어떤 판단을 내릴 수 있는지를 봐야 했다. 요청이 받아들여진 순간과 화면에 반영된 순간의 차이를 설명하고 그 사이를 처리 흐름에 넣은 것이 초기 구축 뒤에도 계속 필요한 개발이었다.
