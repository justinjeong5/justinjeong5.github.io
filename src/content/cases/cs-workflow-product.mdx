사용자가 광고 미션을 끝냈는데 리워드를 받지 못했다고 문의했습니다. 운영자가 최근 적립 기록 하나만 보고 이번 문의도 해결됐다고 판단할 수는 없습니다. 반복 참여에서는 문의한 회차와 적립 시점이 다를 수 있기 때문입니다. **이번 문의의 근거를 읽고 처리한 뒤, 처리 결과를 언제 완료로 볼 수 있는지 알려주는 화면**이 필요했습니다.

저는 2024년 12월부터 광고 운영 대시보드의 문의 관리 화면과 TypeScript API client, BFF의 조회·처리 경로를 맡았습니다. 서버 담당자는 참여·적립 서비스와 응답을 준비했고, 제품 담당자는 운영자의 판단 순서와 출시 범위를 검토했습니다. 첫 운영 출시는 2025년 1월이었습니다.

## 운영자가 이번 문의를 판단할 근거

상세 화면에는 문의·사용자·캠페인의 식별 정보와 시점, 미션 상태, 이벤트 이력, 처리 이력을 연결했습니다. 자료를 많이 보여주는 것보다 **모두 같은 문의를 설명하는지**가 중요했습니다. 어떤 참여인지 확인하고, 해당 미션이 적립됐는지 읽고, 지금 처리할 수 있는지를 판단한 다음 적립·완료를 실행하도록 화면을 구성했습니다.

조회가 성공해도 응답만으로 판단하기 어려운 부분은 서버 담당자와 다시 맞췄습니다. 반복 참여의 복수 이벤트 문맥과 완료 처리자 등을 확인하고, 오류는 재현 조건과 함께 전달했습니다. 첫 출시에서는 근거 확인부터 적립·완료까지 한 건을 처리하는 흐름을 우선했습니다. 사진 확대 등 바로 필요한 편의성은 반영하고, 다른 캠페인 즉시 적용과 완료 취소 등은 제품 담당자와 후속 범위로 나눴습니다.

## 서버가 받았다고 운영 화면도 완료된 것은 아니었다

실사용에서는 적립 요청 API가 성공한 뒤에도 화면이 읽는 미션 상태에는 바로 반영되지 않는 일이 있었습니다. 처음 화면은 성공 응답을 받자 완료처럼 안내했습니다. 그러나 운영자는 다시 확인해야 했고, 완료 표시와 이벤트 이력이 어긋나 보일 수 있었습니다.

저는 **요청 수락**과 **조회로 확인한 상태 반영**을 나눴습니다. 요청이 성공하면 미션별로 '확인 중'을 보여주고, 1초 간격으로 상태를 다시 읽었습니다. 이전 상태에서 변화가 있거나 적립 완료 상태를 관찰하면 화면을 갱신해 확인을 끝냈습니다. 상한을 넘기거나 조회가 실패하면 완료라고 단정하지 않고 후속 확인이 필요하다고 알렸습니다. 상세 화면을 떠날 때는 타이머와 listener를 정리했습니다.

이 판단은 운영 화면이 무엇을 증명할 수 있는지도 분명히 했습니다. 조회로 상태 변화를 확인하는 것은 운영자가 다음 행동을 정할 근거입니다. 지급·정산의 최종 확정은 서버의 책임으로 남습니다. 후속 변경은 1월 23일 배포와 페이지 진입 확인으로 이어졌습니다.

## 이번 건의 완료와 다음 건의 조회도 분리했다

5월에는 완료·반려 뒤 다음 미처리 문의로 이동하는 흐름을 더했습니다. 현재 문의의 처리가 성공한 뒤 서버에 다음 문의를 따로 요청했습니다. 다음 건이 없으면 없다고, 조회가 실패하면 불러오지 못했다고 알렸습니다. 이 실패를 앞선 문의의 처리 실패로 다시 보여주지 않았습니다. 주소가 바뀐 뒤 상세 조회가 실패할 때는 이전 문의의 사용자·캠페인·처리 정보도 비웠습니다.

첫 출시는 운영자가 한 문의의 근거를 읽고 처리할 수 있게 한 단계였습니다. 이후 실사용을 통해 **요청 수락, 화면에서 확인한 상태 반영, 다음 문의 조회가 각각 다른 완료 조건**이라는 점을 제품에 반영했습니다. 운영자가 안심하고 다음 일을 시작할 시점을 화면이 정확히 설명하는 것이 이 작업의 핵심이었습니다.
