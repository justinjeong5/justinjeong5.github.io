리포트를 내려받은 고객이 날짜를 계산에 사용할 수 없다고 했습니다. 화면에서도 날짜가 보이고 파일에도 값이 있었지만, 문자열로 저장된 날짜는 며칠이 지났는지 계산하거나 다른 자료와 맞추기 전에 다시 변환해야 했습니다.

처음에는 문자 깨짐이나 표시 형식의 문제로 읽었습니다. 고객 설문을 직접 확인하고 다시 질문하면서, 불편의 중심이 **보이는 날짜가 아니라 계산에 사용할 날짜**라는 것을 알게 됐습니다. 글자의 구분자를 바꾸는 것과 값의 타입을 바꾸는 것은 다른 해결이었습니다.

2023년에는 이 질문에서 리포트의 후처리 업무를 개선했습니다. 최초 다운로드 기능을 만든 시기와는 별개의 작업입니다.

## 같은 모양의 셀도 같은 데이터는 아니었다

화면에 `2023-08-03`이라고 표시된 두 셀을 생각해 보겠습니다. 하나는 그 문자를 그대로 가진 문자열이고, 다른 하나는 날짜 값에 표시 형식을 적용한 결과일 수 있습니다. 사용자는 둘을 같은 날짜로 보지만 계산과 정렬은 다른 값을 읽습니다.

값의 타입과 화면에 표시할 형식을 나눠 다뤘습니다. 날짜·숫자·비율 등의 필드에서 계산할 값은 유지하고, 리포트를 읽을 때 필요한 형식은 따로 적용했습니다. 필드의 표시 조건과 변환 결과도 테스트로 남겼습니다.

구현의 목적은 파일의 장식이 아니라 고객이 다음 작업에서 다시 타입을 고치는 부담을 없애는 것이었습니다.

## 금액이라고 항상 통화 표시가 필요한 것은 아니었다

운영 담당자에게 자료를 어떻게 취합하는지 물었습니다. 복사해 붙이고 다른 표와 합치는 업무를 확인한 뒤, 통화가 아니라 숫자 표시를 사용하는 선택을 했습니다.

금액이라는 도메인 이름만으로 형식을 정하면 사용자가 이어서 할 작업을 놓칠 수 있었습니다. 화면에서 읽을 때 자연스러운 표현과 다른 표에서 계산할 값이 같지 않을 수 있기 때문입니다.

취합 방식을 확인하니 변환 방법만 고르면 되는 작업이 아니었습니다. 고객과 운영자가 다른 표에서 다시 계산할 수 있는 값을 전달해야 했습니다.

## 포맷을 넣은 뒤의 회귀도 같은 작업이었다

포맷팅은 첫 구현 뒤 수정과 되돌림, 재도입을 거쳤습니다. 날짜를 실제 값으로 옮기는 과정에서 시간 표현과 실행 환경에 따라 달라지는 조건도 다뤄야 했습니다.

제가 만든 formatter와 테스트의 결과만으로 모든 환경의 문제가 해결됐다고 판단하지는 않았습니다. 이후 시간대·OS 조건의 수정은 동료의 구현을 통합·배포하며 이어 갔습니다. 10월에는 배포 안내 뒤 제보자가 정상 동작을 확인했습니다.

처음 문제를 정의하고 직접 구현한 범위와, 동료의 수정으로 전달한 후속을 나눠 설명해야 이 작업의 흐름이 정확해집니다. 사용자에게는 둘 다 리포트를 다시 쓸 수 있게 하는 과정이었습니다.

## 다운로드 이후의 일을 제품 안으로 가져오기

리포트는 화면에서 조회가 끝나거나 파일이 만들어졌을 때만 완성되는 기능이 아니었습니다. 날짜를 계산하고 값을 합치는 다음 작업에서 데이터가 어떤 의미를 유지하는지도 제품의 일부였습니다.

고객이 어떤 도구를 쓰는지뿐 아니라 **그 도구에서 무엇을 하려는지**를 확인하면서 구현이 달라졌습니다. 날짜의 구분자를 바꾸는 대신 값의 타입을 바꿨고, 금액 표시도 자료 취합 방식을 물은 뒤 숫자로 정했습니다. 다음 데이터 기능에서도 출력 형식을 고르기 전에 그 결과를 다시 사용하는 작업부터 확인하려고 합니다.
