리포트를 내려받은 고객이 날짜를 계산에 쓸 수 없다고 했다. 화면에서는 날짜가 잘 보이고 파일에도 값이 있다. 그런데 그 값이 문자열이면 며칠이 지났는지 계산하거나 다른 자료와 맞추는 작업에서는 다시 변환해야 한다.

처음에는 문자 깨짐이나 표시 형식의 문제로 읽었다. 고객 설문을 직접 확인하고 다시 질문하면서, 불편의 중심이 **보이는 날짜가 아니라 계산에 사용할 날짜**라는 것을 알게 됐다. 글자의 구분자를 바꾸는 것과 값의 타입을 바꾸는 것은 다른 해결이었다.

2023년에는 이 질문에서 리포트의 후처리 업무를 개선했다. 최초 다운로드 기능을 만든 시기와는 별개의 작업이다.

## 같은 모양의 셀도 같은 데이터는 아니었다

화면에 `2023-08-03`이라고 표시된 두 셀을 생각해 보자. 하나는 그 문자를 그대로 가진 문자열이고, 다른 하나는 날짜 값에 표시 형식을 적용한 결과일 수 있다. 사용자는 둘을 같은 날짜로 보지만 계산과 정렬은 다른 값을 읽는다.

값의 타입과 화면에 표시할 형식을 나눠 다뤘다. 날짜·숫자·비율 등의 필드에서 계산할 값은 유지하고, 리포트를 읽을 때 필요한 형식은 따로 적용했다. 필드의 표시 조건과 변환 결과도 테스트로 남겼다.

구현의 목적은 파일의 장식이 아니라 고객이 다음 작업에서 다시 타입을 고치는 부담을 없애는 것이었다.

## 금액이라고 항상 통화 표시가 필요한 것은 아니었다

운영 담당자에게 자료를 어떻게 취합하는지 물었다. 복사해 붙이고 다른 표와 합치는 업무를 확인한 뒤, 통화가 아니라 숫자 표시를 사용하는 선택을 했다.

금액이라는 도메인 이름만으로 형식을 정하면 사용자가 이어서 할 작업을 놓칠 수 있었다. 화면에서 읽을 때 자연스러운 표현과 다른 표에서 계산할 값이 같지 않을 수 있기 때문이다.

이 질문은 개발자가 편한 변환을 고르는 것에서, 고객과 운영자가 실제로 이어 쓰는 데이터를 고르는 것으로 판단의 범위를 바꿨다.

## 포맷을 넣은 뒤의 회귀도 같은 작업이었다

포맷팅은 첫 구현 뒤 수정과 되돌림, 재도입을 거쳤다. 날짜를 실제 값으로 옮기는 과정에서 시간 표현과 실행 환경에 따라 달라지는 조건도 다뤄야 했다.

내가 만든 formatter와 테스트의 결과만으로 모든 환경을 끝냈다고 읽지는 않았다. 이후 시간대·OS 조건의 수정은 동료의 구현을 통합·배포하며 이어 갔다. 10월에는 배포 안내 뒤 제보자가 정상 동작을 확인했다.

처음 문제를 정의하고 직접 구현한 범위와, 동료의 수정으로 전달한 후속을 나눠 설명해야 이 작업의 흐름이 정확해진다. 사용자에게는 둘 다 리포트를 다시 쓸 수 있게 하는 과정이었다.

## 다운로드 이후의 일을 제품 안으로 가져오기

리포트는 화면에서 조회가 끝나거나 파일이 만들어졌을 때만 완성되는 기능이 아니었다. 날짜를 계산하고 값을 합치는 다음 작업에서 데이터가 어떤 의미를 유지하는지도 제품의 일부였다.

이 경험에서 남는 것은 사용자가 어느 도구를 쓴다는 정보보다 **그 도구에서 무엇을 하려고 하는가**라는 질문이다. 날짜의 구분자를 바꾸려던 생각이 데이터 타입의 변경으로 이어졌고, 금액의 표시도 취합 업무를 확인한 뒤 달라졌다. 다음 데이터 기능에서도 출력 형식을 먼저 고르기보다 그 결과를 다시 사용할 행동부터 묻고 싶다.
