턱걸이 30회를 목표로 운동하려면 횟수를 적는 것 외에도 기억할 것이 있습니다. 오늘은 맨몸과 중량 중 무엇을 해야 하는지, 지난번에는 어느 무게로 몇 세트를 끝냈는지, 다음에는 횟수나 중량을 올려도 되는지입니다. 운동을 기록한 뒤에도 이 판단을 제가 다시 해야 한다면, 앱은 메모장 역할에서 크게 벗어나지 못합니다.

제가 원한 [풀업 30](https://pullup-30-coach.vercel.app/)은 **오늘 할 운동을 보고, 수행을 남기면 다음 계획과 성장 확인까지 이어지는 개인 코칭 앱**이었습니다. AI와 대화하며 HTML·JavaScript 기반 PWA를 만들고 직접 확인하면서 다듬었습니다. 이후 기존 동작과 데이터를 유지하는 조건으로 Next.js·React·TypeScript 전환까지 진행했습니다.

처음부터 이 모든 구성이 정해져 있던 것은 아닙니다. 초기 앱에는 바꾼 중량을 저장해도 다음 목표가 기본값으로 돌아가는 문제가 있었습니다. 세트 입력은 있어도 지금 어느 세트를 진행하는지 모호했고, 기록을 저장한 뒤에도 입력 화면이 남아 있었습니다. 하나씩 고치면서 제가 확인할 대상도 기능의 존재에서 **운동 전·중·후의 흐름이 이어지는지**로 바뀌었습니다.

## 오늘 할 일에 집중할 수 있는 제품으로 범위를 정했다

여러 운동을 관리하는 범용 기록장을 만들기보다, 턱걸이 목표에 필요한 맨몸·중량 운동과 측정, 휴식으로 범위를 좁혔습니다. 로그인과 서버 동기화도 넣지 않았습니다. 개인적으로 바로 쓰는 도구를 만드는 데 먼저 집중하고, 기록은 브라우저에 저장하며 JSON 백업으로 옮길 수 있게 했습니다.

화면은 사용하는 시점에 따라 나눴습니다. 운동 탭은 오늘 할 일과 현재 진행을, 달력·기록은 과거 수행과 측정의 변화를, 설정·백업은 앞으로의 일정과 기록 관리를 맡습니다. 최고 기록과 다음 목표가 같은 숫자를 보여주는 것이 아니라, 서로 다른 질문에 답하도록 했습니다.

예를 들어 훈련 목표를 한 단계 올렸다고 실제 최대 수행 횟수가 늘었다고 표시하지 않습니다. 측정 기록이 없으면 최고 기록은 미측정으로 남기고, 첫 운동을 제안하는 계산용 기본값은 따로 사용합니다. 계획상 휴식과 실제로 남긴 휴식도 구별했습니다. 달력에 일정이 있다는 사실을 운동한 사실로 바꾸지 않으려는 선택이었습니다.

이렇게 범위를 정하니 새로운 정보를 넣을 때도 기준이 생겼습니다. 더 많은 수치를 보여줄 수 있는지가 아니라, 운동할 때 무엇을 해야 하는지 또는 기록을 돌아볼 때 무엇을 알 수 있는지를 먼저 봤습니다.

## 기록·추천·달력이 같은 수행을 읽게 했다

초기 추천 문제를 고치려면 저장한 중량을 화면에 다시 보여주는 것만으로는 부족했습니다. 실제 수행이 다음 계획을 계산하는 기준으로 들어가야 했습니다.

추천은 대상 날짜 이전의 기록을 순서대로 읽습니다. 중량 예정이었어도 맨몸으로 기록했다면 실제 맨몸 수행을 사용합니다. 휴식이나 과거의 미기록 날짜를 운동한 것으로 세지 않고, 앞으로의 일정은 아직 수행하지 않은 계획으로 읽습니다. 과거 기록을 수정하면 그 이후 목표도 다시 계산합니다.

중량이 바뀌면 연속 성공의 기준도 바뀝니다. 이전 무게에서의 성공을 새 무게의 성공으로 이어 세지 않도록, 실제 중량이 달라졌을 때 성공 횟수를 초기화하고 그 기록의 목표와 수행을 비교했습니다. 요일 변경은 다음 날부터 적용하고 과거의 일정 이력은 유지했습니다.

단순히 모든 화면을 같은 값으로 채우는 문제가 아니었습니다. 입력 화면은 지금 수행할 목표를, 기록 화면은 당시 수행한 값을, 추천은 그 이력을 읽은 다음 계획을 보여줘야 했습니다. **하나의 기록이 어느 날짜의 어떤 판단에 쓰이는지**를 정해야 화면 사이의 불일치를 설명할 수 있었습니다.

## 운동 중에는 입력보다 진행 상태가 먼저 보이도록

운동 화면에서는 숫자 폼보다 세트를 진행하는 경험이 중요했습니다. 완료한 세트, 지금 진행하는 세트, 아직 시작하지 않은 세트를 구별하고 순서대로 열도록 했습니다. 손가락이 누른 영역을 가릴 수 있으니 터치 반응은 화면의 토스트로도 알려주도록 요청했습니다.

입력한 숫자가 있다는 것과 운동을 완료했다는 것도 달랐습니다. 세트에 목표 횟수가 미리 들어 있어도 마지막 세트를 마치기 전에는 완료 기록으로 저장할 수 없게 했습니다. 반대로 이미 완료한 기록을 수정할 때는 새 운동을 처음부터 진행하도록 만들면 안 됐습니다. 새 기록과 수정의 저장 조건을 나눈 이유입니다.

앱을 나갔다 돌아오는 경우에는 진행 초안을 복원하되 완료 이력과 섞지 않았습니다. 날짜·운동 종류별로 보관하고 목표와 보관 시간을 확인합니다. 종류를 바꿨다가 돌아오거나 새로고침했을 때도 입력 맥락이 유지되는지 살폈습니다.

저장 이후에는 입력 폼 대신 완료한 기록을 보여주고, 수정은 별도 행동으로 뒀습니다. 달력에서 과거 날짜를 고르는 것과 오늘의 운동으로 돌아오는 것도 다른 흐름으로 다뤘습니다. 이 과정에서 저장 버튼 하나를 고치는 일보다, 저장 전후에 사용자가 어느 상태에 있는지 설명하는 일이 더 중요해졌습니다.

## 화면이 완성된 뒤에는 변경하기 쉬운 구조가 필요했다

기능과 표현을 반복해서 다듬자 원래 HTML에는 계산·저장·화면 코드와 후속 스크립트가 겹쳤습니다. 나중에 붙인 코드가 입력을 숨기거나 DOM을 옮기고, 이전 핸들러의 동작을 다시 바꿨습니다. 새 화면을 하나 더 붙이는 방식으로는 어느 코드가 최종 상태를 결정하는지 따라가기 어려워졌습니다.

Next.js로 전환할 때 제가 요구한 것은 코드의 모양을 바꾸는 일이 아니었습니다. **기존 제품의 기능·디자인·기록을 유지하면서, 다음 변경을 검증할 수 있는 구조로 옮기는 것**이었습니다. AI에 원본 소스와 테스트, 저장 형식, 실제 화면을 먼저 확보하고 책임을 나눠 구현하도록 요청했습니다. 인증과 DB는 이 작업에 섞지 않았습니다.

구현에서는 화면을 운동·달력·측정·설정·백업 기능으로 나누고, 추천과 측정 계산은 순수 도메인 모듈로, 브라우저 저장과 데이터 이전은 저장소 계층으로 분리했습니다. 실제 UI와 테스트가 같은 TypeScript 계산 모듈을 사용하도록 했습니다. 테스트용 계산만 맞고 앱 안의 별도 계산은 틀릴 수 있는 구조를 피하려는 방향이었습니다.

기존 디자인을 다시 꾸미는 것도 이번 전환의 목적은 아니었습니다. 원래 화면을 비교 기준으로 두고 호환 스타일을 유지하며, 새 영역은 CSS Modules로 분리했습니다. 기술 구조가 달라졌다는 이유로 이미 익숙해진 사용 경험까지 함께 바꾸지 않도록 했습니다.

## 기록을 가진 앱의 전환은 데이터부터 지켜야 했다

브라우저 저장형 앱에서 코드만 잘 옮겨도 기록이 사라지면 사용할 수 없습니다. 기존 저장 키를 바로 새 형식으로 덮어쓰는 대신, 원본을 보존한 채 검증한 데이터를 별도 키에 저장하는 방식을 사용했습니다. 원본 스냅샷과 이전 저장본도 나눴습니다.

여기서는 정상 데이터의 읽기만 확인하지 않았습니다. 이전을 다시 실행해도 같은 결과가 나오는지, 알 수 없는 필드와 과거 형식이 유지되는지, 손상된 JSON이나 저장 실패가 원본을 덮지 않는지 확인했습니다. 가져오기에서도 빈 객체를 유효한 백업으로 취급하지 않도록 했습니다.

새 앱을 별도 도메인에 배포하면 기존 브라우저의 기록을 자동으로 읽을 수 없습니다. 그래서 JSON 내보내기·가져오기 경로를 함께 제공했습니다. 원본 앱을 유지한 채 전환한 앱을 별도로 검증한 것도 같은 이유였습니다. 배포를 되돌리는 것과 새 앱에서 추가한 기록을 되돌리는 것은 다르므로, 데이터 이동을 코드 배포의 부속 작업으로 두지 않았습니다.

## AI의 완료 보고 대신 같은 상황을 다시 실행했다

AI를 활용하면서 가장 자주 생긴 간격은 ‘구현했다’는 설명과 실제 사용 결과 사이였습니다. 그래서 전환 때는 요구사항을 문장으로 전달하는 데서 멈추지 않고, 원본과 새 앱이 같은 입력에서 무엇을 보여줘야 하는지 비교할 수 있도록 했습니다.

기존 함수 실행으로 기대값을 만들고, 미측정·실제 수행·휴식·과거 수정·중량 변경·손상된 백업·진행 초안 같은 조건을 고정 데이터로 준비했습니다. 브라우저에서는 저장·수정·삭제·백업 복원을 실제 버튼으로 실행했습니다. 화면 비교도 빈 페이지 하나가 아니라 입력 중, 완료 조회, 모달과 밝은·어두운 테마까지 포함했습니다.

다섯 화면 크기에서 같은 시나리오를 반복한 검사를 포함해, 425건의 브라우저 검사가 로컬과 배포 환경에서 각각 통과했습니다. 추천 계산뿐 아니라 기록을 입력하고 다시 읽는 전체 경로를 확인한 결과입니다.

PWA에서는 개발 서버와 배포 결과가 다를 수 있다는 것도 드러났습니다. 로컬 빌드의 자산 이름을 캐시 대상으로 삼았지만, 배포된 앱에서 참조하는 자산과 맞지 않아 오프라인 캐시가 실패했습니다. 최종 구현은 배포 HTML에서 실제 JS·CSS 주소를 찾고, 필요한 자산을 확보한 뒤 화면을 캐시하도록 바뀌었습니다. 온라인에서 한 번 더 새로고침하지 않아도 첫 진입 뒤 오프라인으로 다시 열리는지 별도로 검사했습니다.

AI는 이 수정의 구현과 브라우저 검증을 실행했고, 저는 제품의 요구사항과 전환 조건, 비교 기준을 정했습니다. 직접 사용하며 어긋난 흐름은 다시 설명했습니다. 구현을 위임해도 무엇을 유지해야 하는지와 무엇을 확인한 뒤 다음 단계로 갈지는 정해야 했습니다.

## 기능을 만드는 것에서 사용할 수 있는 제품을 끝내는 것으로

지금 앱에는 오늘 운동의 확인과 세트 진행, 기록 조회·수정, 달력과 측정 현황, 일정 설정과 백업이 연결돼 있습니다. Next.js 전환본도 구현을 마치고 [별도 배포 환경](https://pullup-30-next-preview-dakqyry9r-justinjeong-1612s-projects.vercel.app/)에서 브라우저 비교와 오프라인 검증을 마쳤습니다. 기존 운영 앱은 그대로 유지했습니다. 실제 iPhone·Android의 설치 경험과 운영 도메인 전환은 그 다음 확인 대상으로 분리했습니다.

처음에는 다음 추천이 기본값으로 돌아가는 것이 가장 눈에 띄는 문제였습니다. 전체를 만들고 나니 추천 하나만 맞는 것으로는 충분하지 않았습니다. 진행 중인 입력은 이어져야 하고, 완료 기록은 다시 읽을 수 있어야 하며, 구조를 바꿔도 쌓아 둔 기록은 남아야 했습니다.

돌아보면 AI 덕분에 구현을 넓게 시도할 수 있었지만, 제품이 좋아지는 방향까지 자동으로 정해지지는 않았습니다. 실제로 사용해 보고 기대와 다른 장면을 설명하고, 그 장면을 다시 확인할 기준으로 바꾸는 과정이 필요했습니다. 작은 개인 앱에서도 제가 끝내야 할 일은 화면을 채우는 것보다, 사용자가 다음 날 다시 열어 이어서 사용할 수 있는 흐름을 만드는 쪽에 가까웠습니다.
