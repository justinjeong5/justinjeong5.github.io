응답이 왔다고 해서 지금 화면에 적용해도 되는 것은 아니다. 사용자가 새 요청을 시작했다면 그 응답이 이전 요청의 것인지부터 구분해야 한다. 빈 결과도 마찬가지다. “없음”이 어느 요청에 대한 답인지가 중요하다.

광고 판정에서 이전의 빈 조회 결과가 최신 요청의 결과처럼 사용되는 경로를 다뤘다. 나는 고정 대기 시간을 늘리는 대신 보너스 판정의 요청을 일반 조회와 분리하는 방향을 택했다.

## 전체 조회 정책을 바꾸지 않은 이유

공용 fetcher와 일반 Query 정책은 유지했다. 특정 판정의 최신성을 다루기 위해 전체 캐시나 다른 광고 흐름까지 바꿀 필요는 없었다. 필요한 처리를 어느 요청에 둘지 먼저 좁혔다.

구현에서는 요청 키와 세대 값을 사용해 현재 요청에 대응하는 결과만 상태에 반영하도록 했다. 재조회·초기화·비활성화와 정리 과정에서는 이전 요청의 취소 신호와 세대 변경을 함께 다뤘다.

## 결과를 쓰는 순간만 확인하면 끝날까

이전 요청이 끝나며 실행하는 정리 작업도 새 요청에 영향을 줄 수 있다. 이전 요청의 cleanup이 현재 활성 controller를 지우면, 응답 적용을 막아둔 것만으로는 충분하지 않다. 결과를 반영할 때뿐 아니라 정리할 때도 자신이 어느 요청에 속하는지 확인하도록 했다.

mock HTTP 클라이언트로는 취소 신호 전달과 새로운 응답 반영 시나리오를 구성했다. 이 테스트는 웹의 요청·상태 처리를 다루며 실제 서버의 취소나 기기의 광고 결과까지 확인한 것은 아니다.

이 경험에서 남은 질문은 “요청이 끝났는가”보다 “어느 요청이 지금 상태를 바꿀 수 있는가”다. 취소 신호와 최신 결과 판정, 정리 작업은 모두 필요할 수 있지만 같은 역할을 하지는 않는다. [브릿지 관측](/cases/bridge-observation-contract)에서도 새 처리를 넣으면서 기존 호출의 책임은 따로 유지했다.
