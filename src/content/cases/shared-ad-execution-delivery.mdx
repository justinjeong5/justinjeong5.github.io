여러 종류의 광고가 한 제품에 들어오면 서버가 고른 후보를 실제로 실행하고, 그 결과를 다음 미션이나 리워드 안내로 연결해야 한다. 공급사마다 실행과 완료를 알려주는 방식이 달라 제품 화면이 모든 SDK를 직접 알게 하면 다음 공급을 붙일 때마다 화면의 판단도 바뀐다.

1월에는 광고 후보를 순회하는 제품 흐름과 공급사별 표시·완료를 읽는 adapter를 나눴다. 이후 4월에 다른 팀의 제품을 지원하면서 그 공통 코드만으로는 끝나지 않는 조건을 만났다. 내부 노출은 집계되는데 공급사 로그에는 실행 흔적이 없었다.

서버가 같으니 광고 데이터도 같다는 설명만으로는 부족했다. **실제로 그 데이터를 읽고 실행하는 FE 소비자도 같은가**를 확인해야 했다.

## 제품이 원하는 결과와 공급사가 보내는 사건

공통 흐름은 후보를 고르고 실행 결과에 따라 다음 행동을 정했다. 공급사 adapter는 SDK 호출과 시작·완료·닫힘 신호를 제품이 읽을 결과로 바꿨다.

1월의 handler에서는 공급사 완료 신호가 왔는지를 기록하고 닫힘 때 Promise를 끝냈다. 이 광고의 완료 조건은 클릭이었으므로, 사용자가 닫았다는 사건만으로 완료를 만들어서는 안 됐다. 완료 뒤 닫힘과 완료 없는 닫힘은 다른 결과였다. 영상의 시청 완료와도 같은 이름으로 묶지 않았다.

| 실행 순서 | 제품이 읽을 의미 |
| --- | --- |
| 공급사 완료 신호 → 닫힘 | 해당 광고의 완료 조건을 충족하고 종료 |
| 완료 신호 없이 닫힘 | 미완료로 종료 |
| tracker·BI의 동기 호출 오류 | 실제 광고 실행의 결과와 분리 |

두 완료 순서는 별도 테스트 조건으로 남겼다. 관측 호출의 동기 예외를 잡는 코드도 있었다. 관측을 더하는 것이 광고 자체의 실행을 깨뜨리지 않게 한 경계다.

영상 코어를 나눈 작업도 비슷했다. 재생·source·가시성·음소거는 앱 내부 코어에 두고, 광고 추적과 외부 클릭 정책은 제품 wrapper에 남겼다. wrapper가 실제로 새 코어를 소비하는 구조였다. 재사용할 재생 기능과 상품이 정하는 다음 행동을 같은 모듈에 넣지 않았다.

## 같은 서버를 쓰는 다른 화면에는 실행 코드가 없었다

4월 문제를 읽어 보니 타팀 FE에는 해당 광고 source를 처리할 handler가 없었다. 공용 데이터에 SDK 정보가 들어와도 소비자는 기본 fallback으로 가고 있었다. 내부 tracker가 호출된 것은 공급사 SDK가 시작됐다는 증거가 아니었다.

나는 서버의 입력뿐 아니라 소비자의 분기와 공급사 실행 경로를 이어서 확인했다. source·provider와 필수 SDK parameter를 읽고 실제 호출에 전달할 조건을 정했다. 서버 parameter가 nested 또는 root 형태로 들어오는 경로도 구별했다.

SDK 정보가 없거나 다른 provider인 조건, 필수값 누락과 유효한 입력을 나눈 테스트를 보강했다. 잘못된 입력을 실제 실행 가능한 후보처럼 읽지 않게 하는 준비 단계였다.

## adapter 하나와 제품의 loop는 함께 연결돼야 했다

입력 검증 뒤 SDK 호출·callback·timeout을 Promise 결과로 연결하고, 그 결과를 소비하는 제품의 광고 순회 흐름에도 넣었다. 실행 함수만 추가하고 실제 source 분기에 연결하지 않으면 이전 fallback이 계속 결과를 설명할 수 있다.

4월 소비자의 boolean 결과와 1월 handler의 완료 판정도 이름만 보고 같은 것으로 취급하지 않았다. 공급사가 보내는 사건과 제품이 요구하는 성공 조건을 해당 소비 계약에 맞춰 읽어야 했다.

```text
서버의 광고 후보
  → 실행 가능한 source·입력 확인
  → 공급사 adapter
  → 해당 제품이 읽을 완료 결과
  → 다음 후보 또는 다음 참여
```

공통화를 설명할 때 파일이 어디로 이동했는지보다, 실제 호출자가 어떤 입력과 결과를 사용하고 있는지가 더 중요했다.

## 낯선 제품의 전달은 소유 팀과 함께 확인했다

제품을 소유한 팀에는 로컬 실행·진입·전체 QA의 도움이 필요하다고 설명했다. 내가 구현을 준비할 수 있다는 사실과 그 제품의 모든 동작을 혼자 확인할 수 있다는 것은 달랐다.

4월 17일에는 누락된 실행 경로와 검증 환경을 공유했다. 이후 SDK QA를 진행하고, 21일에는 소유 제품의 담당자들과 광고뿐 아니라 기존 콘텐츠의 동작도 확인한 뒤 배포했다. 확인과 배포 뒤 감사의 반응이 이어졌다.

그 결과는 공용 입력이 실제 다른 제품의 SDK 실행까지 연결된 것이었다. 공급사 SDK 자체를 만든 경험과는 다르지만, 소비 계약을 구현하고 해당 제품에서 사용할 수 있는 상태로 전달한 책임은 내가 맡았다.

## 공용 코드의 완료는 소비자에서 확인된다

처음에는 공급사의 사건을 제품 결과로 바꾸는 흐름을 만들었다. 다른 팀을 지원하면서는 그 인터페이스가 실제로 사용되는지까지 확인해야 했다. 내부 집계와 공급사 실행이 달랐던 장면이 이 차이를 선명하게 보여줬다.

공용 모듈에 기능이 있다는 사실만으로 제품에 기능이 있다는 뜻은 아니었다. 입력 검증과 결과의 의미, 실제 소비자의 분기, 소유 팀의 QA와 배포가 연결돼야 했다. 다음에 공용 기능을 만든다면 모듈의 API와 함께 그것을 읽을 소비자와 전달의 끝점부터 찾고 싶다.
