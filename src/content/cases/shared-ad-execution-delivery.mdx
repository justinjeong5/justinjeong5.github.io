제품에 여러 종류의 광고가 들어오면 서버가 고른 후보를 실행하고 그 결과를 다음 미션이나 리워드 안내로 연결해야 합니다. 그런데 공급사마다 실행과 완료를 알려주는 방식이 다릅니다. 화면에서 모든 SDK를 직접 다루면 새 공급사를 붙일 때마다 화면의 판단도 바꿔야 했습니다.

저는 1월에 광고 후보를 순회하는 제품 흐름과 공급사별 표시·완료를 처리하는 adapter를 나눴습니다. 이후 4월에 다른 팀의 제품을 지원하면서, 그 제품에서도 광고 실행 코드가 제대로 연결됐는지 확인해야 했습니다. 내부에는 노출이 집계되는데 공급사 로그에는 실행 흔적이 없는 문제가 있었습니다.

같은 서버에서 광고 데이터를 받더라도 SDK를 실행하는 코드까지 같다고 볼 수는 없었습니다. 그래서 **다른 팀의 FE에도 해당 SDK를 실행하는 코드가 연결돼 있는지** 확인하며, 입력 데이터와 광고 종류에 따른 실행 분기를 살폈습니다.

## 제품이 원하는 결과와 공급사가 보내는 사건

공통 흐름은 후보를 고르고 실행 결과에 따라 다음 행동을 정했습니다. 공급사 adapter는 SDK 호출과 시작·완료·닫힘 신호를 제품이 읽을 결과로 바꿨습니다.

1월의 handler에서는 공급사 완료 신호가 왔는지를 기록하고 닫힘 때 Promise를 끝냈습니다. 이 광고의 완료 조건은 클릭이었으므로, 사용자가 닫았다는 사건만으로 완료를 만들어서는 안 됐습니다. 완료 뒤 닫힘과 완료 없는 닫힘은 다른 결과였습니다. 영상의 시청 완료와도 같은 이름으로 묶지 않았습니다.

| 실행 순서 | 제품이 읽을 의미 |
| --- | --- |
| 공급사 완료 신호 → 닫힘 | 해당 광고의 완료 조건을 충족하고 종료 |
| 완료 신호 없이 닫힘 | 미완료로 종료 |
| tracker·BI의 동기 호출 오류 | 실제 광고 실행의 결과와 분리 |

두 완료 순서는 별도 테스트 조건으로 남겼습니다. 관측 호출의 동기 예외를 잡는 코드도 있었습니다. 관측 호출의 동기 예외가 광고 실행에 영향을 주지 않도록 한 처리입니다.

## 같은 서버를 쓰는 다른 화면에는 실행 코드가 없었다

4월의 문제를 조사해 보니 타팀 FE에는 해당 광고 source를 처리할 handler가 없었습니다. 공용 데이터에 SDK 정보가 들어와도, 그 제품에서는 기본 fallback이 실행되고 있었습니다. 내부 tracker가 호출된 것은 공급사 SDK가 시작됐다는 증거가 아니었습니다.

저는 서버가 내려준 입력값뿐 아니라 제품 코드의 실행 분기와 공급사 SDK 호출 경로까지 이어서 확인했습니다. source·provider와 필수 SDK parameter를 읽고 실제 호출에 전달할 조건을 정했습니다. 서버 parameter가 nested 또는 root 형태로 들어오는 경로도 구별했습니다.

SDK 정보가 없거나 다른 provider인 조건, 필수값 누락과 유효한 입력을 나눈 테스트를 보강했습니다. 잘못된 입력을 실제 실행 가능한 후보처럼 읽지 않게 하는 준비 단계였습니다.

## adapter 하나와 제품의 loop는 함께 연결돼야 했다

입력 검증 뒤 SDK 호출·callback·timeout을 Promise 결과로 연결하고, 그 결과를 처리하는 제품의 광고 후보 순회 로직에도 연결했습니다. 실행 함수만 추가하고 해당 source 분기에 연결하지 않으면 SDK 대신 기존 fallback이 계속 실행될 수 있습니다.

4월에 연결한 제품의 boolean 결과와 1월 handler의 완료 판정도 이름만 보고 같은 것으로 취급하지 않았습니다. 공급사가 보내는 신호를 각 제품이 정한 성공 조건에 맞춰 해석해야 했습니다.

```text
서버의 광고 후보
  → 실행 가능한 source·입력 확인
  → 공급사 adapter
  → 해당 제품이 읽을 완료 결과
  → 다음 후보 또는 다음 참여
```

## 낯선 제품의 전달은 소유 팀과 함께 확인했다

제품을 소유한 팀에는 로컬 실행·진입·전체 QA의 도움이 필요하다고 설명했습니다. 제가 구현을 준비할 수 있다는 사실과 그 제품의 모든 동작을 혼자 확인할 수 있다는 것은 달랐습니다.

4월 17일에는 누락된 실행 경로와 검증 환경을 공유했습니다. 이후 SDK QA를 진행하고, 21일에는 소유 제품의 담당자들과 광고뿐 아니라 기존 콘텐츠의 동작도 확인한 뒤 배포했습니다. 확인과 배포 뒤 감사의 반응이 이어졌습니다.

다른 팀 제품이 서버에서 받은 광고 정보로 실제 SDK를 실행하도록 연결했습니다. 공급사 SDK 자체를 개발한 것은 아니지만, 해당 제품이 기대하는 입력과 완료 결과에 맞춰 연동하고 소유 팀과 QA·배포까지 함께 진행했습니다.

## 공용 코드가 실제 제품에서도 실행되도록

서버에서 같은 광고 데이터를 받아도 다른 팀의 화면에는 SDK 실행 코드가 없었습니다. 해당 source 분기에 공급사 실행 코드를 연결하고 소유 팀과 기존 콘텐츠까지 QA한 뒤 배포했습니다. 공용 함수가 있는 것만으로 그 제품에서 광고가 실행되는 것은 아니었습니다.
