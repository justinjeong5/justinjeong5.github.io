다른 팀의 제품에서 광고 노출은 내부에 기록됐지만 공급사 쪽에는 실행 흔적이 없었습니다. 서버가 광고 후보를 내려주고 내부 추적이 호출됐다는 사실만으로 실제 공급사 SDK가 실행됐다고 판단할 수 없는 상황이었습니다.

이 글은 **공용 광고 데이터를 받는 제품마다 실행 코드까지 연결돼 있는지 확인하고, 빠진 경로를 제품 소유 팀과 함께 전달한 과정**입니다.

## 같은 후보를 받아도 같은 실행이 일어나지는 않았다

저는 먼저 서버 응답에서 공급사를 가리키는 정보가 내려오는지와 해당 제품의 FE가 그 정보를 어떻게 처리하는지를 따로 봤습니다. 조사 결과, 타팀 FE에는 이 광고 source를 맡을 handler가 없어 기본 fallback이 실행되고 있었습니다. 내부 tracker 호출은 이 경로에서도 일어날 수 있어 SDK 실행의 증거가 아니었습니다.

1월에 제가 작업한 공용 광고 흐름에서는 후보를 고르는 제품 로직과 SDK의 시작·완료·닫힘 신호를 해석하는 공급사 adapter를 나눴습니다. 그러나 그 구조가 있다고 해서 다른 제품의 호출 분기까지 자동으로 생기는 것은 아니었습니다. 4월에는 **실행이 빠진 제품의 경계**를 확인하는 데 집중했습니다.

## 실행 가능한 입력부터 제품의 결과까지 연결했다

서버의 source·provider와 필수 SDK parameter를 확인하고, 유효한 후보일 때만 공급사 실행 함수로 보내도록 했습니다. 실제 입력이 중첩된 형태 또는 최상위 형태로 올 수 있는 조건도 구분했습니다. SDK 정보가 없거나 다른 provider이거나 필수값이 빠졌을 때는 실행 가능한 광고처럼 다루지 않도록 테스트했습니다.

실행 함수만 추가하면 기존 fallback이 계속 선택될 수 있었습니다. 그래서 해당 제품의 광고 후보 순회 분기에도 adapter를 연결하고, SDK callback과 timeout의 결과를 그 제품이 읽는 완료 결과로 변환했습니다. 1월 adapter의 완료 조건과 4월 제품의 boolean 결과는 같은 이름으로 뭉뚱그리지 않았습니다. 공급사가 보낸 신호를 제품의 성공 조건에 맞게 해석해야 했기 때문입니다.

```text
서버의 후보 → source·입력 확인 → 공급사 SDK 실행
                                  → 제품의 완료 결과 → 다음 후보 또는 참여
```

## 제품 소유 팀과 끝까지 확인했다

낯선 제품의 전체 동작을 제가 혼자 보증할 수는 없었습니다. 4월 17일 누락 경로와 검증 환경을 공유하고, 소유 팀에 로컬 진입과 전체 QA 협조를 요청했습니다. 이후 SDK 실행을 확인했으며, 21일에는 담당자들과 광고뿐 아니라 기존 콘텐츠의 동작도 확인한 뒤 배포했습니다.

제가 해결한 것은 공급사 SDK 자체의 문제가 아니라 **서버의 광고 후보와 타제품 FE의 실제 실행 사이에 빠진 연결**이었습니다. 입력 검증과 호출 분기, 결과 해석, 소유 팀의 QA를 이어서 전달했습니다. 이 경험은 공용 인터페이스를 만든 뒤에도 각 제품의 실제 실행 경로를 별도로 검증해야 한다는 기준으로 남았습니다.
