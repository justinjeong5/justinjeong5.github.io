운영자가 여러 미션을 세트로 구성하고 사용자는 그중 하나를 골라 참여하는 상품을 만들었다. 사용자에게는 선택 화면이 하나 추가되지만, 운영자는 기존 미션을 복사하고 그룹과 옵션을 바꾸며 새로운 구성을 저장한다. 두 화면이 같은 상품의 규칙을 읽어야 했다.

기존 목록을 그대로 검증하면 새 상품의 세트 단위를 놓친다. 반대로 모든 미션을 새 규칙으로 바꾸면 기존 상품의 설정이 달라진다. 새 화면을 만드는 일과 기존 설정의 의미를 지키는 일이 함께 있었다.

나는 Gateway의 조회·쓰기 연결과 운영 화면의 검증·복제 입력을 수정했고, 동료들과 사용자 참여 FE를 통합했다. 서버는 상품의 저장·선택·참여 정책을 제공했다.

## 선택한 화면과 제출한 선택은 달랐다

참여 화면은 세트 목록과 이미 제출했는지를 조회했다. 기존 선택이 있다면 다시 고르게 하지 않고 기존 참여 화면으로 연결했다. 아직 제출하지 않았다면 세트를 살펴보고 하나를 선택해 제출할 수 있게 했다.

화면에서 미리 보는 선택과 서버가 받은 선택은 다른 상태였다. 제출 성공 후에는 기존 query를 유지해 참여 화면으로 이어 가고, 실패하면 안내하면서 제출 중 상태를 풀었다. 새 선택 화면이 기존 참여 경로를 대체하는 것이 아니라, 사용자가 들어갈 미션을 확정하는 앞단이 된 것이다.

## 검증할 단위를 상품에 맞췄다

운영 QA에서는 기존 목록을 검사하는 범위와 세트마다 검사할 범위를 구별했다. 새 상품은 기여 확인(eligibility) 유형의 미션이 세트마다 최대 하나인지 검사하고, 기존 상품은 원래 목록 기준을 유지했다.

전체 목록에 같은 검증기를 한 번 적용하면 다른 세트의 미션이 서로 영향을 줄 수 있다. UI가 나뉘었다는 이유만으로 규칙이 나뉜 것도 아니다. 검증 단위를 실제 저장·참여의 단위에 맞춰야 했다.

기존 단가 값과 새 설정의 저장 관계도 QA에서 확인했다. 한 화면이 정상적으로 저장되는지만 보는 대신, 다른 상품의 입력이 남아 있는 조건을 함께 읽었다.

## 복제는 같은 내용을 새 대상으로 만드는 일이다

처음에는 복제 문제를 재현하지 못했다. 동료가 캠페인을 복사하고 그룹과 옵션을 바꾼 뒤, 기존 미션을 복사하고 다시 세트를 복제하는 순서를 전달했다. 같은 순서를 따라가자 단순히 새 세트 하나를 만드는 테스트에서는 보이지 않던 문제가 드러났다.

기존 미션 ID를 그대로 넘기면 새 구성을 만들려던 동작이 기존 대상을 가리킬 수 있었다. 전체 세트 객체를 복사하기보다 **새 template 선택과 복사할 missions 입력을 분리**하고, 기존 미션 식별자를 제거했다. 세트의 제목·설명도 실제 대상을 표시하도록 보완했다.

```text
복사할 미션의 내용
  + 새 세트를 만들 template
  - 기존 미션의 식별자
  → 새로운 구성의 입력
```

내용을 재사용하는 것과 같은 대상을 재사용하는 것은 다른 일이다. 기존 객체가 편리하다는 이유로 입력 전체를 복사하면 서버가 구별해야 할 새 생성과 기존 관계가 섞일 수 있었다.

## 코드 통합 뒤에도 전달할 경로가 남았다

서버 반영 뒤 FE를 전달했지만 Gateway 연결이 빠진 조건이 다시 발견됐다. 화면·서버·Gateway가 함께 연결돼야 운영 설정과 실제 참여가 이어질 수 있었다.

수정과 배포 보고 뒤 동료의 특정 동작 확인을 받았다. 이미 잘못 저장된 데이터가 자동으로 고쳐진 것은 아니어서 그 데이터를 재사용하지 않도록 안내했다. 코드를 고친 결과와 이전 데이터가 유지하는 결과는 별개였다.

이 과정에서 사용한 확인은 재현 순서를 맞춘 QA와 동료의 동작 확인이었다. 신규 설정의 저장, 기존 미션의 반복 복사처럼 실제 운영자가 만드는 입력을 따라가는 것이 중요했다.

## 두 사용자가 같은 상품을 다루게 하기

새 상품은 운영자의 세트 구성에서 사용자 선택과 기존 참여까지 연결됐다. 검증 단위를 나누고 복제 입력을 정리하며, 기존 상품의 규칙을 그대로 유지할 범위도 남겼다.

특히 재현 순서를 공유한 장면이 기억에 남는다. 내가 처음 만든 단순 입력에서는 정상이었지만 운영자는 기존 캠페인과 미션을 계속 재사용하고 있었다. 운영 도구에서는 새 기능의 첫 입력뿐 아니라, 이전 작업이 남긴 값을 가지고 다음 작업을 만드는 방식까지 이해해야 했다. 그 실제 순서가 설정 모델을 다시 판단하게 했다.
