운영자가 여러 미션을 세트로 구성하고 사용자는 그중 하나를 골라 참여하는 상품을 만들었습니다. 저는 운영 화면의 검증·복제 입력과 Gateway의 조회·쓰기 연결을 수정하고, 동료들과 참여 화면을 통합했습니다. **운영자가 저장한 선택지가 사용자의 제출과 기존 참여까지 이어져야** 한 상품이 완성됩니다.

새 상품은 세트마다 제한을 확인해야 했습니다. 기존 목록 전체에 같은 규칙을 적용하면 기존 상품의 설정까지 달라지므로, 새 상품의 검증 범위만 나눠야 했습니다.

서버는 저장·선택·참여 정책을 제공했습니다.

## 선택한 화면과 제출한 선택은 달랐다

참여 화면은 세트 목록과 이미 제출했는지를 조회했습니다. 기존 선택이 있다면 다시 고르게 하지 않고 기존 참여 화면으로 연결했습니다. 아직 제출하지 않았다면 세트를 살펴보고 하나를 선택해 제출할 수 있게 했습니다.

화면에서 미리 고른 상태만으로는 서버에 선택이 제출된 것이 아닙니다. 제출에 성공하면 기존 query를 유지해 참여 화면으로 이어 가고, 실패하면 안내하면서 제출 중 상태를 풀었습니다. 선택 화면에서 들어갈 미션을 확정한 뒤 기존 참여 경로를 사용하도록 했습니다.

## 검증할 단위를 상품에 맞췄다

운영 QA에서는 기존 목록을 검사하는 범위와 세트마다 검사할 범위를 구별했습니다. 새 상품은 기여 확인(eligibility) 유형의 미션이 세트마다 최대 하나인지 검사하고, 기존 상품은 원래 목록 기준을 유지했습니다.

전체 목록에 검증기를 한 번 적용하면 서로 다른 세트의 미션이 같은 제한을 적용받을 수 있었습니다. UI를 세트별로 나누는 것과 함께, 실제 저장·참여 단위에 맞춰 검증 범위도 나눴습니다.

QA에서는 새 상품의 저장뿐 아니라 기존 상품의 입력이 같은 변경 뒤에도 유지되는지 확인했습니다.

## 복제는 같은 내용을 새 대상으로 만드는 일이다

복제 문제는 새 세트 하나를 만드는 테스트에서는 드러나지 않았습니다. 동료가 실제 운영자가 캠페인·미션·세트를 차례로 복사하는 순서를 알려줬고, 그 순서로 재현했습니다.

기존 미션 ID를 그대로 넘기면 새 구성을 만들려던 동작이 기존 대상을 가리킬 수 있었습니다. 새 세트의 틀과 복사할 미션 내용을 따로 구성하고, 기존 미션 식별자를 제거했습니다.

복사할 내용은 남기고 기존 대상을 가리키는 관계만 뺀 것입니다. 운영 화면에서 새 상품을 만드는 행동이 서버에서도 새 대상으로 처리돼야 했습니다.

## 코드 통합 뒤에도 전달할 경로가 남았다

서버 반영 뒤 FE를 전달했지만 Gateway 연결이 빠진 조건이 다시 발견됐습니다. 화면·서버·Gateway가 함께 연결돼야 운영 설정과 실제 참여가 이어질 수 있었습니다.

수정과 배포 보고 뒤 동료의 동작 확인을 받았습니다. 이미 잘못 저장된 데이터가 자동으로 고쳐진 것은 아니어서 재사용하지 않도록 안내했습니다.

QA도 새 값을 한 번 넣는 순서뿐 아니라 운영자가 기존 값을 반복해서 복사하는 순서로 확인했습니다.

## 두 사용자가 같은 상품을 다루게 하기

새 상품은 운영자의 세트 구성에서 사용자 선택·제출과 기존 참여까지 연결됐습니다. 검증은 새 상품의 세트 단위로 제한하고 기존 상품의 규칙은 유지했습니다.

동료가 알려준 복사 순서에서 새 입력에 남으면 안 되는 식별자를 찾았습니다. 새 상품의 첫 저장뿐 아니라 **운영자가 이전 작업을 재사용하는 방식**까지 확인해야 같은 상품 규칙이 두 화면에서 이어졌습니다.
