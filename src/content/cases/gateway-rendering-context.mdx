파트너 앱에서 PlayHub Quest 참여 링크를 열었는데 다음 화면이 나오지 않았습니다. 게이트웨이는 목적지를 골랐고 목적지 응답도 도착했지만, 특정 Android WebView에서는 빈 화면이 남았습니다. **문제는 어디로 갈지 결정하는 단계가 아니라, 다음 라우트의 화면이 커밋되기를 기다리는 단계에 있었습니다.**

Quest의 진입 게이트웨이는 앱 연동 모듈이 준비되기를 기다리고, 앱이 지원하는 기능을 조회해 인앱 화면과 하이브리드 화면 중 하나를 고르는 프론트엔드 진입점입니다. 인앱 화면은 앱이 제공하는 기능으로 참여를 처리하고, 하이브리드 화면은 앱에서 시작하더라도 참여 일부를 외부 웹으로 이어갈 수 있습니다. 동료가 빈 화면을 재현한 조건을 함께 살펴본 뒤, 저는 라우트 전환을 없앤 PoC와 후속 구현을 진행했습니다.

## 응답은 왔는데 전환이 끝나지 않았다

이전 흐름에서 게이트웨이는 목적지 경로를 만든 다음 `router.replace`를 호출했습니다. 게이트웨이가 목적지 화면을 직접 그리지 않는 동안, 새 라우트의 화면이 커밋되어야 사용자가 다음 장면을 볼 수 있었습니다.

```text
Quest 진입
  → 앱 연동 모듈 초기화
  → 지원 기능 조회
  → 목적지 선택
  → router.replace(목적지)
  → 새 라우트의 화면 커밋
```

앞 단계가 늦는 것과 마지막 단계가 늦는 것은 해결 방법이 다릅니다. 진단용 이벤트에 문서 가시성, 타이머 지연, 라우트 응답의 도착 여부를 함께 남겨 분기했습니다. 게이트웨이가 목적지를 골랐다는 기록과 목적지의 RSC 응답 기록이 있는데도 빈 화면이 남아 있다면, 응답이 오지 않은 문제와 전환 커밋이 늦은 문제를 구별할 수 있습니다. 관찰된 사례는 후자였습니다. 따라서 기능 조회만 단축하거나 응답만 다시 받아서는 그 대기 구간을 없앨 수 없었습니다. 다만 **왜 해당 WebView에서 전환 커밋이 늦었는지**까지 확정한 것은 아닙니다.

문서 전체를 다시 여는 `window.location.replace`도 검토했지만, 일부 매체 WebView에서는 그 이동이 가로막히는 회귀가 확인됐습니다. 결국 선택한 방향은 다른 종류의 이동으로 바꾸는 것이 아니라, **게이트웨이와 목적지 사이의 이동 자체를 없애는 것**이었습니다.

## 라우트 이동을 없애고 실행 책임을 옮겼다

기능 조회 결과로 인앱 또는 하이브리드 화면을 고른 뒤, 게이트웨이의 현재 라우트에서 그 화면을 렌더했습니다. 목적지 페이지를 정적으로 가져와, 그 페이지 청크를 전환 시점에 따로 받는 대기 지점을 줄였습니다. 그만큼 첫 진입 번들이 커질 수 있다는 비용은 감수했습니다.

하지만 기존 목적지 라우트에는 화면 컴포넌트 외에도 역할이 있었습니다. 경로만 없애고 컴포넌트만 넣으면 다음 세 가지가 달라질 수 있었습니다.

| 기존 라우트가 맡던 일 | 이동을 없앤 뒤 필요한 처리 |
| --- | --- |
| URL의 `target`으로 실행 모드 전달 | 현재 주소의 쿼리만 갱신하고 반영을 확인 |
| 목적지 layout의 테마·광고 설정 | 직접 렌더에도 같은 셸 적용 |
| 전환을 기다리는 동안의 화면 | 로딩·복구 화면을 게이트웨이에서 관리 |

가장 미묘한 부분은 URL이었습니다. 하이브리드 화면의 모드는 `target` 쿼리 값에도 영향을 받습니다. 목적지를 고른 직후 URL을 읽는 훅이 아직 이전 값을 보고 있다면, 새 화면이 잘못된 모드로 시작할 수 있습니다. 그래서 `history.replaceState`로 **현재 pathname은 유지하고 쿼리만** 바꾼 뒤, `useSearchParams`가 변경된 `target`을 읽을 때 목적지를 렌더했습니다. 경로 전체를 다시 만들지 않아 기존 `basePath`도 건드리지 않았습니다.

아래는 실행 순서를 보이기 위한 재구성 코드이며 실제 회사 코드는 아닙니다.

```tsx
const params = useSearchParams();
const destination = resolveFromCapability(capability);

useEffect(() => {
  if (!destination || params.get("target") === "newTab") return;
  history.replaceState(null, "", queryOnlyWithTarget("newTab"));
}, [destination, params]);

if (!destination || params.get("target") !== "newTab") return <Loading />;
return <DestinationScreen kind={destination} />;
```

첫 번째 확인은 “어느 화면인가”, 두 번째 확인은 “그 화면이 읽을 실행 모드가 준비됐는가”입니다. 여기서 `target=newTab`은 하이브리드 화면에도 앱 안에서 진입했다는 맥락을 전달합니다. 이 값이 반영되기 전에는 로딩 화면을 유지했습니다.

이때 `target`은 기능 조회의 입력이 아니라 조회 결과를 URL에 남긴 출력입니다. 쿼리가 바뀔 때마다 기능 조회 effect를 다시 실행하면 스스로 기록한 결과 때문에 다시 목적지를 고르는 루프가 생길 수 있었습니다. effect가 비교하는 입력에서는 `target`을 제외하고, 같은 목적지를 다시 얻었을 때 진단 이벤트도 중복 발행하지 않도록 했습니다.

목적지의 layout도 그대로 통과하지 않습니다. 두 화면의 테마를 적용하고 하이브리드일 때만 광고 스크립트를 넣는 공통 셸을 만들어, 기존 목적지 라우트와 게이트웨이의 직접 렌더가 같은 구성을 사용하게 했습니다.

## 기다리는 화면과 늦게 온 결과

앱 연동 모듈이나 기능 조회를 기다리는 동안에도 빈 화면이 보이지 않도록, 목적지 결정 전의 로딩 화면을 반환하도록 바꿨습니다. 기존 복구 화면이 먼저 나타났더라도 목적지가 늦게 결정되면 실제 화면이 이를 대체합니다. 기능 조회에 실패한 경우에는 인앱 기능을 사용할 수 있다고 추정하지 않고 하이브리드 화면으로 진행합니다.

회귀 테스트에서는 초기화 전 대기, 기능 조회 실패, URL에 `target`이 반영되기 전의 렌더 차단, 늦은 결과와 언마운트, 같은 결과의 중복 이벤트를 각각 확인했습니다. 특히 목적지를 고른 것과 **그 목적지를 올바른 모드로 화면에 띄운 것**을 별도 조건으로 다뤘습니다.

6월에 이 변경은 제품 코드에 통합됐습니다. 확인된 결과는 게이트웨이에서 목적지로 넘어가는 소프트 라우트 전환을 제거하고, 직접 렌더 경로의 URL·레이아웃·대기 상태를 테스트로 보호한 것입니다. 모든 기기의 흰 화면이 사라졌다는 운영 결과나 WebView 엔진의 원인까지 입증한 것은 아닙니다.

이 사례가 보여주는 것은 “느린 응답을 빠르게 만들었다”가 아닙니다. **응답 이후에 멈춘 화면 전환을 제거하고, 그 전환이 전달하던 실행 조건을 직접 복원한 과정**입니다. 비슷한 진입 화면이라면 라우트 커밋을 기다리는 구간, 목적지가 URL에서 읽는 값, 건너뛴 layout과 대기 화면의 책임을 먼저 확인해야 합니다.
