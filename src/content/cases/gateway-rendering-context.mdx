참여 링크를 연 뒤 앱 안의 화면으로 갈지, 외부 웹 화면으로 갈지 선택하는 중간 단계가 있었다. publisher 초기화와 capability, 즉 해당 환경이 제공할 수 있는 기능을 읽고 목적지를 정했다.

이 단계에서 soft navigation을 하면 라우터 전환과 목적지 마운트 단계가 추가된다. 특정 Android WebView에서 빈 화면을 재현한 동료와 조건을 살펴보고, 나는 같은 경로에서 목적지 컴포넌트를 렌더하는 방향으로 PoC와 후속 구현을 진행했다. 여기서 다룰 질문은 **페이지를 이동하지 않는 대신 무엇을 더 동기화해야 하는가**다.

## 목적지보다 먼저 준비될 입력을 구별했다

publisher가 아직 준비되지 않았는데 capability를 읽거나, target이 URL에 반영되기 전에 외부 웹 모드를 렌더하면 다른 실행 환경으로 시작할 수 있었다. 기다릴 조건을 나누고 준비된 결과로 목적지를 선택했다.

capability 조회가 실패한 경우는 외부 웹으로 연결하는 fallback을 사용했다. 성공·실패의 경로가 모두 같은 화면 진입을 설명해야 했다.

## query는 바꾸되 pathname은 유지했다

soft navigation hop 대신 같은 route에서 컴포넌트를 합성했다. target을 바꿀 때는 search만 `history.replaceState`로 반영해 pathname과 basePath를 유지했고, 반영된 target을 읽은 뒤 올바른 모드를 렌더했다.

이 순서가 중요했다. target이 URL에 반영되기 전에 이전 입력으로 모드를 결정하면 의도한 실행 환경과 다른 화면을 시작할 수 있다. 상태를 바꾸는 일과 그 상태를 읽어 실행을 시작하는 일을 이어야 했다.

target을 주입한 변화 때문에 capability effect가 다시 실행되지 않도록, 그 입력에서는 target을 제외했다. 실행 환경을 알아내기 위한 입력과 알아낸 환경을 URL에 남기는 출력을 구별한 것이다.

## 목적지만 렌더하면 원래 layout의 책임이 빠진다

페이지 이동을 생략하면 원래 목적지 layout을 통과하지 않는다. 목적지 컴포넌트만 넣는 것으로는 theme과 외부 웹의 광고 설정이 따라오지 않았다.

공유 shell을 재사용해 직접 렌더에서도 그 구성을 유지했다. 눈에 보이는 화면과 실제 실행 환경이 같다고 말하려면 컴포넌트의 내용뿐 아니라 원래 layout이 준비하던 책임도 함께 전달해야 했다.

## 기다림과 늦은 결과를 다른 입력으로 검증했다

publisher 대기, capability 실패의 fallback, target 반영 전의 대기와 언마운트 조건을 구분했다. 타이머가 늦어지는 조건과 중복 BI 발행도 테스트 사례에 남겼다.

| 조건 | 지켜야 할 결과 |
| --- | --- |
| publisher가 준비되지 않음 | 목적지 판단을 앞당기지 않음 |
| capability 조회 실패 | 외부 웹 fallback |
| URL target이 아직 반영되지 않음 | 잘못된 모드로 먼저 시작하지 않음 |
| 컴포넌트 종료 | 이후 결과가 종료한 흐름을 이어가지 않음 |
| 같은 진입을 다시 읽음 | 계측을 중복 발행하지 않음 |

이 구현은 6월에 main으로 통합됐다. 당시 기기의 모든 흰 화면이 없어졌거나 브라우저 엔진의 원인을 확정했다는 결과와는 구별한다. 내가 바꾼 것은 중간 이동과 목적지 실행을 연결하는 FE 구조였다.

## 이동을 줄이려면 없어지는 책임도 찾아야 했다

같은 경로에서 목적지를 렌더하니 중간 이동의 hop은 없어졌지만, URL의 반영 시점과 layout의 준비를 직접 연결할 일이 생겼다. 복잡성이 그냥 사라진 것이 아니라 더 명시적으로 다뤄야 할 책임이 바뀐 셈이다.

이 선택을 돌아보면 페이지를 덜 넘기는 것만큼, 생략한 페이지가 무엇을 준비하던 곳인지 확인한 과정이 중요했다. 다음에 진입 흐름을 단순하게 만든다면 제거할 화면과 함께 남겨야 할 상태·설정·종료 조건을 먼저 보게 될 것 같다.
