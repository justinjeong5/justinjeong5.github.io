파트너 앱에서 PlayHub Quest 참여 링크를 누른 사용자가 다음 화면으로 넘어가지 못하고 빈 화면에 머무는 사례가 있었습니다. Quest는 앱이 지원하는 기능에 따라 두 가지 참여 화면 중 하나를 고릅니다. 이 선택을 맡은 진입 화면을 게이트웨이라고 불렀습니다.

동료가 특정 Android WebView에서 문제를 재현했고, 저는 **어느 단계에서 멈추는지 확인한 뒤 전환 구조를 바꾸는 작업**을 맡았습니다. 기능 조회가 늦은 것인지, 새 화면의 응답을 받지 못한 것인지, 응답을 받은 뒤에도 화면이 바뀌지 않는 것인지에 따라 수정할 곳이 달랐습니다.

## 응답이 늦은 문제와 화면이 늦게 바뀌는 문제를 나누다

당시 게이트웨이는 앱의 지원 기능으로 목적지를 고른 뒤 `router.replace`로 해당 페이지로 이동했습니다. 목적지를 결정해도 새 페이지의 화면 전환이 끝나기 전까지는 사용자가 다음 화면을 볼 수 없는 구조였습니다.

저는 게이트웨이가 목적지를 결정한 시점과 새 화면을 구성하는 서버 응답(RSC)이 도착한 시점을 구별해 기록했습니다. 조사한 사례에서는 그 응답이 도착한 뒤에도 화면 전환이 끝나지 않았습니다. 따라서 기능 조회나 네트워크 응답을 단순히 다시 시도하는 것보다, **응답 이후에 남은 페이지 이동 단계를 줄이는 것**이 이 사례에 맞는 수정이었습니다. 전환이 왜 늦게 끝났는지 WebView 내부 원인까지 규명한 것은 아닙니다.

페이지를 통째로 다시 여는 방법도 검토했습니다. 하지만 일부 매체의 WebView가 그 이동을 가로막는 회귀가 확인됐습니다. 이동 방식을 바꾸는 대신, 목적지를 고른 현재 화면에서 바로 그 목적지 화면을 렌더하는 방향으로 바꿨습니다.

## 이동을 없애면서 기존 화면의 조건을 보존하다

페이지 이동을 없애는 것만으로는 같은 화면이 나오지 않았습니다. 원래 목적지 페이지는 URL에서 앱 안에서 시작했는지 같은 진입 정보를 읽고, 페이지 레이아웃에서 테마와 광고 설정을 적용했습니다. 목적지 컴포넌트만 현재 화면에 넣으면 이 조건이 빠질 수 있었습니다.

저는 `history.replaceState`로 주소의 진입 정보(`target`)만 바꾸고, 화면이 그 값을 읽은 뒤에 렌더하도록 순서를 정했습니다. 그렇지 않으면 앱에서 시작한 참여를 앱 밖에서 시작한 것으로 잘못 판단할 수 있었습니다. 기존 목적지 레이아웃의 설정도 공통 셸로 옮겨 직접 렌더할 때 같은 구성을 사용했습니다. **목적지를 선택하는 것과 그 목적지를 올바른 환경에서 시작하는 것을 별도로 확인한 셈입니다.**

전환 시 새 화면 코드를 다시 기다리지 않도록 목적지 코드를 진입 단계에 포함하고, 준비 중에는 로딩 화면을 보여줬습니다. 대신 처음 내려받는 코드가 커질 수 있었습니다.

## 확인한 변화와 남은 경계

테스트에서는 앱의 지원 기능을 조회하지 못해도 다음 화면으로 진행하는지, URL의 진입 정보가 반영되기 전에 잘못된 모드로 화면이 뜨지 않는지를 확인했습니다.

이 변경은 2026년 6월 제품 코드에 통합됐습니다. 사용자가 다음 화면을 보기 위해 별도 페이지 이동이 끝나기를 기다리던 구조를 없애고, 같은 화면에서 목적지를 렌더하는 경로를 테스트로 확인했습니다. 모든 기기의 빈 화면이 사라졌다는 운영 지표는 확인하지 못했습니다.

이 일을 통해 제가 풀어야 했던 문제는 ‘어느 페이지로 보낼까’가 아니라 **‘목적지를 이미 알 때 왜 화면은 아직 비어 있는가’**였습니다. 멈춘 단계를 구별한 뒤 그 전환을 제거하되, 전환이 전달하던 URL과 레이아웃 조건은 보존해야 했습니다.
