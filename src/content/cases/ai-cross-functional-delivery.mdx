새 보너스 화면의 문의 기능에는 앱별로 보여줄 문의 분류와 실제 생성 요청을 허용할 범위가 필요했습니다. 화면에서 미지원 분류를 숨길 수는 있지만, 직접 보낸 생성 요청까지 막지는 못합니다. 저는 프론트엔드 밖의 Python 서버 변경도 맡아 **허용하지 않은 문의가 저장되거나 외부 처리로 넘어가지 않도록** 경계를 정했습니다.

AI는 낯선 서버 코드의 조사와 초안 작성에 활용했습니다. 제 역할은 제품이 허용하는 요청과 부수효과를 정의하고, 코드와 테스트가 그 조건을 지키는지 확인하며, DB를 담당한 동료와 반영 순서를 맞추는 것이었습니다.

## 오류를 반환하기 전에 멈춰야 했다

문의 생성 경로에는 DB 저장, 외부 문의 생성, 자동 처리가 이어졌습니다. 미지원 요청에 오류를 반환하더라도 이미 저장한 뒤라면 늦습니다. 그래서 앱과 분류의 지원 여부를 **저장·외부 처리 전에** 검사하도록 수정했습니다. 조회에서 보여주는 항목과 생성에서 허용하는 입력도 같은 지원 범위를 따르는지 살폈습니다.

테스트에는 미지원 요청 시 DB에 문의가 남지 않고 외부 문의 생성·자동 처리가 호출되지 않는 조건을 넣었습니다. 지원 요청은 앱과 분류가 저장되고 외부 생성으로 이어지는 경로를 확인했습니다. 오류 문구보다 먼저, 잘못된 요청이 실행 단계로 들어가지 않는지를 검증한 셈입니다.

## 새 분류를 넣는 순서도 계약이었다

새 문의 분류를 저장하려면 DB ENUM에 값이 추가돼야 했습니다. 화면의 표시 순서에 맞춰 기존 DB 값의 순서를 바꾸면 안 된다는 DBA의 의견을 확인했습니다. 새 값은 DB의 마지막에 추가하고, 화면에 제공하는 순서는 Python 정의에서 따로 다루기로 맞췄습니다.

저는 AI와 함께 서버 코드·테스트·DDL 초안을 준비하고 DBA에게 검토 자료를 전달했습니다. 공유 DB의 현행 스키마와 실행 방식은 DBA가 확인했으며, 운영·검증 환경의 실제 DB 반영도 DBA가 맡았습니다. 제가 코드를 준비했다는 사실과 DB를 직접 변경했다는 주장은 구분해야 합니다.

## DB가 준비된 뒤 코드를 병합했다

서버 코드가 새 ENUM 값을 쓰는데 DB가 아직 받지 못하면 기능의 절반만 준비된 상태가 됩니다. 팀에서는 다른 동료도 메인 브랜치를 수시로 배포했으므로, 코드를 먼저 병합하고 나중에 DB를 바꾸는 순서는 안전하지 않았습니다. DBA의 반영 완료 보고를 받은 뒤 서버 변경을 병합했습니다.

이 일은 AI를 사용했다는 이야기보다 **지원 범위 검증을 부수효과 앞에 두고, 코드와 DB의 실제 반영 순서를 팀 운영 방식에 맞춘 판단**을 보여줍니다. 낯선 언어의 초안을 빠르게 얻을 수 있어도, 무엇이 저장되면 안 되는지와 누가 언제 운영 상태를 바꾸는지는 제가 확인해야 했습니다.
