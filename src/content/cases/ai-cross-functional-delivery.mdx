문의 기능의 서버 코드와 검토 자료를 준비했지만 바로 병합하지는 않았습니다. 새 분류를 사용하는 코드만 반영하면 DB가 그 값을 저장하지 못할 수 있었기 때문입니다. DB를 맡은 담당자의 반영 완료 보고를 받은 뒤 다음 변경을 진행했습니다.

이 일은 새 보너스 화면의 문의 기능에서 시작했습니다. 앱별 문의 분류 조회, 생성 요청이 지원 대상인지 확인하는 검증, 새 분류를 저장할 DB 값이 모두 필요했습니다. Python 서버가 낯선 프론트엔드 개발자였지만, 팀에 남은 병목을 AI와 함께 맡아 기존 코드를 조사하고 구현했습니다. AI가 제안한 코드가 필요한 조건을 지키는지 검토하고, DB 변경과 코드 병합을 누가 어떤 순서로 진행할지도 함께 확인했습니다.

## 화면에 보이는 선택지와 서버가 허용할 입력

분류 조회와 문의 생성은 한 기능의 두 경로였습니다. 조회에서는 사용자가 고를 수 있는 항목을 제공합니다. 생성에서는 입력을 받아 DB 저장과 외부 문의 처리로 넘어갑니다. 조회에서 항목을 숨겨도 직접 생성 요청이 들어올 수 있으므로 화면의 제한으로 서버 검증을 대신할 수 없었습니다.

AI로 초안을 만들고 앱별 분류 조회, 기존 생성 경로를 조사하고 지원 앱과 미지원 앱을 나누었습니다. 제품의 적용 범위가 좁혀지는 후속 수정도 이어졌습니다. 구현할 항목 목록만 정하는 것보다, 지원 범위의 변경이 조회와 생성 양쪽에서 같은 의미를 갖는지를 봐야 했습니다.

프론트엔드에서 다루던 입력과 행동의 관계를 서버에서도 확인했습니다. 화면에서 선택지를 제공하더라도 실제 요청을 실행하는 시점에 그 선택이 허용되는지 다시 검사해야 했습니다.

## 오류를 반환했어도 너무 늦을 수 있다

생성 요청에는 저장과 외부 문의 생성, 자동 처리 같은 부수효과가 있었습니다. 미지원 요청에 오류 응답을 추가해도 그 전에 문의가 저장됐다면 이미 처리할 일이 생깁니다.

그래서 수정안을 검토할 때는 예외의 종류뿐 아니라 검증의 위치를 봤습니다. 잘못된 입력이 실행 단계에 들어가기 전에 멈춰야 했습니다. 설명용 흐름은 다음과 같습니다.

```text
입력과 앱의 지원 범위 확인
  ├─ 미지원 → 거절, 저장·외부 처리 시작하지 않음
  └─ 지원 → 문의 저장 → 외부 처리 연결
```

테스트에도 미지원 요청에서는 DB에 문의가 남지 않고 외부 문의 생성과 자동 처리가 호출되지 않는 조건을 넣었습니다. 지원 요청은 저장된 앱과 분류, 외부 생성으로 이어지는 결과를 다뤘습니다.

AI의 수정안을 검토하려면 무엇을 막을지 먼저 정해야 했습니다. 제품이 허용하는 행동과 잘못된 요청에서 발생하면 안 되는 결과를 설명한 뒤, 코드와 테스트가 그 조건을 지키는지 읽었습니다.

## 같은 목록처럼 보여도 저장 순서는 다른 문제였다

새 문의 분류에는 DB의 ENUM 변경이 필요했습니다. 화면에서는 항목을 보기 좋은 위치에 놓고 싶지만, 기존 DB 값의 순서를 같은 이유로 움직일 수는 없었습니다.

DBA가 기존 값의 순서를 유지해야 한다는 의견을 줬을 때, 화면에 제공하는 Python 정의의 순서도 같아야 하는지 확인했습니다. 저장 순서와 화면 정렬은 따로 정할 수 있다는 데 의견을 맞춘 뒤, 새 값은 DB의 마지막에 추가하고 화면 순서는 Python 정의에서 다뤘습니다. AI와 준비한 DDL도 이 조건에 맞춰 검토 자료로 전달했습니다.

여기서 AI와 준비한 것은 코드와 검토 자료였습니다. 공유 DB의 현행 스키마와 실행 방식은 DBA가 확인하고 운영·검증 환경에 반영했습니다. 같은 기능의 작업이어도 누가 실제 상태를 바꿀 수 있는지는 달랐습니다.

## 코드가 준비된 시점에 바로 병합하지 않았다

서버가 새 분류를 쓰는데 DB가 아직 저장할 수 없다면 기능의 한쪽만 반영됩니다. AI와 검토하는 과정에서는 코드 병합과 배포를 별도 단계로 보는 설명도 나왔지만, 우리 팀에서는 다른 동료가 메인 브랜치를 수시로 배포하고 있었습니다. 제 변경을 병합한 뒤 누군가 배포할 수 있다는 운영 맥락까지 판단해야 했습니다.

그래서 DB 반영 완료 뒤 서버 변경을 병합하기로 정했습니다. 담당자의 완료 보고를 받은 뒤 그 순서로 이어 갔습니다. AI가 일반적으로 설명한 절차를 그대로 따르는 대신, 우리 팀에서 실제로 다음 상태를 바꿀 수 있는 사람과 시점을 확인한 선택이었습니다.

코드와 테스트를 준비하고 DBA의 DB 반영 완료 보고를 받은 뒤 서버 변경을 병합했습니다. 익숙하지 않은 언어로 코드를 만드는 것뿐 아니라, 그 코드가 적용되기 전에 필요한 DB 변경까지 확인한 작업이었습니다.

## 업무 경계를 넓힐 때 남는 판단

마지막 병합의 조건은 코드가 준비됐다는 것 하나가 아니었습니다. DBA의 완료 보고를 받아야 저장할 값이 준비됐음을 알 수 있었습니다. 이 순서를 되짚으면, 낯선 언어의 수정안을 이해한다는 말도 문법과 로직을 읽는 데서 끝나지 않습니다. 그 코드가 언제 적용되어도 되는지 설명하는 일까지 연결돼 있었습니다.

프론트엔드 밖의 일을 맡으면서 모든 구현을 혼자 통제할 필요는 없었습니다. 다만 지원하지 않는 요청이 남기면 안 되는 흔적, 기존 저장 값과의 호환성, 다음 변경 전에 기다려야 할 완료 보고는 제가 설명할 수 있어야 했습니다. AI가 낯선 서버 코드에 진입하는 부담을 낮춰 줬고, 저는 이 세 조건을 확인하며 변경을 팀에 전달했습니다.
