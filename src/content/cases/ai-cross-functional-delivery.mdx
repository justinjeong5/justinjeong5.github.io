새 보너스 기능을 화면에 넣는 것만으로 제품의 문의 흐름이 완성되지는 않았다. 사용자가 문의를 남기려면 서버가 해당 앱에 맞는 분류를 제공하고, 실제 문의 요청도 그 앱에서 지원하는지 검사해야 했다. 문의 분류를 저장하는 DB에도 새 값이 필요했다.

Python 서버 경험은 적어 AI에 맥락 조사와 구현 계획을 맡겼다. 나는 허용할 요청과 반영 순서를 담당자와 확인하며 변경을 검토 가능한 범위로 묶었다. 제품 흐름에 남은 일을 프론트엔드 밖까지 연결해 전달하려는 작업이었다.

## 먼저 화면의 요구를 서버의 두 책임으로 나누었다

분류 조회와 문의 생성은 같은 기능처럼 보이지만 서로 다른 책임을 가진다. 조회는 사용자에게 가능한 선택을 보여준다. 생성은 입력이 실제로 허용되는지 검사하고 외부 처리와 저장으로 이어진다. 화면에서 선택지를 숨겼다는 이유로 생성 경로의 검증을 생략할 수는 없다.

AI와 함께 앱별 분류 조회와 기존 문의 생성 경로를 확인하고 변경했다. 새 문의 유형을 지원하는 앱과 지원하지 않는 앱을 구분하도록 했다. 서버 반영 뒤에는 적용 대상을 좁히는 후속 변경도 이어졌다.

AI가 익숙하지 않은 코드를 빠르게 찾아 수정해 주더라도, 제품이 어느 입력을 허용하는지 결정할 책임까지 사라지지는 않는다. 여기서는 화면이 필요한 분류를 받는 것과 서버가 잘못된 요청을 거부하는 것을 모두 결과에 포함했다.

## 잘못된 요청은 오류를 반환하기 전에 무엇을 했는지도 봐야 한다

문의 생성에는 DB 저장과 외부 문의 처리, 자동 적립 경로 같은 부수효과가 연결돼 있었다. 미지원 앱의 요청을 오류로 끝내더라도 이미 외부 처리를 시작한 뒤라면 입력 검증의 목적을 만족하지 못한다.

그래서 테스트는 잘못된 입력에서 예외가 발생하는지만 확인하지 않았다. 미지원 앱의 보너스 문의가 DB에 남지 않고, 외부 문의 생성과 자동 처리도 호출하지 않는 조건을 함께 남겼다. 지원하는 입력은 저장된 앱과 분류, 외부 생성 경로가 연결되는지를 확인하도록 했다. 분류 조회에 잘못된 앱 식별자가 들어오는 경우도 거부 조건에 포함했다.

서비스 경계에서 잘못된 요청이 부수효과보다 먼저 차단되는지를 테스트했다. AI에게 테스트를 요청할 때도 요청의 성공 여부보다 이 순서가 중요한 이유를 설명할 수 있어야 했다.

## 화면의 분류 순서와 DB의 저장 순서를 구별했다

새 분류를 추가하는 과정에서 DB의 ENUM 순서와 Python에서 화면에 제공할 분류 순서를 다시 확인했다. 화면에서 보기 좋은 순서를 만들려고 기존 DB 값의 위치를 바꾸면 저장 값의 의미를 건드릴 수 있었다.

기존 DB 값의 순서는 유지하고 새 값은 마지막에 추가하는 방식으로 DBA에게 검토용 DDL과 변경 내용을 전달했다. API 표시 순서는 별도의 Python 정의에서 다루었다. 저장의 호환성과 화면의 표현은 같은 순서 목록처럼 보여도 다른 계약이었다.

DB 반영은 DBA가 현행 스키마와 실행 방식을 확인하고 수행했다. 코드 준비와 운영 반영을 별개의 완료 상태로 두고, 담당자의 반영 완료를 확인했다.

## 코드 완료보다 먼저 맞춰야 했던 반영 순서

서버가 새 분류를 사용하기 시작했는데 DB는 아직 그 값을 저장할 수 없다면 기능의 한쪽만 준비된 것이다. DB 변경 완료 뒤 서버 변경을 병합하기로 정했고, 담당자의 운영·검증 환경 반영 완료 보고를 받은 뒤 그 순서로 진행했다.

내가 맡은 일에는 화면 밖의 코드 수정뿐 아니라 이 순서를 닫는 일이 포함됐다. 필요한 변경을 제한하고, 담당자가 확인할 자료를 만들고, 완료 신호 뒤에 다음 단계를 진행했다.

## AI에 위임할 범위와 직접 확인할 끝점

비슷한 시기의 [배포 환경 선택 개선](/cases/deployment-config-contracts/)에서는 Go 설정 처리와 프론트엔드 소비 모델을 AI와 구현했다. 그때도 화면이 정상이라는 사실만으로는 충분하지 않았다. 구 전용 코드가 남아 있으면 새 설정이 실패해도 같은 화면이 나올 수 있어서, 소비자 선언과 전용 분기 제거가 함께 적용된 버전을 직접 배포해 확인했다.

문의 분류에서는 그 끝점이 달랐다. 잘못된 입력을 부수효과 전에 거부하는 코드와 테스트, 기존 저장 값의 순서, DBA 반영 후 병합이라는 순서를 연결했다. 같은 AI 협업이라도 어느 결과를 직접 확인해야 전달됐다고 말할 수 있는지는 제품의 실패 경계에 따라 달랐다.

## 작은 서버 변경을 팀이 이어받을 수 있는 결과로 만들기

앱별 문의 분류와 지원 여부 검증이 기존 서버 경로에 들어갔고, DB 변경은 담당자의 반영 완료와 연결한 뒤 서버 변경을 병합했다. 새 화면이 요구하는 계약을 화면 밖까지 이어 붙인 결과였다.

이 경험에서 AI 활용의 의미는 사용할 수 있는 언어가 하나 늘었다는 데 있지 않다. 익숙하지 않은 영역을 AI에게 조사·구현하게 하면서도 입력의 범위, 부수효과의 순서, 운영 반영의 책임을 다시 확인한 데 있었다. 팀이 검토하고 적용할 수 있는 작은 변경으로 만들어 전달하는 과정까지가 내 일이었다.
