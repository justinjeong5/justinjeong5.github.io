## 확인 근거와 공개 범위

병목 논의·적용 안내와 설정 변경·제거·회귀 대응을 여러 시점에서 대조했습니다. 동일 조건의 성능 실험이나 팀 전체 절감 수치로 환산하지 않습니다.

이 글은 원문을 대조한 공개용 재구성입니다. 내부 코드·협의 원문·고객 정보는 공개하지 않으므로 방문자가 원문을 직접 검증할 수 있는 자료는 아닙니다.

## 무엇부터 바꿀지 먼저 골랐다

느린 빌드의 loader/plugin별 병목을 살피고 캐시와 라이브러리 최적화의 우선순위를 정했다. 미사용 파일이나 중복 라이브러리 정리는 당시 노력 대비 효과가 낮다고 판단해 뒤로 뒀다.

처음 빌드와 캐시 이후 반복 빌드의 조건이 달랐다. 동료에게 차이와 적용 방법을 안내했고, 측정 도구 자체의 오버헤드에 대한 피드백도 수용했다.

## 도입이 마지막 단계는 아니었다

Webpack 전환 뒤 의존성 호환 문제에 대응하면서 기존 cache-loader를 제거했다. 이후 개발 속도 회귀를 보고하고 Webpack·Babel·ESLint의 다른 캐시 설정으로 변경했다.

QA/DevOps의 도움과 서로 다른 배포 문제를 구분해 기록한다. 특정 의존성 하나가 모든 실패의 원인이었다거나 모든 문제를 해결했다는 이야기는 아니다.

## 숫자보다 조건을 먼저 남긴다

여러 시기·기기·최초/반복 빌드의 값은 동일한 실험이 아니다. 여기서는 정확 개선율을 합성하지 않고 병목 구분, 우선순위, 피드백, 호환 문제 이후의 변경 대응을 설명한다.

개발 빌드 변경을 사용자 페이지의 성능이나 팀 전체 생산성 수치로 확대하지 않는다. 같은 조건의 후속 측정과 장기 결과는 별도로 확인할 대상이다.

[정적 FE 앱의 전달 경계](/cases/frontend-delivery-boundary)는 다른 시점의 전환이다. 두 기록은 같은 migration이 아니라 기술 변경의 제약을 팀과 다룬 별개의 사례다.
