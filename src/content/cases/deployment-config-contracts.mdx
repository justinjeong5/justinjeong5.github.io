배포할 서비스와 환경이 환경 이름 하나에 함께 들어 있었다. 운영자는 긴 목록을 읽으며 원하는 조합을 골라야 했다. 비슷한 이름을 구별하는 부담을 줄이려고 프로젝트와 환경을 두 단계로 선택하게 만들었다. 배포 대상을 새로 만드는 작업이 아니라 이미 있는 대상을 더 쉽게 찾는 작업이었다.

처음에는 특정 제품의 이름 규칙을 프론트엔드에서 해석했다. 제한된 범위에서 선택 경험을 바꾸되 배포 요청에는 원래 환경 이름을 보냈다. 하지만 이 방식은 그 제품의 이름과 차원 순서를 공용 도구 코드에 남겼다. 다른 저장소도 같은 분류를 쓰게 만들 것인지, 저장소마다 다른 구조를 표현하게 할 것인지가 다음 문제였다.

## 작은 개선이 공용 도구의 규칙이 되는 지점

초기에는 하나의 목록에서 그룹을 표시하는 방식과 계층형 선택 컴포넌트도 검토했다. 전자는 긴 목록을 계속 탐색해야 했고, 후자는 값 변환과 키보드 접근을 검증할 일이 늘었다. 두 개의 선택 상자는 후보를 좁히면서도 기존 환경 객체를 그대로 유지할 수 있었다. 이 판단은 당시 작업의 제약에 따른 것이지 특정 컴포넌트가 일반적으로 부적합하다는 뜻은 아니다.

초기 구현은 이름이 예상 형식과 맞지 않거나 중복되면 전체 평면 목록으로 돌아갔다. 분류할 수 있는 항목만 보여주면 나머지 배포 대상이 사라질 수 있기 때문이다. 편의 기능이 실패했을 때 기존 작업이 가능한 쪽으로 물러나는 경계였다.

이후 제품 결합에 대한 리뷰를 받아들여 구조를 다시 정했다. 프로젝트가 먼저이고 환경이 나중이라는 순서도 도구의 고정 규칙일 이유가 없었다. 제품과 담당 팀처럼 다른 이름을 쓰더라도 선택 UI는 분류 구조를 다뤄야 했다. 구현은 AI에 위임하면서 이 요구와 기존 동작을 보존할 범위는 직접 다시 정했다.

## 허용한 값과 존재하는 조합은 다르다

저장소 설정에는 이름을 나누는 구분자, 두 차원의 순서, 그룹과 옵션으로 보여줄 차원, 표시 이름과 선택적인 허용 값 목록을 선언하게 했다. 서버는 이를 UI가 사용할 그룹·옵션 모델로 정규화했다. 이때 지원한 구조는 두 차원이다. 무한한 계층 선택기를 만들지는 않았다.

중요한 것은 허용 값 목록을 선택지의 목록으로 오해하지 않는 일이었다. 서비스 값에 A와 B가 있고 환경 값에 개발과 운영이 있다고 해서 네 조합이 모두 존재하는 것은 아니다. A의 운영 환경만 선언돼 있을 수도 있다. 선택지는 실제 환경 목록을 순회하며 만들고, 허용 값 목록은 각 값이 유효한지 검사하는 데 사용했다.

그룹과 표시 이름은 화면을 위한 값이다. 최종 옵션에는 원래 환경 식별자가 남는다. 배포·잠금·롤백 요청은 이 원본 값을 사용하므로 표시 규칙을 바꿔도 기존 서버의 대상 해석을 바꾸지 않는다. UI의 프로젝트 필드가 배포 요청에 새 필드로 섞이지 않는 것도 확인할 계약이었다.

## 표시 설정이 잘못돼도 배포 설정은 읽을 수 있어야 했다

설정 선언이 추가되면 실패 방식도 늘어난다. YAML 타입이 잘못되거나 차원 이름에 오타가 있을 수 있고, 허용하지 않은 값이나 중복된 환경 이름이 들어올 수도 있다. 이 오류를 모두 핵심 배포 설정의 파싱 실패로 처리하면 화면을 편하게 만들려던 설정 때문에 배포 자체가 막힌다.

UI 설정의 해석 오류는 별도로 보관했다. 설정 조회 API는 경고와 원본 환경 목록을 반환하고, 화면은 기존 평면 선택을 사용할 수 있게 했다. CLI에도 같은 설정을 로컬에서 검증할 경로를 추가했다. 핵심 배포 평가가 기존 방식대로 동작하는 경계와 UI 선언의 오류 처리를 분리한 것이다.

이 구조에서 fallback은 잘못된 선언을 정상이라고 숨기는 동작이 아니다. 경고를 남기면서 작업 가능한 원본 목록을 제공한다. 표시 설정을 고칠 책임과 배포할 대상을 선택할 책임이 각각 남는다.

## 선택을 바꾸면 이전 요청의 권한도 끝난다

선택기는 동기적인 폼 요소지만 그 주변에는 비동기 요청이 있었다. 환경 A의 최근 배포를 조회한 뒤 B로 바꾸었는데 A의 응답이 늦게 오면, 선택 상자는 B인데 화면의 배포 정보는 A가 되는 문제가 생긴다.

환경이 바뀔 때 현재·최근 배포 정보와 대기 중인 요청의 식별자를 함께 초기화했다. 응답을 반영할 때는 요청 식별자뿐 아니라 요청했던 원본 환경 이름도 현재 선택과 같은지 확인했다. 롤백 화면은 선택한 배포 이력까지 함께 비워 이전 환경에서 고른 대상을 새 환경에서 재사용하지 않게 했다.

배포 이력 목록에서는 그룹만 고른 상태도 허용했다. 이때 조회하는 것은 해당 그룹에 실제로 포함된 환경 이름들의 배열이다. 선택 UI에서 존재하지 않는 조합을 만들지 않았던 판단을 조회 조건에도 유지했다. 설정 조회 실패와 이력 조회 실패, 조회 결과가 없는 상태도 각각 다르게 표현했다.

## 정상 화면만으로는 새 구현을 검증할 수 없었다

설정 기반 선택 모델을 넣은 과도기에는 제품 전용 분기가 남아 있었다. 새 선언이 잘못돼도 구 코드가 같은 화면을 만들 수 있다면 화면이 정상이라는 관찰만으로는 새 기능의 성공을 판단할 수 없다.

그래서 소비 저장소에 선언이 들어간 상태와 공용 도구에서 전용 분기가 제거된 상태를 함께 확인 대상으로 삼았다. AI에는 구현과 변경 전달을 맡기고 배포는 직접 진행했다. 그 조합의 버전을 검증 환경에 배포해 환경 선택과 실제 배포 동작을 확인했다. 테스트 개수를 늘리는 것보다 먼저 어떤 버전을 확인해야 성공의 의미가 분명한지를 바꾼 것이다.

그 뒤 선택 구조를 이력 조회·잠금·롤백 화면에도 연결했다. 팀에 공유한 뒤에는 잠금 탭에서 환경별로 보고 싶었다는 동료의 반응이 있었다. 롤백 UI를 검증하다 발견한 오래된 배포 참조의 실패는 별도로 보고했고, 참조가 없는 브랜치를 막는 수정은 인프라 담당자가 맡았다.

## 저장소가 표시 규칙을 갖고, 도구는 원본 대상을 전달한다

완료한 변화는 특정 제품 이름을 도구 코드에서 해석하던 방식을 저장소의 표시 선언으로 옮긴 것이다. 운영자는 그룹으로 후보를 좁힐 수 있고, 화면을 바꾸는 설정은 기존 배포 대상과 요청 형식을 유지한다. 선택이 바뀐 뒤에는 이전 조회 결과와 선택한 배포도 함께 버린다.

이 작업에서 가장 크게 달라진 판단은 공용 도구의 개선을 화면 표현만으로 볼 수 없다는 점이었다. 설정이 무엇을 선언하는지, 실패할 때 어느 기능까지 멈추는지, 어느 소비 버전을 확인해야 새 코드가 실행됐다고 말할 수 있는지가 같은 변경 안에 있었다. 그 연결을 정한 뒤에야 새 선택기를 다른 화면으로 확장할 수 있었다.
