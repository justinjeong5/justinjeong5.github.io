배포 화면에는 길고 비슷한 환경 이름이 한 목록에 있었습니다. 원하는 프로젝트를 찾은 다음 정확한 환경을 골라야 하는데, 화면에서는 모든 이름을 처음부터 같은 수준으로 보여줬습니다. 새 환경을 만드는 기능보다 기존 대상을 쉽게 찾을 방법이 필요했습니다.

프로젝트와 환경을 두 번에 나눠 고르게 만들었습니다. 이후 공용 도구가 특정 제품의 이름을 해석하게 됐다는 반론을 받았습니다. 그 의견을 반영하면서 **표시 규칙을 어디에 둘지, 선택한 원래 환경을 배포 요청까지 어떻게 유지할지**를 다시 정했습니다.

## 처음부터 큰 설정 모델을 만들지 않았다

초기 설계에서 그룹을 표시한 긴 목록, Cascader, 두 Select, 공개 설정 스키마 확장을 비교했습니다. 긴 목록은 탐색 부담이 남았고, Cascader는 값 변환과 키보드 동작을 확인할 비용이 있었습니다. 처음의 단일 사례를 위해 설정 스키마까지 바로 바꾸는 선택은 영향 범위가 컸습니다.

그래서 제한적으로 활성화하는 FE 선택기를 먼저 만들었습니다. 프로젝트를 고르면 환경 후보를 좁히되, 각 옵션에는 원래 환경 객체를 유지했습니다. 표시를 나누는 정보와 배포할 대상의 식별자는 다르게 취급했습니다.

분류에 실패한 이름이 있으면 일부 환경만 조용히 숨기지 않고 원래 평면 목록으로 돌아갔습니다. 편의 기능의 실패 때문에 선택 가능한 배포 대상을 잃어서는 안 됐습니다. 제출 요청에도 프로젝트 같은 새 UI 필드를 추가하지 않고 기존 환경 이름을 보냈습니다.

## 반론은 UI가 아니라 규칙의 주인을 바꿨다

제품 전용 이름을 공용 코드가 해석하면, 다른 저장소가 다른 순서를 쓸 때 도구 자체를 고쳐야 합니다. 이 결합에 대한 리뷰를 수용해 표시 규칙을 소비 저장소의 선언으로 옮겼습니다.

정확히 두 차원의 이름·순서·표시와 허용 값을 설정으로 표현하고, 공용 도구는 그 선언과 원본 환경 목록을 읽도록 했습니다. Go 설정 처리와 API·CLI, 프론트엔드 소비 모델을 함께 바꿨습니다. AI에 구현과 변경 준비를 맡겼지만 바뀐 요구와 검증할 대상을 정하는 일은 제가 이어 갔습니다.

설정으로 옮기면서도 무한한 계층을 고르는 기능까지 만들지는 않았습니다. 필요한 두 차원만 선언하게 하고 기존 환경 식별자는 유지했습니다. 현재 문제를 해결하는 범위에서 공용 도구의 결합을 줄였습니다.

## 허용된 값의 곱이 실제 환경은 아니었다

설정에 프로젝트와 환경의 허용 값이 있다고 그 모든 조합이 존재하는 것은 아닙니다. 예를 들어 프로젝트 A의 운영 환경만 있는데, 값 목록을 곱해 검증 환경까지 만들어 보여주면 선택할 수 없는 대상을 UI가 발명합니다.

선택지는 실제 원본 환경들을 해석해 만들었습니다. 설정은 이름을 어떻게 읽을지 정하고, 존재 여부는 원본 환경 목록이 정했습니다. 그룹만 고른 이력 조회도 해당 그룹에 실제 존재하는 환경 이름들로 요청했습니다.

| 정보 | 맡은 의미 |
| --- | --- |
| 표시 설정 | 두 차원과 이름·순서를 해석하는 방법 |
| 원본 환경 목록 | 실제 선택하고 조회할 수 있는 대상 |
| 제출 값 | 기존 실행 계약의 원본 환경 이름 |

설정이 잘못됐을 때도 표시 설정의 오류와 core 배포 설정의 오류를 나눴습니다. 편의 설정은 경고와 평면 목록으로 돌아갈 수 있지만, 실행할 설정까지 잘못된 일을 정상처럼 넘기는 것은 다른 문제였습니다.

## 환경을 바꾸면 이전 조회의 권한도 끝난다

A의 배포 정보를 읽는 동안 사용자가 B로 바꿀 수 있었습니다. 선택 상자는 B인데 늦은 A의 응답이 화면을 채우면, 화면의 의미와 실제 대상이 달라집니다.

환경 변경 때 현재·최근 결과와 pending request를 비웠습니다. 응답을 적용할 때는 요청 식별자와 요청했던 원본 환경이 지금 선택과 같은지 함께 확인했습니다. 같은 환경에서도 새 refresh가 시작될 수 있어 환경 이름만 비교하는 것으로는 부족했습니다.

Rollback에서는 조회 이력뿐 아니라 선택한 배포 대상도 초기화했습니다. 늦은 조회를 막았더라도 A에서 고른 실행 입력을 B에서 들고 있으면 문제가 남습니다. 조회 데이터와 다음 명령의 대상이 같은 환경을 설명해야 했습니다.

## 정상 화면이 새 구현의 성공을 증명하지 않았다

새 설정이 들어가도 제품 전용 구 분기가 남아 있으면 같은 화면이 나올 수 있었습니다. 그 상태에서는 새 선언이 잘못돼도 이전 코드가 성공을 대신 설명합니다.

그래서 소비 저장소의 선언과 공용 도구의 전용 분기 제거가 함께 들어간 버전을 검증 대상으로 다시 정했습니다. 배포는 직접 진행해 환경 선택과 실제 배포를 확인했습니다. 보이는 선택기의 모양뿐 아니라 원래 배포 대상이 요청에 남는지를 확인하는 작업이었습니다.

후속에서는 Home·Lock·Rollback의 탐색도 같은 계약으로 연결했습니다. Lock 환경별 탐색에 대한 동료의 감사가 있었고, 최근 배포 대상을 사용한 rollback도 확인했습니다. 오래된 SHA의 branch guard는 DevOps 동료의 작업이었습니다. 제가 바꾼 선택기와 배포 backend의 안전장치를 같은 성과로 합치지 않았습니다.

## 편의를 더하면서 실행의 의미는 그대로 두기

저장소는 표시 규칙을 선언할 수 있게 됐고, 도구는 제품 이름을 덜 알아도 실제 환경을 보여줄 수 있었습니다. 선택 변경과 늦은 응답을 함께 다뤘고, 구 구현이 성공을 대신하지 못하는 조합에서 소비 동작을 확인했습니다.

지금 이 작업을 돌아보면 두 번의 재판단이 남습니다. 리뷰에서는 편리한 화면이 공용 도구에 제품 지식을 넣고 있다는 점을 봤고, 배포 확인에서는 정상 화면을 구 코드가 대신 만들 수 있다는 점을 봤습니다. 하나는 규칙을 어디에 둘지, 다른 하나는 무엇을 성공의 증거로 볼지를 바꿨습니다.

다음에 비슷한 편의 기능을 만든다면 화면을 어떻게 나눌지와 함께 도구가 어떤 제품 규칙을 알아야 하는지부터 적어 보려고 합니다. 이번에는 두 선택 상자를 만든 뒤 표시 규칙의 위치를 바꿨고, 검증에서도 구 코드가 성공을 대신하지 않는 조합을 골라야 했습니다. 편리해진 화면이 원래 배포 대상을 그대로 실행하는지 확인하는 데까지 작업이 이어졌습니다.
