배포 화면에서는 여러 프로젝트의 길고 비슷한 환경 이름이 한 목록에 섞여 있었습니다. 운영자가 프로젝트를 찾고 정확한 환경을 고르기 쉽게 두 단계 선택기로 바꿨지만, 곧 다른 문제가 드러났습니다. **여러 팀이 쓰는 도구가 한 제품의 이름 규칙을 코드에 직접 담게 된 것**입니다.

동료의 리뷰를 받고 저는 표시 규칙의 주인을 제품 저장소로 옮겼습니다. 다만 화면에서 보기 좋게 묶은 이름이 실제 배포 대상을 바꾸면 안 됐습니다. 이 글은 **선택을 쉽게 만들면서 배포 요청의 의미는 유지한 과정**입니다.

## 처음부터 큰 설정 모델을 만들지 않았다

처음에는 공용 설정 전체를 바꾸기보다 선택 화면에서 프로젝트를 고르면 환경 후보를 좁히는 방식을 적용했습니다. 한 제품의 사용 문제를 확인하는 단계에서 여러 팀의 설정 계약까지 즉시 바꾸는 비용이 컸기 때문입니다.

각 선택지에는 원래 환경 객체를 유지했습니다. 화면에 보여줄 그룹 이름과 실제 배포할 대상을 분리한 것입니다.

분류에 실패한 이름이 있으면 일부 환경만 조용히 숨기지 않고 원래 평면 목록으로 돌아갔습니다. 편의 기능의 실패 때문에 선택 가능한 배포 대상을 잃어서는 안 됐습니다. 제출 요청에도 프로젝트 같은 새 UI 필드를 추가하지 않고 기존 환경 이름을 보냈습니다.

## 반론은 UI가 아니라 규칙의 주인을 바꿨다

제품 전용 이름을 공용 코드가 해석하면, 다른 저장소가 다른 순서를 쓸 때 도구 자체를 고쳐야 합니다. 이 결합에 대한 리뷰를 수용해 표시 규칙을 서비스 저장소의 선언으로 옮겼습니다.

제품 저장소가 이름과 순서를 선언하고, 공용 도구는 그 선언과 실제 환경 목록을 읽도록 설정·API·CLI·화면을 연결했습니다. AI의 구현 도움을 받았지만 리뷰로 바뀐 요구와 검증할 버전 조합은 제가 정했습니다.

설정으로 옮기면서도 무한한 계층을 고르는 기능까지 만들지는 않았습니다. 필요한 두 차원만 선언하게 하고 기존 환경 식별자는 유지했습니다. 현재 문제를 해결하는 범위에서 공용 도구의 결합을 줄였습니다.

## 허용된 값의 곱이 실제 환경은 아니었다

설정에 프로젝트와 환경의 허용 값이 있다고 그 모든 조합이 존재하는 것은 아닙니다. 예를 들어 프로젝트 A의 운영 환경만 있는데, 값 목록을 곱해 검증 환경까지 만들어 보여주면 선택할 수 없는 대상을 UI가 발명합니다.

선택지는 실제 원본 환경들을 해석해 만들었습니다. 설정은 이름을 어떻게 읽을지 정하고, 존재 여부는 원본 환경 목록이 정했습니다. 그룹만 고른 이력 조회도 해당 그룹에 실제 존재하는 환경 이름들로 요청했습니다.

설정이 잘못됐을 때도 표시 설정의 오류와 core 배포 설정의 오류를 나눴습니다. 편의 설정은 경고와 평면 목록으로 돌아갈 수 있지만, 실행할 설정까지 잘못된 일을 정상처럼 넘기는 것은 다른 문제였습니다.

## 정상 화면이 새 구현의 성공을 증명하지 않았다

새 설정이 들어가도 제품 전용 분기가 남아 있으면 같은 화면이 나올 수 있었습니다. 그 상태에서는 새 선언이 잘못돼도 이전 코드가 성공을 대신 설명합니다.

그래서 서비스 저장소의 선언과 공용 도구의 전용 분기 제거가 함께 들어간 버전을 검증 대상으로 다시 정했습니다. 배포는 직접 진행해 환경 선택과 실제 배포를 확인했습니다. 보이는 선택기의 모양뿐 아니라 원래 배포 대상이 요청에 남는지를 확인하는 작업이었습니다.

후속 Home·Lock·Rollback 화면도 같은 실제 환경 목록을 사용하게 했습니다. 환경을 바꾸는 동안 이전 환경의 늦은 조회 결과나 선택한 배포 대상이 남지 않도록 했습니다. 오래된 SHA의 branch guard는 DevOps 동료의 별도 작업이었습니다.

## 편의를 더하면서 실행의 의미는 그대로 두기

서비스 저장소의 표시 선언과 공용 도구의 제품 전용 분기 제거를 함께 넣은 버전으로 환경 선택과 실제 배포를 확인했습니다. 화면에서 편해진 선택이 배포 대상을 바꾸지 않도록, **규칙은 해당 제품이 선언하고 실행은 원래 환경을 기준으로 하는 경계**를 남겼습니다.
