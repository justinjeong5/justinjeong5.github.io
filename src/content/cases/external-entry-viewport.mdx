외부 앱의 콘텐츠 링크를 누르면 iPhone Chrome에 새 탭이 열렸습니다. 그 첫 화면에서는 콘텐츠가 잘렸는데, 같은 탭을 새로고침하면 정상으로 보였습니다. 같은 페이지라도 처음 들어오는 순간과 다시 읽는 순간의 표시가 달랐습니다.

처음에는 작은 화면에 콘텐츠가 너무 큰 것인지, 상단 광고가 늦게 붙으며 내용을 밀어낸 것인지 의심할 수 있었습니다. 이 화면에는 광고 공간도 있었으므로 실제로 살펴볼 이유가 있는 가설이었습니다. 화면 높이나 CSS를 손대면 해결될 것처럼 보이기도 했습니다.

다만 새로고침만으로 정상화되는 증상은 콘텐츠 크기만으로 설명하기 어려웠습니다. 저는 CSS를 바꾸기 전에 광고가 붙는 시점과 외부 앱에서 브라우저를 처음 여는 순서를 나눠 살폈습니다. 어느 조건이 실제 화면의 차이를 만드는지 확인하려고 했습니다.

## 슬롯을 고친 뒤에도 남은 증상

광고 설정을 기다리는 동안 슬롯까지 사라지면, 광고가 준비된 뒤 콘텐츠가 아래로 밀립니다. 슬롯을 비동기 설정 gate 밖에 두고 최초 HTML부터 공간을 예약하도록 바꿨습니다. 광고 요청 여부는 내부에서 판단하되 그 공간은 유지하는 방식이었습니다.

슬롯을 유지하니 광고 준비 상태 때문에 레이아웃이 달라지는 경로는 줄었습니다. 하지만 외부 앱에서 처음 열 때의 화면 왜곡은 그대로 남았습니다. 슬롯 예약과 최초 진입의 표시 문제를 계속 나눠 조사해야 했습니다.

깨진 화면과 새로고침 뒤 정상 화면에서 viewport 높이, 문서 높이, 스크롤 위치, 배너 슬롯의 사각형을 비교했습니다. 관찰 시점의 값은 같았고, 슬롯도 이미 위쪽에 자리하고 있었습니다. 화면이 다르게 보인다는 사실을 DOM의 overflow나 슬롯 부재만으로 설명하기 어려워졌습니다.

## CSS를 더 바꾸기 전에 진입 경계를 나누기

문제는 같은 콘텐츠에서도 외부 앱에서 새 탭으로 처음 들어오는 조건에 묶여 있었습니다. 정상 상태의 geometry를 바꾸는 넓은 CSS 수정 대신, 첫 document navigation과 후속 navigation의 차이를 살폈습니다.

관찰이 가리킨 것은 페이지가 계산한 크기와 브라우저가 실제로 보여주는 영역 사이의 차이였습니다. 특정 브라우저 내부 callback을 원인으로 확정한 것은 아니었습니다. 브라우저의 표시 단계라는 가설과, 제품에서 적용할 수 있는 호환 처리를 나눴습니다.

최종 구현에서는 대상 최초 진입에만 같은 origin의 경량 문서를 거쳐 원래 화면으로 돌아오게 했습니다. hydration 전에 이동하고, 경량 문서의 `pageshow` 또는 완료 상태를 지난 뒤 두 번의 `requestAnimationFrame`을 거쳐 복귀했습니다. 단순히 화면 높이를 다시 계산하는 대신 후속 문서 이동을 통과시키는 절차였습니다.

## 우회도 실행 조건과 비용을 가진다

모든 화면과 모든 브라우저를 왕복시키지는 않았습니다. 대상 콘텐츠 경로, iOS Chrome, 최초 navigation, 비어 있는 referrer 조건을 확인했습니다. 같은 URL에 대한 marker로 복귀 후 다시 우회하는 반복을 막았습니다.

복귀 주소는 같은 origin과 허용한 콘텐츠 경로인지 검사했습니다. `replace`를 사용해 경량 문서가 별도의 뒤로 가기 단계로 남지 않게 했습니다. 정상 화면으로 돌아오는 것만큼 우회가 새로운 탐색 흐름을 만들지 않는 것도 중요했습니다.

비용은 남았습니다. 대상 진입은 문서를 한 번 더 거치며 원래 HTML을 다시 요청할 수 있습니다. 이 절차를 제거하려면 브라우저 버전이 올랐다는 이유만으로 판단하기보다, 같은 외부 최초 진입에서 화면과 요청 흐름을 다시 비교해야 합니다.

## 정상화한 경로와 아직 설명하지 못한 내부 원인

당시 실제 기기에서 확인한 대상 환경에서는, 새로고침해야 정상으로 보이던 최초 진입 화면이 정상으로 표시됐습니다. 서로 다른 대상 콘텐츠에서 이 결과를 확인했고, 슬롯 예약·제한된 bootstrap 왕복·진입과 복귀 조건 테스트를 포함한 변경도 병합됐습니다. 사용자가 콘텐츠에 처음 들어오는 경로를 정상으로 보게 한 것이 이 작업에서 확인한 화면 결과였습니다.

정상화는 우회 절차 전체의 결과입니다. 두 프레임 대기만의 효과나 브라우저 내부 원인을 단독으로 확정한 것은 아닙니다.

깨진 화면과 정상 화면의 DOM 측정값은 같았습니다. 그래서 CSS 크기를 더 바꾸기보다 최초 진입과 새로고침의 문서 요청 순서를 비교했습니다. 당시 확인한 기기에서는 제한된 문서 왕복을 적용한 뒤 새로고침 없이 화면이 보였습니다. 브라우저 내부 원인까지 확정한 것은 아닙니다.
