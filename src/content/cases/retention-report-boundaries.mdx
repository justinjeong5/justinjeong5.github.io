리텐션 리포트를 만드는 일은 그래프를 그리는 작업처럼 보인다. 하지만 운영자가 그 숫자로 판단하려면 어느 날짜를 기준으로 묶었는지, 빈 칸은 무엇을 뜻하는지, 아직 모이지 않은 데이터는 어떻게 읽어야 하는지가 먼저 필요했다.

화면에 표가 생겼는데 서로 다른 기간의 값을 같은 조건처럼 비교하거나, 자료가 제공되지 않은 칸을 실제 결과로 받아들인다면 리포트는 판단을 돕기 어렵다. 내가 이 작업에서 다룬 문제는 데이터를 보여주는 기능과 데이터를 읽는 조건을 함께 맞추는 일이었다.

## 날짜를 보내는 쪽과 기본값을 정하는 쪽

서버 담당자와는 FE가 광고의 시작·종료 날짜를 보내는 경우와 날짜 query를 생략했을 때의 기본값을 논의했다. 나는 두 경우를 나눠 계약을 제안했다. 화면에서 선택한 기간과 서버가 해석한 기간이 같은 질문을 가리켜야 했기 때문이다.

날짜 하나를 추가하는 것도 단순한 폼 변경은 아니었다. 어느 쪽이 기본 기간을 정하는지에 따라 화면의 입력과 조회 결과를 설명하는 방법이 달라진다. 이 협의는 이후 구현을 읽을 때도 입력을 보냈다는 사실과 서버의 해석을 따로 보게 만든다.

## 응답을 그대로 그리지 않고 행과 열의 의미를 맞추기

리포트에서는 기준일별 코호트와 전환 수, 기준일 이후의 day-offset 값을 표의 행과 열로 바꿨다. 응답에 들어 있는 날짜와 배열의 순서만 따라 출력하는 것이 아니라, 각 값을 해당 날짜 열에 놓는 정규화가 필요했다.

빈 위치를 채우는 방식도 화면 표현과 연결됐다. 정규화에서는 빠진 일자의 값을 0으로 채우고, 그래프에서는 0인 위치를 빈 셀로 표시했다. 이 구현은 같은 열 구조를 만들지만, 응답에 값이 없는 경우와 실제 값이 0인 경우를 화면에서 구분하지 못한다. 지금 다시 설계한다면 미관측 값을 별도 상태로 두고, 실제 0과 다른 표시를 주고 싶다.

CSV도 같은 날짜·전환 수와 일자별 값을 평평한 열로 만들었다. 화면에서 비교한 값을 파일로 가져가 다시 살펴볼 수 있어야 리포트가 읽는 데서 끝나지 않는다. 표와 내보내기가 같은 구조를 가리키는지 중요했다.

## 숫자 옆의 안내도 기능의 일부였다

데이터에는 표본과 실험적 성격, 완전성·갱신 시점, 작은 규모에서 제공되지 않는 값의 조건이 있었다. 이런 한계를 알리는 문구에도 참여했다. 선명한 그래프가 데이터의 조건까지 지워버리지 않도록 하는 설명이었다.

이 안내는 개발자의 책임을 피하기 위해 붙이는 문장이 아니라, 리포트의 수치를 해석하는 사용법이다. 아직 집계가 충분하지 않은 값과 안정적으로 비교할 수 있는 값을 같은 확신으로 읽지 않게 해야 했다.

QA에서는 통계 서비스 상태 때문에 전체 결과를 확인하기 어려운 상황도 공유했다. 화면이 정상적으로 그려지는지와 실제 자료가 올바른 조건으로 조회되는지는 다른 곳에서 만나는 문제였다. FE와 gateway, 통계 담당자가 함께 맞춰야 하는 작업이었다.

## 화면과 파일에서 같은 자료를 살펴볼 수 있게

구현 뒤에는 코호트의 날짜와 전환 수, 일자별 값을 표에서 비교하고 같은 구조로 CSV를 받을 수 있게 됐다. 데이터가 없는 화면과 자료가 있는 화면을 나누고, 자료가 있을 때 그 해석에 필요한 안내를 보여주는 흐름도 들어갔다.

사용량을 무엇으로 확인할지도 질문했다. 리포트가 열렸는지와 운영자가 어떤 판단에 쓰는지는 다른 질문이기 때문이다. 이것은 기능을 만든 다음에도 보고 싶은 결과였다.

이 경험을 돌아보면 리포트 UI는 숫자의 마지막 포장지가 아니다. 응답의 구조를 읽을 수 있는 표로 바꾸고, 숫자의 조건을 사용자가 판단할 수 있는 설명으로 연결하는 곳이다. 화면의 코드가 데이터의 의미와 만나는 지점을 다룬 작업으로 남았다.
